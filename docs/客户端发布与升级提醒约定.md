# 客户端发布与升级提醒约定

> 适用范围：AWBotDSH 桌面客户端、AWBot 安卓客户端、以及随 GitHub Release 分发的浏览器插件包。
> 编制：2026-11-23　|　结论均可按代码与线上 Release 回查。

AWBot 生态有三条**互不相干**的升级通道，都指向同一个仓库 `liujh0729-jpg/AI-enterprise-OEM`，但取的东西不同。发布时按本文件核对资产名，任何一端都能自动发现新版本；改名字就会断。

---

## 一、三条通道

| 通道 | 谁在用 | 取什么 | 结果 |
|---|---|---|---|
| 站点自升级 | 平台后台「平台升级」（`backend/src/upgrade/`，`UPGRADE_GITHUB_REPO`） | `releases/latest` 的源码包或 `.zip` 资产 | 服务端覆盖自身代码并可回滚，与客户端无关 |
| 手机端 AWBot | APK 内「设置 → 检查更新」（`awbot-app/app/lib/update/`，`updateRepo`） | `releases/latest` + 可选 `update.json` 清单 + `SHA256SUMS` | 下载对应 ABI 的 APK 并安装 |
| 桌面端 AWBotDSH | 应用菜单「检查更新…」、启动/回前台/唤醒的自动提醒 | `releases/latest` 的资产清单 | **只给下载直链**，不下载不安装 |

桌面端只在没有封入更新源的发行版（安装包里不存在 `resources/app-update.yml`，即 unsigned 构建）才走 GitHub 通道；封入更新源的构建仍走 electron-updater 私有 feed，不发这些请求。

## 二、请求地址与仓库配置

- 元数据：`GET https://api.github.com/repos/<仓库>/releases/latest`，无 Token，公开仓库；未鉴权按 IP 限流 60 次/小时，因此桌面端自动检查按 **24 小时**节流，且只在有新版时提醒一次。
- 桌面端仓库地址在打包时封入应用清单字段 `awbotdshReleaseRepository`，默认 `liujh0729-jpg/AI-enterprise-OEM`；换仓库用打包环境变量 `AWBOTDSH_RELEASE_REPOSITORY=<owner>/<repo>`，不改代码。
- 下载直链一律用 Release 返回的 `browser_download_url`，客户端不自行拼接。

## 三、资产命名契约（关键）

客户端按**资产文件名**识别版本，不是按 Release tag。命名不符的资产会被直接忽略。

| 组件 | 必须的文件名 | 版本取自 | 已装版本来源 |
|---|---|---|---|
| 桌面客户端（Windows） | `AWBotDSH-<版本>-win-x64[-unsigned].exe` | 文件名里的 `<版本>` | 应用自身版本号 |
| 桌面客户端（macOS） | `AWBotDSH-<版本>[-arm64\|-x64\|-universal][-unsigned].dmg` | 同上 | 同上 |
| 企业浏览器插件 | `aipdd-enterprise-v<版本>.zip` | 文件名里 `v` 之后的部分 | 随包 `aipdd-enterprise/manifest.json` 的 `version` |
| 网页桥接扩展 | `awbotdsh-chrome-bridge-v<版本>.zip` | 同上 | 随包 `chrome-bridge-extension/manifest.json` 的 `version` |
| 安卓客户端 | `AWBot-<版本>-arm64.apk`（或 `-x64`） | 文件名 | APK 自身版本 |
| 安卓清单（可选） | `update.json`、`SHA256SUMS` | — | 手机端优先读清单，缺失时回退用 API 结果 |

要点：

1. **同一组件在 Release 里可以并存多枚**（例如新旧两版安装包），客户端取语义化版本最大的那枚，与上传顺序无关。
2. **版本比较是宽松的语义化比较**：`1.30.02` 这类带前导零或四段的 Chrome 清单版本能正常解析；`0.2.2-rc.5 < 0.2.3` 的预发布序也正确。非版本字符串会被当作无效而不报告。
3. **站点版本与客户端版本不同轨**（站点 `v1.8.0`，客户端 `0.2.2-rc.5`），所以桌面端绝不用 tag 当客户端版本，只看资产文件名；发布 tag 只用于 Release 页面链接。
4. 桌面端**不会**因为发现新版而自动下载或安装；插件包更新同样只给链接，需人工替换并重新加载扩展。

## 四、桌面端提醒形态

- 手动：应用菜单「检查更新…」→ 逐行列出「组件：当前 → 最新」，按钮「前往下载 / 复制直链 / 打开发布页 / 稍后」；无新版时显示当前版本；连不上仓库时提示可打开发布页。
- 自动：启动、回到前台、系统唤醒时按 24 小时节流查询，仅当**客户端本体**有新版时发一次系统通知，点击打开下载直链。同一版本的提醒在 `userData/release-notices` 落标记文件，重启不重复。
- 左下角更新状态位对这类无 feed 构建不再显示「检查失败」。

## 五、发布动作清单

1. 出包（AWBotDSH 桌面端私有源码仓）：`pnpm --filter @deepseek-ai/dsh-desktop run package:win:x64:unsigned`，产物在 `apps/desktop/.desktop-build/targets/win-x64/unsigned-artifacts/`。
2. 上传前自证新逻辑确实在包里：读 `win-unpacked/resources/app.asar` 与 `app.asar.unpacked/.../bundled-extensions/*/manifest.json`，确认关键符号（如 `DesktopReleaseNotice`、`awbotdshReleaseRepository`）与扩展版本一致。
3. 覆盖同名资产：先传临时名资产、比对 GitHub 回算的 `digest` 与本机 `sha256`，再删旧资产、把新资产改回正式名；`content_type` 不能在 PATCH 阶段提交。覆盖会把该资产的 `download_count` 归零。
4. 覆盖后验证：`api.github.com/repos/<仓库>/releases/latest` 能看到新资产名与大小；直链分段下载返回 206。
5. 老包看不到这些提醒——**第一次升级必须让用户手动装新包**，此后才自动提醒。发布说明里要写清这条。

## 六、失效自查

| 现象 | 原因 |
|---|---|
| 有新版但「已是最新版本」 | 资产名不合第三节的模式，或文件名里的版本与已装版本相同 |
| 弹窗提示读取失败 | 仓库改名/转私有、Release 未发布、或触发了未鉴权限流（稍后重试） |
| 只有插件行没有客户端行 | 当前平台没有匹配的 dmg/exe 资产（例如只上传了 Windows 包却跑在 Mac 上） |
| 重启后重复提醒 | `userData/release-notices` 不可写（标记写入失败只记日志，不阻断功能） |
| 手机端拿不到包 | 没有匹配 ABI 的 `AWBot-<版本>-arm64.apk`，或 `update.json` 指向了不存在的资产名 |
