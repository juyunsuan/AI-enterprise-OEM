# 建站管理 · 健康管理小程序工具 设计方案

> 状态：**已确认范围，实施中**（2026-11-18 需求方拍定四项口径，见 §一）。
> 参考源码：《php 智慧医疗管理系统》（微擎 We7 架构 + `hyb_yl` 医疗插件 + `hyb_ylmz` 门诊插件；MySQL 331 张表（含微擎框架表）、原生微信小程序 289 页、PC 端 web/app 两套管理界面）。分析产物在 `.tmp-ref/health-ref/`（页面清单 `pages.txt`、表清单 `tables_parsed.txt`），**该目录在 .gitignore 内，源码与数据种子不入仓**。
> **本方案不是移植参考源码，而是把它全部业务能力按本项目技术架构（Next.js 16 + Hono + Prisma + antd 6 + zod 契约 + 原生微信小程序）重写一遍**：代码、文案、界面、数据结构全部自写，不复制、不翻译搬运参考包内任何文件（第三方商业程序，含授权校验类文件）。
> 本业务与平台其它业务**互不影响**：独立表前缀 `health_`、独立契约前缀 `Health_`/`HealthAdmin_`、独立路由域 `/enterprise/health/**` 与 `/api/public/health/**`、独立功能码 `health`、独立小程序工程 `miniprogram-health/`。只**向下调用**平台既有底座（见 §二），底座不为它改行为。

## 一、产品口径（需求方已确认）

| 决策点 | 结论 |
| --- | --- |
| 交付范围 | **丙档：全量对齐参考源码**。参考包的 15 个功能簇、8 类角色全部重写——含医院/科室/医生库与号源挂号、药品与器械实物商城（含物流售后）、机构与医生自助入驻 + 分账提现、推客分销、保险理赔申请、绿通就医与手术快约、体检中心、药师审方、健康科普与患教社区。 |
| 小程序内「卖东西」 | **另带实物商城**：商品/SKU/购物车/下单/发货/收货/售后全流程在健康管理店铺内自成一域；**不**与已上线的「电商平台小程序」共用商品与订单表（两条业务互不影响是硬要求）。 |
| 入驻与结算模型 | **支持机构与医生自助入驻 + 分账提现**：机构（医院/诊所/体检中心）与医护（医生/健管师/药师/导诊师）各自提交资质 → 店主审核 → 上架接单；服务收入按店铺设定的分账比例计入机构与个人收益，个人可申请提现（银行卡台账 + 提现规则与税点），**平台不经手资金**，提现由店主线下完成，线上只做台账与状态。 |
| 端与沟通 | 一部小程序里做**顾客端 + 医护工作台端**（同一工程内按身份切页，分包控制主包体积）。**所有文字沟通与在线客服统一复用平台 AI客服（service-desk）的开放会话**，不自建聊天系统；电话/视频问诊做成**预约单 + 订阅消息到点提醒 + 回拨**，不建 WebRTC 房间。 |
| 资金与收款 | 沿用上门服务/电商小程序已定口径：顾客付款直进**该店铺自己的微信支付商户号**（`WechatPayClient` JSAPI + 回调 + 原路退款），平台侧可一键关掉「允许在线收款」；关掉后订单落线下收款标记，不生成支付通道。 |

### 与「既有底座」的分工（重要）

平台已经为自营小程序工具沉淀了一层私域底座（`backend/src/private-mini/`，2026-11-18 由上门服务与电商两工具共建）。健康管理是**第三个接入方**，凡是「主体凭据、出包、发布、顾客身份、支付通道」这类与业务语义无关的事，一律走底座，**不在 health 域里重写第二遍**：

| 能力 | 复用点 | 健康管理侧要做的 |
| --- | --- | --- |
| 小程序主体凭据（AppID/AppSecret/代码上传密钥/商户号/APIv3/合法域名/类目/订阅模板） | `miniProgramApp` 表（`scene` 判别）+ `MiniAppService`（掩码回显、自检、payRuntime、requireUploadCredentials） | 契约加 `HEALTH` 场景；`Onsite_saveWechat` 同构的 `Health_saveWechat/testWechat` |
| 出包（模板注入 → zip） | `private-mini/package-builder.ts`（`collectTemplate` / `injectConfig` / `injectAppId` / `buildStoreZip` / `assertPackageSize` / `readTemplateMeta`） | 提供 `miniprogram-health/` 模板 + 注入键 `apiBase` / `shopCode` / `appId` |
| 出包台账 | `miniProgramTenantRelease`（`scene` 判别，含版本/通道/SHA-256/直传状态/审核态/下载数） | 直接按 `scene='HEALTH'` 读写，不建第二张发布表 |
| 直传微信 | `miniprogram/miniprogram-ci.service.ts`（子进程 + 同店互斥） | 复用；沿用「只生成开发版，提审发布在用户自己的微信公众平台」文案口径 |
| 微信接口（token / 小程序码 / 订阅消息 / code2Session） | `miniprogram/miniprogram.client.ts` | 复用 |
| C 端身份与令牌 | `private-mini/customer-token.ts`（独立 HMAC 令牌，与站内 User 物理隔离） | 复用同一签名族，`scene` 带 `HEALTH`；顾客表独立 `health_customers` |
| 微信支付 JSAPI / 回调 / 退款 | `points/wechat-pay.client.ts`（`WechatPayClient`） | 复用（上门服务即用此实现） |
| **在线客服与会话** | **`service-desk`（AI客服）**：站点 siteKey、坐席 agents、开放会话 `/api/public/service-desk/open/session`、消息 SSE `/open/stream/:id`、上传 `/open/upload`、满意度 `/open/rate/:id`、渠道回调 | 只做**绑定**：把健康管理的「图文问诊咨询」与「在线客服入口」映射成该店铺的一个 AI客服站点 + 坐席（店主/医护），问诊单号写进会话元数据；**不写任何聊天表** |
| 文件与图片 | `oss/oss.service.ts` | 复用 |
| 站点域名（出包与支付回调都要） | `common/site-url.ts` | 复用 |
| 单据号方言 | `common/document-number.ts` | 复用 |
| 审计留痕 | `auditLog` | 复用 |
| 订阅消息字段位约定 | `private-mini` `MINI_TEMPLATE_KEYS` + 各业务 notify service 的写法 | 在 health 域内按「健管场景字段位」实现一份 notify service（字段位与上门服务不同，属业务语义，不塞进底座） |

**明确不复用**：上门服务（`onsite_*`）与电商（`mall_*`）的业务表、状态机、装修组件、技师排班引擎——它们各自是独立业务，健康管理的号源、订单、商品都要自己的实现与自己的表。各板块的开关与停服动作互不复用。

## 二、命名与落点约定

| 层 | 落点 |
| --- | --- |
| 业务键 | `health`（功能码、菜单、平台参数键 `health_platform_settings`） |
| 契约 | `packages/contracts/src/health.ts`；操作前缀 `Health_`（店主端）、`HealthAdmin_`（平台侧）；场景常量 `HEALTH` 加入 `PRIVATE_MINI_SCENES`。医护端走免登录公开通道，不进 JSON 契约与 OpenAPI |

| 工作台前端 | `frontend/src/app/health/**`，`frontend/src/api/health.ts`；卡片入口 `frontend/src/app/site-builder/page.tsx`「小程序」板块第 4 张卡 |
| 平台后台 | `ADMIN_SECTIONS` 增 `{ key: "health", group: "system" }`，页签组件 `frontend/src/app/admin/_components/health-tab.tsx` |
| 小程序工程 | 仓库根 `miniprogram-health/`（原生微信小程序，无构建依赖；模板目录可用 `MINIPROGRAM_HEALTH_DIR` 覆盖） |
| 迁移 | 从 `0122_health_core` 起按簇递增（当前仓库最新为 `0121_onsite_address`） |
| 方案与实现差异 | 以代码为准，回写本文 §十四「落地实况」 |

> **易混点**：`backend/src/health.controller.ts` 是平台存活探针（`GET /health`），与本业务无关；本业务全部路由带 `enterprise` 或 `public/health` 前缀，不会与之冲突。前端路由 `/health` 属工作台页面树，也不冲突。

## 五、核心算法与状态机（集中实现点，禁止散写）

| 实现点 | 文件 | 口径 |
| --- | --- | --- |
| 订单状态机（12 种 bizType） | `health.order.rules.ts` | `PENDING_PAYMENT → PAID →(履约分支)→ SERVING/DELIVERED → COMPLETED → REVIEWED`；旁路 `CANCELLED/EXPIRED/REFUND_PENDING/REFUNDED/AFTER_SALE_*`；`bizType` 决定可达集合与核销要求（挂号/体检/年卡权益必须核销，商品必须收货）。状态转换表 + 非法转换抛业务异常，全部单测覆盖 |
| 算价引擎 | `health.order.pricing.ts` | 原价 = Σ(明细 × 数量 × 会员/服务价) → 券（满减/折扣，作用域命中） → 积分抵扣（比例与上限） → 运费（模板：包邮门槛/区域加价/门店自提 0）→ 实付；每单落 `health_order_price_flows` 快照，改配置不影响历史单 |
| 号源引擎 | `health.slot.engine.ts` | 周模板 → 生成日排班 → 拆号源行；占用判定按 `slotId` 行锁式条件更新（`occupied < quota`）；取消/退款按 `trade.refundReleaseSlot` 决定是否回补；跨零点与「最少提前 N 分钟」同上门服务口径 |
| 指标异常规则 | `health.metric.engine.ts` | 规则类型：绝对上下限 / 相对基线偏移 / 连续 N 次同向 / 时段限定；命中写 `health_alerts` 并按规则通知对象扇出；去重窗口 `alertDedupeMinutes` 防轰炸；**只报「超出你的管理目标区间」，不下诊断结论** |
| 随访任务生成 | `health.followup.engine.ts` | 方案步骤 → 未来 N 天任务（周期 + 起止 + 节假日顺延策略）；完成/跳过/逾期三态；逾期升级提醒给责任人与店主 |
| 分账与收益 | `health.commission.engine.ts` | 支付成功时按作用域优先级（服务 > 医护 > 机构 > 店铺默认）算 `health_order_shares`；退款按比例冲销；`settleableAt = 完成 + canTxHours` 后才进可提现收益 |
| 核销 | `health.verify.service.ts` | 一单一码（`verifyCode`），扫码核销校验店铺 + 状态 + 有效期；已核销不可重复；年卡权益按「权益次数」扣减 |
| 会话绑定 | `health.consult.service.ts` | 问诊单接单 → 用该店铺 AI客服站点开一条开放会话（顾客令牌身份 + 坐席=接诊医护）→ 会话 id 回写；会话结束评价回写订单评价；**本域零聊天表** |
| 触达 | `health.notify.service.ts` | 订阅消息字段位固定并公示（下单/接单/随访提醒/服药提醒/预警/预约开始）；失败只留痕不抛错，绝不带崩业务链路 |

## 十、业务隔离边界（硬要求）

1. **表**：只写 `health_*` 与底座共享表（`miniProgramApp`/`miniProgramTenantRelease`，按 `scene='HEALTH'` 过滤）。不读写 `onsite_*`/`mall_*`/`knowledge_pay_*`，不做跨业务 JOIN。
2. **路由**：`/enterprise/health/**`、`/enterprise/admin/health/**`、`/api/public/health/**`；其它模块不因本次改动新增或变更行为。
3. **底座改动仅限「加场景」**：`PRIVATE_MINI_SCENES` 增加 `HEALTH`、label 增加一项；`package-builder`/`ci`/`customer-token` 的行为对 ONSITE/MALL 保持逐字节不变（有单测锁定）。
4. **AI客服只当服务用**：健康管理不引入对 service-desk 的写死依赖之外的改动；若 AI客服侧需要新增字段（如按业务来源过滤会话），走它的既有 `meta`，不改它的表。
5. **资金**：顾客钱进店铺自己的商户号；店内积分/余额/收益是店铺内账，不与平台积分体系（算力积分、卡密）互通、不折算。
6. **失败面**：本板块被平台关闭 → 只拦 `/enterprise/health/**`；C 端通道返回「服务未开通」空态；对其它板块零影响。

## 十二、合规红线（健康/医疗属性必须内建，不是选项）

1. **不出诊断**：任何自动逻辑（导诊、指标预警、报告解读、AI 建议）都表述为「提示/建议/就医参考」，界面与接口文案不得出现「确诊」「已患」结论；诊断字段只允许认证医护人工填写并留痕。
2. **处方与药品**：处方单必须挂认证医师 + 药师审核态；处方药（`health_drugs.prescriptionRequired`）在商城下单前强制先有有效处方/关联问诊单，缺则拦下单并说明原因。
3. **资质留痕**：机构与医护的执业资质件、审核人、审核时间全部进店内台账，由店主在工作台内审核与下架；下架即端上不可见，历史单保留，平台不介入具体内容审核。
4. **敏感个人信息**：健康数据属敏感个人信息——协议与采集告知（`health_agreements`）强制展示、下单/建档处明示收集范围；证件号、手机号列表页脱敏展示；订阅消息与推送不带明文病情；导出与删除按店铺提供「导出我的数据 / 申请删除」通道并留审计。
5. **资金与代收款**：平台不代收款、不代提现打款；线上只做台账。平台侧「允许在线收款」开关是资金合规闸门，关掉后即便店铺填了商户号也不下发支付通道。
6. **紧急就医**：小程序在预警、问诊首页与协议处固定提示「急危重症请直接拨打 120 或就近急诊」，本工具不构成急救指导；一键求救类能力沿用上门服务已有报警口径另实现，不与预警混淆。
