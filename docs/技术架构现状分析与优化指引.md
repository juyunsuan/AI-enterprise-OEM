## 一、执行摘要

**一句话现状**：这是一个以 **Hono + Prisma（MySQL/PostgreSQL 双方言）** 为后端、**Next.js 16 纯客户端渲染** 为 Web 前端、通过 **`@enterprise/contracts` 契约包** 打通前后端类型、并以 **6 个物理独立的微信小程序 + 4 类外部设备客户端** 为触点的**大型企业 SaaS 单体工作台**。

**架构上的三个鲜明特征**（均为代码事实）：

1. **契约驱动 + 约定式路由是主干**：后端并非 Nest 式分层单体，而是 `packages/contracts/src/endpoints.ts`（15722 行、440 个 `path:` 条目）定义端点，`backend/src/http/automation-routes.ts` 用 `moduleHandlers()`（88 次调用）按前缀约定派生 handler，动态注册；命令式 `route-groups/`（26 域）与 `app.ts` 公开通道并存。README 口径的 2087 个 HTTP 操作与契约 440 个 path 是两种统计维度（前者含全部 handler 变体与内部操作，后者是契约化端点条目）。

2. **租户与身份靠"键 + 令牌 issuer"实现逻辑隔离，而非数据库级隔离**：无独立 `Tenant` model，租户统一抽象为 `(orgType, orgUserId)`（`tenant/tenant-scope.service.ts:11`）；C 端顾客按 `shopId/siteId + customerId` 双条件过滤；不同终端用不同 JWT issuer + HKDF/HMAC 派生密钥做**物理隔离**。这套设计边界清晰、注释完备，但**隔离正确性高度依赖每个 service 自觉过滤**，缺少数据库层强制约束。

3. **能力在"技术底座层"共享充分，在"业务终端层"几乎零共享**：Web 侧 `api/http.ts` + `endpoint.ts`（2163 处调用）+ `query/business.ts` 高度统一；后端 `transport.ts`（唯一网络出口）、`ai-gateway.ts`、契约包均为真正共享。但 **6 个小程序的 `request.js / auth.js / session.js / api.js` 是纯物理复制**（kp↔card-shop 的 request.js 相似度 88.3%，dh↔kp 的 session.js 相似度 82.0%），后端 5 套令牌模块中 dh↔kp 相似度 62%。

**最需要决策的一件事**（详见第八、十章）：**"用户"和"订单"这两项能力在 6 个小程序里被重复实现了 6 遍，且数据、令牌、表结构各自独立**。这在单机小团队早期是"快"的选择，但随着小程序数量增长，已形成**一致性风险（一处安全修复要改 6 份）、扩展性差（新增小程序=复制 5-7 个 utils）、边界约定化（onsite/brand/card-shop 共用 `private-mini-customer` issuer，仅靠 `scene+shopId` 双条件过滤）** 三重压力。建议按"**公共底座抽包 + 领域能力收敛**"两步走，而不是激进合并数据表。

## 三、项目分层与工程拓扑

### 3.1 Monorepo 边界

`pnpm-workspace.yaml` 只声明 3 类成员：`frontend`、`backend`、`packages/*`。这是**唯一的编译期代码共享边界**。

| 工程 | 包管理 | 是否进 workspace | 是否依赖 `@enterprise/contracts` |
|---|---|---|---|
| `backend` | pnpm | ✅ | ✅ workspace:*（315 处引用，排除历史快照） |
| `frontend` | pnpm | ✅ | ✅ workspace:*（669 处引用） |
| `packages/contracts` | pnpm | ✅ | 自身即契约源 |
| 6 个小程序 | 无 package.json | ❌ | ❌ 纯物理复制 |
| `bot-host-client` | npm（独立 lock） | ❌ | ❌ |
| `awbot-app` | Flutter | ❌ | ❌ |
| `extensions` / `hardware-devkit` | 原生 / Python | ❌ | ❌ |

**结论**：契约包只在 Web 前后端之间真正复用；小程序与外部客户端靠"HTTP 协议 + 出包时配置注入"对齐，不共享代码。

### 3.2 部署拓扑（docker-compose.yml + infra/nginx）

- 本地一键：`mysql:8.0`（:13306）→ `api`（backend/Dockerfile，:1690，启动即 `prisma migrate deploy`）→ `web`（frontend/Dockerfile，:15890）。
- nginx `enterprise.conf` 监听 **:15889**，`/api/*` 反代 1690（SSE 关缓冲、300s 超时），`/` 反代 15890；独立 `default_server` 承接 GEO 独立站，按 Host 反查站点。
- 生产：`backend/.env.production.example` + `production-database.mjs check/backup/migrate`（要求 24h 内备份 + sha256 + 0600）。

## 四、核心模块分析

### 4.1 后端：Hono 应用层与三条路由路径

**入口装配**（`backend/src/main.ts:24`）：`validateConfig()` → `createServices()` → 构造约 28 个 scheduler → `prisma.$connect()` → `createApp()` → `serve()`，含 SIGTERM/SIGINT 优雅关闭。

**DI 容器**（`backend/src/http/services.ts`）：`createServices()`（:555）手工 `new` 出全部 service/controller，`type Services = ReturnType<typeof createServices>`（:3682）。**全项目唯一组装点，无第三方 DI 框架**——优点是依赖可见，缺点是单文件 3682 行、任何新增依赖都要改这里。

**三条路由路径并存**（这是理解后端最关键的事实）：

| 路径 | 文件 | 机制 | 规模 |
|---|---|---|---|
| A. 契约动态注册（主干） | `http/automation-routes.ts` | `handlers` 映射（:177，约 470 条手写）+ `moduleHandlers(prefix, controller)`（:1329，88 次调用）按前缀派生方法名 | 440 契约端点 |
| B. 命令式业务域 | `http/routes.ts` + `route-groups/*.ts` | 每域显式 `app.openapi(createRoute(...), handler)` | 26 个路由组 |
| C. 公开通道 | `http/app.ts:460-522` | 各 `registerXxxPublic`，免站内会话 | 15+ 通道 |

> 注意 `:1607-1609` 按路径参数个数排序注册，避免静态路径（如 `merge-preview`）被 `/:id` 抢占——这类细节说明路由层有成熟的工程经验，但也说明动态注册的心智负担不低。

**认证链**（`auth/auth.service.ts:44` `authenticate()`）：
1. `/api/v1/**` 机器通道：`x-api-key` 或 `Bearer ek_`，sha256 查 `ApiKey` 表 → `AuditLog`；
2. 公开请求白名单（:19-35）；
3. 站内请求：`parseAccessToken()` → 必须 `isSsoSession` → `accounts.assertSessionValid()`（tokenVersion 二次核对）。

JWT 自签（`auth/token.ts:16`）：issuer `enterprise-sso`，默认 2 天，「记住我」30 天，密钥 `HMAC(JWT_SECRET,'enterprise-sso-session')`（:156）与上游令牌密钥分离；Cookie 名 `aiworkin_token`（`auth/session.ts:21`）。

**租户与身份**：无 `Tenant` model；`Tenant={orgType,orgUserId,...}`（`tenant/tenant-scope.service.ts:11`），`resolve()`（:55）按 5 级优先级（主体切换器 → 自有企业 → 在职成员 → 旧挂靠 → 个人）解析；`requireMember()`（:202）校验目标在册。RBAC 用 `requireRoles/hasRole/requireAdmin`（`identity/identity.service.ts:383,420,431`）。

### 4.2 数据层：扁平宽表 + 无 DAO

`prisma/schema.prisma`：816 model、0 enum、**仅 16 处 `@relation`**、129 migrations。多数表用 `orgType/orgUserId` 或 `shopId/customerId` 字符串硬关联，属**刻意扁平宽表**而非标准关系建模。

- 无 repository/DAO 目录，各 `*.service.ts` 直接 `this.prisma.<model>.xxx()`；`$transaction` 出现在 112 文件、259 处。
- `PrismaService extends PrismaClient`（`prisma/prisma.service.ts:7`）：连接池 `connection_limit`（默认 10，geo-worker 4）、慢查询告警（默认 500ms）、`$use` 中间作身份缓存失效与指标。
- 双方言：MySQL schema 是唯一事实源，`scripts/gen-prisma-schema.mjs` 派生 PG schema；`common/db-provider.ts` 仅少数原生 SQL 按方言分支。

**架构含义**：扁平宽表换来了查询简单与迁移可控，但把"租户隔离"的责任完全推给了 service 层的 WHERE 条件——这正是第八章要重点评估的风险来源。

### 4.3 Web 前端：纯 CSR + Context/TanStack Query

- Next.js 16.2.7 + React 19.2.4 + Antd 6.3.1；118 `page.tsx`（106 个 `"use client"`），**0 个 `route.ts`**，SSR 仅用于根布局 metadata。连官网首页都用 `useEffect + homepageApi.view()` 客户端取数（`app/page.tsx:47-58`）。
- 状态：无 zustand/redux；4 个核心 Context（`providers.tsx:42-53`）+ TanStack Query（`query/business.ts`，QueryKey 以 `["private",userId,identity,enterprise]` 作用域隔离）。
- API 层：`api/http.ts:17` `http<T>()`（`credentials:"same-origin"`，**不设 Authorization 头，全靠 Cookie**；401 派发 `enterprise-session-expired`）+ `api/endpoint.ts:22` `endpoint(definition)`（2163 处调用，Zod 校验入参、拼 `/api/backend`）。仍有 69 处手写 `http()`/30 文件绕过契约。
- 会话中枢 `lib/session.tsx`：`SessionProvider` + `BroadcastChannel('enterprise-session')` 多标签同步 + `clearPrivate()` 切身份清缓存。
- i18n 8 语言（ar RTL），`messages.ts`（1526 行）以中文原文为 key，文件头自述"仅覆盖骨架，深层页面未系统化翻译"。
- 工程压力：`scripts/with-heap.mjs` 强制 10GB 堆（默认 4GB 会 OOM），`next.config.ts:10-19` 关闭 Turbopack 磁盘缓存（曾膨胀到 87GB）。

### 4.4 契约包：`@enterprise/contracts`（全仓唯一编译期共享）

- `packages/contracts/src/endpoints.ts`（15722 行）：聚合 60+ 模块的 `xxxEndpoints`，`type ModuleEndpoints = ...交叉类型`，`export const endpoints`（:15645）展开合并；440 个 `path:` 条目；`EndpointId/EndpointInput/EndpointResponse` 由 endpoints 反推。
- `index.ts`：`apiEnvelope()`（:31）、`requestPath()`（:102）、`safeNextPath()`（:92，防开放重定向）、`ApiError`、`ErrorCode`（errors.ts，含业务码如 `FEATURE_CLOSED 26001`）。
- **设备通道端点刻意不在 endpoints.ts**（`bot-host.ts` 文件头说明）：设备通道用极简 `{ok,...}` 信封，不走站内 `code/message/data`。
- 架构守护 `scripts/check-architecture.mjs`：用 TS AST 强制"契约只能 import zod/相对路径、禁类型断言"、"网络请求必须走统一传输层"、"前端不得依赖服务端配置/DB"。项目**有真正的架构护栏**，这一点值得肯定。

### 4.5 外部客户端（协议耦合，不共享代码）

## 六、关键业务流程

### 6.1 企业账号登录与会话（Web + 用户版小程序）

```
Web 登录页 → POST /api/auth/login (auth/session.ts:105)
  → account.login → issueSsoSession(userId,...,tokenVersion) → setCookie(aiworkin_token)
  → 前端 SessionProvider.me() 拉身份 → 多身份弹窗 switchIdentity → navigationFor() 按身份过滤菜单
用户版小程序 → POST /api/public/miniprogram/login (miniprogram.public.ts:61)
  ├─ 账号密码登录(可选带 code 顺带 upsertBinding 绑 openId)
  └─ 仅 code → miniprogram.client.ts:38 code2Session → findByOpenId/UnionId → 已绑签发 issueSsoSession
  → 未绑定回 bound:false → 跳 login 页账号密码绑定 (pages/login/login.js:100)
```
关键：**用户版小程序复用企业 SSO**，是 6 个里唯一进入 `/enterprise/**` 的；其余 5 个都是私域身份，各自的令牌进不了站内。

### 6.2 私域顾客下单与支付（以品牌商城为例，其余同构）

```
小程序 auth.ensureLogin() → api.login({shopCode,code}) → 后端 code2Session → upsert BrandCustomer
  → 签发 customer 令牌(issuer=private-mini-customer, payload=scene+shopId+customerId+openid)
  → 顾客态读写一律 Authorization: Bearer + ?site/shopCode 寻址
下单: api.previewOrder → api.createOrder → api.payParams → wx.requestPayment
  → 微信支付回调 → brand.pay.service.ts 验证 → brand.order.service.ts 改单
  → 一切读写按 shopId + customerId 双条件过滤 (app.ts:510 注释 + 各 service)
```
onsite 多一条技师链：`顾客令牌 → bind → staff 令牌(issuer=private-mini-onsite-staff)`，技师订单按 `shopId+staffId` 过滤；`onsite.staff-api.spec.ts:235` 有测试明确验证"顾客令牌不能当技师令牌用"。

### 6.3  Bot/AWBot 心跳领取（平台控制 N 台设备）

```
客户端(5s) POST /api/public/bot-host/heartbeat (x-bot-token)
  → bot-host.service.ts:1345 heartbeat(): 刷新在线态 + 领取 PENDING 指令 + 回带需中断指令码
  → 客户端 runner 按 commandCode 幂等入队 → 本机 Agent 执行 → /progress 增量回传 → /result 终稿
  → 平台对话流式展示。离线指令落库，上线按序领取；AWBot 按 clientKind=AWBOT 共用服务、独立通道
```

### 6.4 异步调度

`main.ts` 启动约 28 个 scheduler（超时未付回收、内容池捞 PENDING、SCRM 日切、GEO 出账等），`common/schedule.ts` 是统一排期算法（once/scheduled/recurring、错过不补跑）；独立 GEO worker（:1695）跑采集与 SEO。

## 七、数据流与依赖关系

```
依赖方向（A → B 表示 A 依赖 B）：

  frontend ──workspace:*──▶ @enterprise/contracts ◀──workspace:*── backend
  frontend ──HTTP /api/backend/*──▶ backend (Cookie 会话)

  backend 各 service ──直接 Prisma──▶ MySQL/PG (无 DAO 层)
  scripts/* ──读 dist / 读源码──▶ contracts & backend (构建期守护,不参与运行时)

  企业侧实体 → Account/UserDirectory/EnterpriseProfile, 键 (orgType,orgUserId)
```

### 8.3 场景深评：多个小程序同时使用"用户"和"订单"能力

这是用户最关心的场景。逐维度评估如下（每条带依据）：

**① 复用性 —— 低（技术骨架零复用）**
- 6 份 `request.js`/`auth.js`/`session.js`/`api.js` 物理独立，无 import 共享；`pnpm-workspace.yaml` 不含小程序，各工程连 `package.json` 都没有。
- 唯一共享发生在**出包时的配置注入**：`scripts/pack-miniprogram.mjs` 与 `backend/src/private-mini/package-builder.ts:156 injectConfig()` 只改写 zip 内 `config.js` 的 `apiBase/shopCode/siteCode/appName/themeColor`，源码仓库文件永不变。即"配置共享、代码不共享"。

**② 耦合度 —— 前端低耦合高重复；后端耦合清晰但靠约定**
- 前端各改各的，改一处不影响别处（低耦合），但代价是 6 份同步（高重复）。
- 后端：用户版与 `/enterprise/**` 企业会话强耦合；其余 5 个各走 `/api/public/<域>/**`，互不依赖（清晰）。真正的耦合风险是 **onsite/brand/card-shop 共用 `private-mini-customer` issuer**，隔离完全依赖 payload 的 `scene+shopId+customerId` 与业务层双条件过滤（`customer-token.ts:12` 明确写"越权判定由业务侧按这三个值做双条件过滤"）——这是**约定式边界**，不是强制边界。

**③ 数据归属 —— 完全独立（这点是优点也是负担）**
- 每域有专属表族：`MiniProgramBinding`（企业）、`DigitalHumanMember/Order`、`KnowledgePayMember/Order`、`OnsiteCustomer/Order(+Addon/Refund)`、`BrandCustomer/Order(+Item/Refund)`、`CardShopCustomer/Order(+OrderCard)`。
- openId/unionId 分别落在各自表，按 `siteId|shopId + openid` 唯一约束。
- 优点：域间数据天然隔离，一域迁移不影响他域。负担：同一个"用户"在多个小程序是多个身份，无法跨平台识别（除非靠 unionId 手工关联，只有企业侧 `MiniProgramBinding` 注释提到 unionId 反查）。

**④ 权限边界 —— 设计稳固，但存在两处约定式软肋**
- 稳固处：issuer 分级（enterprise-sso / dh-member / kp-member / private-mini-customer / private-mini-onsite-staff），密钥按 issuer 派生，`app.ts` 各公开通道注释 + onsite 测试均验证"顾客令牌进不了 `/enterprise/**`""技师令牌与顾客令牌物理隔离"。
- 软肋一：onsite/brand/card-shop 共 issuer，隔离靠 `scene+tenantId` 双条件——**任一 service 漏写一个 WHERE 条件就可能跨店/跨场景越权**，且没有自动化审计覆盖所有 service。
- 软肋二：`customer-token.ts` 与 `dh/kp token` 签名口径不一（前者 `createHmac(...).update(issuer)` 返回 Buffer，后两者 `createHash(...).update("oem-xxx|"+secret).digest('hex')`），是两套密钥派生范式，增加误配风险。

**⑤ 扩展性 —— 差**
- 新增一个小程序 = 复制 5-7 个 utils 文件 + 后端新建模块 + 新表族 + 新 issuer/Token 模块 + 新 `registerXxxPublic`。没有模板、没有生成器、没有共享包。
- `services.ts`（3682 行）每加一个域都要手改装配。

**⑥ 一致性 —— 高风险（最实质的痛点）**
- **401 处理有 4 种口径**：用户版 `clearToken` 后抛错；dh/kp/card-shop 清 token 抛"请重新进入小程序"；onsite 区分顾客/技师双清；brand 则**唯一实现 401 自动重登一次**（`request.js:93-98`，用 `send()`/`request()` 分离避开循环依赖）。
- 任何安全修复（token 刷新、错误码约定、超时、埋点、合法域名提示）都要手工同步 6 份，**极易漏改**——这已不是理论风险：card-shop 的 auth.js 落后为 ES5 回调风格、brand 独享自动重登，说明分叉已经发生。

### 8.4 设计思路：公共化底座 + 领域化能力（推荐方向）

关键判断：**不要激进合并数据表**。各域表族独立是合理的产品决策（不同私域店主的数据本质隔离，合并反而引入跨租户风险）。应该分两层收敛：

```
┌─── 第 1 层：公共技术底座（跨端共享，抽 npm 包）────────────────────────┐
│  @mini/core（新建 workspace 包，6 端依赖）：                          │
│   • requestCore(options)：统一 baseUrl/toQuery/信封解包/401 策略/超时   │
│   • sessionCore(storageKey)：token 读写/清除/双令牌(顾客+技师)          │
│   • loginFlow.loginWithCode(code,租户码,apiAdapter)：wx.login 状态机     │
│   • errorMap + 合法域名提示文案                                        │
│  各小程序只保留极薄的 config.js(差异项) + api.js(业务端点)               │
└──────────────────────────────────────────────────────────────────────┘
                              ▼ 依赖
┌─── 第 2 层：领域能力（后端收敛，保留分表）────────────────────────────┐
│  • 统一令牌模块 token-factory.ts：                                    │
│      issueToken({issuer,scene,tenantId,subjectId,openId,ttl})          │
│      verifyToken(token, expectedIssuer)  // 密钥派生算法唯一口径         │
│    5 套 *-token.ts 退化为传参调用；杜绝两套派生范式                     │
│  • CustomerIdentity 领域服务：upsert(siteId|shopId, openid, unionId)    │
│    统一"按租户+openid 定位顾客"的仓储接口，各域表实现该接口             │
│  • Order 领域骨架：统一的订单状态机/幂等键/超时回收/支付回调校验模板     │
│    (参考 common/schedule.ts 的成功模式)，各域只写差异化业务             │
│  • 强制边界：把"按 tenantId + subjectId 过滤"收进仓储层基类/查询构造器    │
│    而非散落 service；用测试 + 架构守护脚本审计所有顾客态查询             │
└──────────────────────────────────────────────────────────────────────┘
```

**为什么这样分**：第 1 层解决"一致性/扩展性"（一处修复 6 端生效），不动数据；第 2 层解决"边界/复用"（隔离从约定升级为框架强制），不动表归属。两层都不要求数据迁移，风险可控、可增量落地。

## 十、架构优化建议（按优先级）

### P0 — 高优先级（数据安全与一致性，建议本迭代启动）

**P0-1　统一令牌签发/验签，消除两套派生范式**
- 问题：R5、R2 的根源。`customer-token.ts` 与 `dh/kp token` 各搞一套。
- 影响：误配即越权或全站令牌失效；共 issuer 边界无法审计。
- 方向：新建 `auth/mini-token-factory.ts`，统一 `issueToken({issuer,scene,tenantId,subjectId,...})` / `verifyToken(token,expectedIssuer)`，密钥派生单一算法；5 套 `*-token.ts` 退化为配置化调用。**保留各自 issuer 与分表，不改数据**。
- 验收：所有令牌模块 no duplicate HMAC 逻辑；单测覆盖"顾客令牌进不了 /enterprise/**""技师/顾客令牌互斥"。

**P0-2　把租户过滤下沉到仓储层，补齐越权自动化审计**
- 问题：R2。隔离靠 service 手写 WHERE。
- 影响：一次漏写 = 跨店数据泄露。
- 方向：为顾客态表提供统一查询构造基类（强制注入 `tenantId+subjectId` 条件）；扩展 `check-architecture.mjs`，扫描所有 `*.public.ts`/顾客态 service，断言查询包含租户条件；把 onsite 已有的"令牌互斥"测试推广到 brand/card-shop/dh/kp。
- 验收：架构守护脚本纳入 CI（`pnpm check:architecture`），越权用例全绿。

**P0-3　收敛 6 份 request/auth/session 为 `@mini/core`**
- 问题：R1、R3 的根源，分叉已发生。
- 影响：一处安全修复要改 6 份，且已不一致。
- 方向：按 8.4 第 1 层抽包，先跨 6 端统一 `requestCore`（含 401 策略、信封解包、合法域名提示），再统一 `sessionCore`。差异项（API_PREFIX、租户码键名、是否自动重登）作为参数注入。
- 验收：6 端 request.js 从 ~90 行降到 <20 行薄封装；401 策略单一实现。

### P1 — 中优先级（可维护性与工程质量，建议下一迭代）

**P1-1　统一 Web 侧 API 调用风格**：69 处手写 `http()` 收敛为契约 `endpoint()` 或显式标注例外的白名单；`check-architecture.mjs` 已有规则可扩展为强制。

**P1-2　收敛 `services.ts` 手工装配**：按域拆分为 `createXxxServices()` 工厂，`createServices()` 只做聚合；降低 3682 行单文件的合并冲突与认知负担。

**P1-3　统一 AES-GCM 凭据加解密**：6+ 份 `*-crypto.ts` 收敛为 `common/credential-crypto.ts`，以 context 字符串区分用途（与令牌 factory 思路一致）。

**P1-4　补齐关键路径测试**：优先覆盖登录/令牌/下单支付/退款状态机/租户过滤；前端至少给 API 层与 Session 层补测试（当前近乎空白）。

**P1-5　路由双轨归一**：中期将命令式 `route-groups` 逐步迁入契约端点，统一 handler 派生口径；短期至少在 `route-baseline.json` 基础上扩大守护覆盖。

### P2 — 低优先级（体验与技术债，排期灵活）

**P2-1　前端 SSR/首屏优化**：官网首页 `/` 与营销落地页改为服务端取数 + 静态化，缓解纯 CSR 首屏与 SEO；评估在保留 Antd 的前提下引入 RSC 数据预取。

**P2-2　i18n 深层覆盖**：建立文案抽取流水线，把深层页面硬编码中文纳入 `messages.ts`。

**P2-3　构建瘦身**：解决 10GB 堆依赖的根因（大文件如 `api/social.ts` 583 行、`query/onsite.ts` 713 行、契约 endpoints 1.5 万行），按域拆包。

**P2-4　清理历史产物**：`workbuddy-host-client`（无源码 asar、通道已下线）、`update/sources/3/...1.4.0/` 历史快照明确标注归档或移除，降低新人认知负担。

## 十一、开发指引

### 11.1 新增一个微信小程序的标准动作（避免再复制 6 份）

1. **优先评估能否复用现有终端**：若是"某私域店主 C 端下单"场景，优先在 brand/card-shop 现有小程序内加场景，而非新建工程。
2. 确需新建时，**必须基于 `@mini/core`**（P0-3 完成后）：只写 `config.js`（差异项）+ `api.js`（业务端点）+ 页面；`request/session/auth/login` 从公共包引入，禁止再复制。
3. 后端：**不要新建 `*Member`/`*Order` 表族和 issuer**——先确认能否复用 `CustomerIdentity`/`Order` 领域骨架（8.4 第 2 层）；确需新 issuer 时通过 `mini-token-factory` 传参签发，不复制 token 模块。
4. 在 `app.ts` 注册 `registerXxxPublic` 时，注释中写明：令牌 issuer、租户过滤键、是否进功能开关。
5. 在 `services.ts` 按域聚合，勿在 3682 行主函数内平铺。
6. 把新域的越权用例、路由纳入 `pnpm check:architecture` 与回归脚本。

### 11.2 修改公共能力时的检查清单

- 改了 401/错误码/超时约定？→ 确认 `@mini/core` 单点修改，6 端自动生效（P0-3 后）；若尚未抽包，**逐一核对 6 份 request.js**。
- 改了令牌 payload/issuer/TTL？→ 同步更新验签方、前端 storage KEY、租户过滤逻辑、测试用例；确认新旧令牌过渡策略。
- 新增 `fetch(` 调用？→ 必须落在 `frontend/src/api/http.ts` 或 `backend/src/http/transport.ts`，否则 `check-architecture.mjs` 会拦截。
- 新增顾客态查询？→ 必须带 `tenantId + subjectId` 双条件，并补越权测试。
- 新增契约端点？→ 写进 `packages/contracts/src/endpoints.ts`，保持"类型由 Schema 推导、禁类型断言、只 import zod/相对路径"。

### 11.3 必跑的本地校验命令（来自根 `package.json`）

```bash
pnpm install && pnpm setup            # 选 MySQL/PG、生成 Prisma Client、迁移
pnpm dev                              # 起 contracts build + api + web + worker + nginx
pnpm build                            # contracts → api → web 顺序构建
pnpm check:architecture               # 架构边界 + 扩展能力 + 洞察技能守护  ★改动后必跑
pnpm typecheck && pnpm lint
pnpm e2e                              # 全 API 流程断言（需隔离库）
pnpm test:isolation / test:regression # 隔离迁移/回归
pnpm pack:miniprogram                 # 打包用户版小程序源码包（注入 apiBase）
```

### 11.4 三条不可逾越的红线（从现有代码约定提炼）

1. **令牌物理隔离**：C 端（顾客/会员/技师）令牌绝不进入 `/enterprise/**`；站内令牌不做 C 端用途。派生密钥按 issuer 隔离。
2. **顾客态双条件过滤**：任何 C 端读写必须 `siteId|shopId + customerId/memberId/staffId` 双条件；查单类接口另设独立限流防枚举。
3. **网络出口唯一**：所有出站 HTTP/SSE 经 `transport.ts`；前端所有请求经 `api/http.ts` + `endpoint.ts`，由架构脚本强制。
