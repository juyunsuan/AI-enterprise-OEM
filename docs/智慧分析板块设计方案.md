# 智慧分析板块设计方案（全域内容热点分析 + 流行趋势分析）

> 状态：**设计待拍板**（§十 决策点未确认前不动代码）。
> 来源：本文重写自外部《智慧分析板块完整方案 v2.0》，原方案按"从零新建采集服务/资产中台/多维表格"设计，与本系统实际底座不符；本版把全部能力落回本系统已有设施，重排为**全域内容热点分析（第一）+ 流行趋势分析（第二）**两个工具。

## 一、一句话定位

在工作台下新增「智慧分析」三级菜单组，下设两个可独立开关的工具：

1. **全域内容热点分析**（`/insight/hotspot`）：订阅自己的垂类（关键词/话题/博主）→ 用**浏览器代理定时采集 + 大数据查询 + 手动导入**三条已有通道把内容收进**预置多维表格**→ 热点引擎聚合打分分层（萌芽/上升/峰值/衰退）→ 看板 / 榜单 / 快报 / 台账 / Agent 问数。
2. **流行趋势分析**（`/insight/trends`）：对**自己的数字资产图片 + 电商采集结果**做 VLM 打标、色彩/元素时序统计、价格带与爆款打分，回答"我的素材池和行业卖盘中，什么元素在升温"。

不新建爬虫集群、不新建向量库、不新建表格引擎、不自建 AI 计量——采集、落表、资产、AI、BI、Agent、开关全部复用底座既有实现。

## 二、原方案与本系统的差距对照（重写依据）

| 原方案设定 | 问题 | 本版落地方式 |
|---|---|---|
| L3 BotBuddy 独立采集服务（代理池/UA 轮换/分片集群） | 本系统 BotBuddy = Agent-Bot 主机/MoBot/WorkBuddy 执行通道（`/agent-bot`）+ 浏览器代理插件 + RPA 指纹浏览器；无独立爬虫服务，也不该起一个 | 采集 = 浏览器代理「采集配方 + 计划任务 + harvest→landRows」闭环（已实现）+ 大数据查询连接器（`backend/src/bigdata`）+ 采集台账二次投递 + 手动导入 |
| L4 数据资产中台（Milvus/流水线/时序库） | 本系统数字资产管理（`/assets`）已有台账（labels/caption/embedding，`digital_asset_entries`）、VLM 理解（`content/vision.service.ts`）、cosine 检索（`ai/retrieval-kernel`）；单体 Node + Prisma 双库，无消息队列 | 资产仍归 `/assets`；聚合计算用关系表 + scheduler（仿 `geo/geo-collection.scheduler.ts`），不上独立中间件 |
| L5 多维表格"模块"（自动化工作流/Webhook） | 现有 `data-table` 是八种列类型 + 行 + 视图 + 授权 + 机器通道，无跨表自动化引擎 | 台账=预置多维表格（列模板单一来源，仿 `BIGDATA_DATASETS` 口径）；"表格→采集任务"的自动化由 insight 模块后端调度器承担，不承诺表格原生 webhook |
| 全链路 `tenant_id` | 本系统资源按 `ownerUserId` 账号归属 + 身份/企业关联（identity/audit 体系） | 所有新表用 `ownerUserId`，与 bigdata/bi/data-table 同口径 |
| 抓秀场/电商/社媒全渠道，对标 POP + 知衣全矩阵 | 平台反爬与条款风险高；本系统采集发生**在用户自己登录态的本机浏览器**里，无代理池 | 数据源限定：订阅范围公开页（用户设备执行、人工确认、全留痕）+ 官方开放平台 API（后续批次）+ 大数据上游 + 用户上传；界面如实标注来源与风险 |
| 自建 Agent 编排 API `/api/agent/chat` | 本系统已有 `/agent` 工作台 + MCP 工具面 + 统一 AI 网关计量 | 热点问数走既有 Agent，注册 `Insight_*` 只读/生成类工具；AI 全部走 `ai/ai-gateway`，新增 BillingRule 科目 |
| OEM 开关另行设计 | 已有功能目录：`backend/src/feature/feature-catalog.data.ts` 种子树 + API 前缀拦截 + 平台后台显隐 | 新增 group/menu code + `/enterprise/insight` 前缀，走既有机制 |

**保留不变的产品内核**（原方案正确且有价值的部分）：订阅制采集（范围=订阅+人工导入）、热点四阶段分层与增速视角、互动/商业/视觉三热度分开展示、概念商业化潜力四象限、多维表格做自定义台账、AI 快报与问答、合规红线（公开内容、不存视频原文件、审计留痕）。

## 四、全域内容热点分析（第一位）

### 4.1 数据流总览

```
垂类订阅策略（关键词/话题/博主 × 平台 × 频率）
   │ ①派发生成采集配方+计划任务            ②大数据连接器          ③手动导入/台账投递
   ▼                                        ▼                      ▼
托管采集窗口定时会话（BotBuddy 主机指纹窗口内加载浏览器代理插件；备用：本机 Chrome 插件）
   harvest→landRows，按幂等锚去重 ───▶ 预置多维表格「热点内容」
                                                                 + 数字资产（封面/素材，可选）
   │
   ▼  insight scheduler（小时/日聚合，仿 geo-collection.scheduler）
读「热点内容」表行 → 关键词/话题分组归并 → 归一互动分+增速 → 阶段判定
   │
   ├─ insight_hotspots（热点事件）+ insight_hotspot_contents（聚类成员）
   ├─ insight_metrics（热点/关键词时序，双库兼容）
   ▼
热点大盘/榜单/详情页（ECharts） + 热点台账（预置多维表格） + AI 快报（产物入数字资产）
   + BI 内置数据集（Insight 热点/内容两张策展数据集） + Agent 工具（Insight_*）
```

要点：**行数据全程走既有 `DataTable_landRows`**（≤500 行/幂等锚/`_source` 来源列/审计），insight 模块不自建内容存储；热点=聚合产物而非采集产物，删了可重算。

### 4.2 垂类订阅管理（页签二）

一条订阅 = `insight_subscriptions` 一行 + 派生物：

| 配置项 | 落地 |
|---|---|
| 名称 / 平台（小红书/抖音/视频号/头条，闭集可扩展） | 表字段；平台枚举进 contracts |
| 关键词 / 话题标签 / 博主主页，可组合 | JSON 数组列 |
| 采集频率 | 映射为计划任务 cron（复用 `RpaChrome_saveSchedule` 同款的账号级计划任务机制，insight 侧存 scheduleId 引用） |
| 过滤规则（排除词/最低互动/内容形式） | 存表，聚合与快报生成时生效 |
| 告警阈值（增速>N% 提醒） | MVP 先做「进入上升阶段在页面标记 + 通知中心推送」，不外发 |
| 单次采集上限 / 每日上限 | 透传 harvest `limit` 与计划任务配额；超限如实回报 |

订阅的采集派生实现为**预置采集配方**：每平台一份 goal 模板（打开搜索页/话题页/博主页 → `harvest mode:discover` 或站点技能配方 → landRows 进「热点内容」表，幂等锚 = 内容链接列），配方文案与列映射放 contracts `INSIGHT_HARVEST_RECIPES`（单一实现点，仿 `BIGDATA_DATASETS` 前后端共用）。订阅保存时创建/更新对应计划任务；订阅停用即暂停任务。

**设备择优（主备两档，派发时按序取用）**：

| 优先级 | 通道 | 前提 | 失败降级 |
|---|---|---|---|
| 1 托管 | BotBuddy 主机指纹窗口内的浏览器代理插件 | ① 主机已配对在线（`/agent-bot`）；② 插件包已装进主机 `~/.botbuddy/chrome-extensions/` 并在指纹窗口按勾选加载；③ 专用「洞察采集」指纹档案内已人工登录目标平台（user-data-dir 持久化登录态） | 主机离线/档案登录态失效 → 降档 2，并在健康度如实标注原因 |
| 2 备用 | 用户本机 Chrome 的浏览器代理插件（现有绿灯设备） | 插件登录本站 | 均无在线设备 → 本轮不执行，记 `NO_DEVICE`，给两条通道的连接入口 |

实现口径：插件设备注册链路补**来源标记**（`managed`/`local` + hostId，contracts 与后端设备表加字段），insight 计划任务派发在现有绿灯闸基础上按来源择优（今天绿灯派发是"任一在线设备"，需加一层优先级选择）；托管窗口遇登录墙沿用 `NEED_LOGIN` 语义如实回报、订阅标记待人工处理，不硬猜不静默。

健康度展示：每订阅显示**执行通道类型**（托管/本机）、最近任务执行时间、成功条数、设备在线状态；托管通道额外显示目标站点登录态检查结果。异常时给「立即手动采集」（预填 goal 深链）、「打开 BotBuddy 主机/指纹档案」与「去连接本机插件」入口（阻断必给出路）。

### 4.3 热点引擎（后端 `backend/src/insight/`）

- **聚合调度**：`insight.scheduler.ts`，按订阅频率把「热点内容」表新增行滚动归并。
- **聚类口径（MVP）**：按话题标签 ∪ 归一化关键词分组（分词用 LLM 批量抽取，入库时一次、幂等），**不做向量聚类**；`similarity` 字段留空位。向量聚类作为决策点 D2，需要时复用 `retrieval-kernel` cosine。
- **打分**（口径继承原方案，权重与阈值 contracts 声明、后台可配）：

```
hot_score = 归一互动分×w1 + 增速分×w2 + 跨平台扩散分×w3 + 内容数分×w4
stage: 萌芽(基数<P30 且增速>+80%) / 上升(+20%~+80%) / 峰值(>P90 且趋平) / 衰退(<-20%)
```

分位数按本账号近 90 天数据标定，避免一刀切。
- **AI 加工**（全走 `ai-gateway`，带 `charge.code` 才扣分）：热点命名与摘要、关联词抽取、情感倾向标注、爆款拆解（标题套路/内容结构/封面要素——封面已在数字资产的走 `AssetVisionService`，未入库的先只做文本拆解）。批量任务仿 `content-job.worker-pool` 的批处理节奏，单次调用上限受配额科目约束。
- **双库兼容**：时序与聚合 SQL 只用 `common/sql-json` 既有工具与通用语法，禁方言函数（见记忆「MySQL/PostgreSQL 双库兼容清单」）。

### 4.4 页面（`frontend/src/app/insight/hotspot/`）

| 热点榜单 | TOP 列表：名称/所属订阅/覆盖平台/得分/增速/内容数/情感/阶段标记；行点开=热点详情（成员内容、观点分化占比、关联词云、首发平台时间线、跳转内容原链与表格行）；聚类纠偏入口：拆分/合并/标记非热点（纠偏记录回灌阈值提示，不改原始行） |

## 五、流行趋势分析（第二位）

定位收窄为**"自有资产 + 自有采集"的趋势量化**，不做 POP 式秀场情报库（数据源拿不到，也不该拿）；界面明示与热点工具共用数据底座。

### 5.1 数据面

- **图片池** = 数字资产管理（`/assets`）现有台账：按标签/时间筛选，批量「AI 打标」→ `AssetVisionService` 出品类/风格/主色辅色（色彩 hex 由 VLM 输出约束 + 前端校正）→ 回写 labels（AI 候选并入人工标签，沿用 `mergeLabels` 不覆盖语义）；embedding 检索照常「以图搜相似」。
- **商品池** = 预置采集配方「电商搜索列表 → landRows 进『电商选品观测』表」（价格/销量展示值/评价数/上新时间/链接，字段取**页面公开可见值**并在界面标注"仅供业务参考"）+ 手动导入。
- **商业观测**（可选升级）= 用户自有店铺数据经 BI 外部数据源接入，趋势模块只读 BI 数据集不直连。

### 5.2 页签

| 页签 | 内容 |
|---|---|
| 元素趋势 | 标签×周/月时序曲线（`insight_metrics` metric_type=visual）、生命周期分层（同 4.3 算子）、增速榜；品类×标签交叉透视（复用 BI 透视组件或直接表格） |
| 色彩趋势 | 主色占比时间分布、色卡墙（按 hex 聚合资产缩略）、色彩增速 Top；点击色卡=筛出该色资产集并可跳 `/assets` |
| 商业选品 | 价格带分布、上新增速、爆款打分（多因子：上新/收藏/评论增速，权重可配）、萌芽款/成熟款/衰退款列表；竞对关注=「电商选品观测」表按店铺列筛选 + 站点技能配方定时重跑 |

## 九、合规与风险（继承原方案、按本系统实现口径收窄）

1. 采集只发生在**租户用户自己本机的浏览器**——主通道是 BotBuddy 主机托管的指纹窗口、备用是本机 Chrome 插件，两条都是用户自有设备与自有账号，客户端始终在用户机器上；只采订阅范围公开页、只存标题/文案/公开互动数/封面，不存视频原文件、不抓登录后可见的私有内容与私信；步骤与截图留痕是审计底座关不掉（同采集落表方案 §H 口径）。托管档案用独立「洞察采集」指纹，与用户日常浏览档案隔离。
2. 平台条款风险如实标注：订阅页与榜单页脚注「来源为用户设备公开页面采集，数据仅供内部选题参考」；不对外宣称平台全量数据。
3. 官方开放平台 API（抖音/小红书热榜接口等）为后续批次的第二通道，资质到位前不承诺。
4. 电商销量取页面公开展示值，界面标注"仅供业务参考，不作为精准经营依据"。
5. 个人信息（博主联系方式）不入预置表列；批量抓联系方式维持「人工确认」红线（采集落表方案 N9=A 已定）。
6. 审计：订阅变更、采集任务启停、快报导出全部 `identity.audit`；AI 用量全走网关计量。
7. 性能：聚合调度增量游标（沿用 landRows `_source` 时间与行 id 游标），单次窗口上限 + 分批，防止大表全扫；`insight_metrics` 行数 = 键数×周期数，可控。
