> 状态：**设计待拍板 v2.1（采集先行重排）**。§十三 决策点未确认前不动代码。

## 一、一句话定位

在工作台下新增「智慧分析」三级菜单组，下设两个可独立开关的工具，两个工具**共用同一条「先采集、后分析」流水线**：

1. **全域内容热点分析**（`/insight/hotspot`）：声明**采集目的**（抓公开内容的互动热度）与**数据源对象**（平台搜索页/话题页/博主主页）→ 采集 SKILL 包定时收割 → 落「热点内容」表（关联数据源/批次）→ 分析引擎聚合打分分层 → 看板 / 榜单 / 快报 / 台账 / Agent 问数。
2. **流行趋势分析**（`/insight/trends`）：声明**采集目的**（看元素/色彩/价格在升温）与**数据源对象**（先设定电商站点对象：搜索列表页/店铺列表页；自有数字资产直读不采集）→ 采集 SKILL 包定时收割 → 落「电商选品观测」表 → VLM 打标与色彩/元素时序统计、价格带与爆款打分。

不新建爬虫集群、不新建向量库、不新建表格引擎、不自建 AI 计量——采集执行位、技能包分发、定时调度、落表、资产、AI、BI、Agent、开关全部复用底座既有实现。

## 二、采集先行的四条硬规则

1. **无目的不采集**：每条订阅/数据源必须写明「服务于哪个分析目的」（热点互动 / 趋势-元素 / 趋势-色彩 / 趋势-选品），未声明目的的数据源不允许启用定时。
2. **无数据源对象不采集**：采集的落点是**站点对象**（平台 + 页面对象 + 关键词或 URL 模板），不是笼统的"抓某平台"；对象先配置、后采集（见 §四 矩阵）。
3. **采集内容必须可关联**：每条内容行带**数据源 id + 采集批次 id + 采集通道 + 采集时间**，从内容行能回溯到批次 → 数据源 → 订阅 → SKILL 包版本 → 执行设备（见 §六）。
4. **采集与分析解耦**：采集是独立可重跑的阶段，分析只**读**采集结果；采集停摆或换通道，分析输入端不变；删了分析产物（热点/趋势）可由采集结果重算。
5. **采集能力即 SKILL 包**：采集步骤封装成技能包，可被 **BotBuddy 客户端 Agent（主）/ WorkBuddy 企业版 / Codex / 本机浏览器代理（备用）**执行，由平台的**定时任务**到点下发（见 §五）。

## 三、原方案与本系统的差距对照（重写依据）

| 原方案设定 | 问题 | 本版落地方式 |
|---|---|---|
| L3 BotBuddy 独立采集服务（代理池/UA 轮换/分片集群） | 本系统 BotBuddy = Agent-Bot 主机/客户端内置 Agent + 浏览器代理插件 + RPA 指纹浏览器；无独立爬虫服务，也不该起一个 | 采集 = **采集 SKILL 包**在**用户自有执行位**跑：`harvest → DataTable_landRows`（已实现），由 `WorkbuddyHostSchedule` 定时下发到 BotBuddy 主机（主）、本机 Chrome 浏览器代理 `RpaChromeSchedule`（备用） |

**保留不变的产品内核**（原方案正确且有价值的部分）：订阅制采集（范围=订阅 + 人工导入）、热点四阶段分层与增速视角、互动/商业/视觉三热度分开展示、概念商业化潜力四象限、多维表格做自定义台账、AI 快报与问答、合规红线（公开内容、不存视频原文件、审计留痕）。

## 四、采集目的 ↔ 数据源对象 ↔ 落表 对应矩阵

> 这张表是「先设定采集对象再采集」的落地口径：**建数据源时就要在这一行里选好目的、站点对象、目标表与 SKILL 包**，不许出现"先采了再说"的采集任务。

| 分析目的 | 需要的数据 | 数据源对象（配置项） | 落表（预置多维表格） | 采集 SKILL 包 |
|---|---|---|---|---|
| 热点 · 内容互动热度 | 公开内容的标题/正文摘要/互动数/作者/话题/发布时间 | 平台（小红书/头条/抖音/视频号）× 页面对象（**关键词搜索页** / **话题页** / **博主主页**）× 关键词或账号 | 热点内容 | `insight-collect-hotspot` |
| 趋势 · 元素 | 商品/图片的品类、风格、元素标签 | 电商平台 × 页面对象（**关键词搜索列表页** / **店铺列表页** / **类目榜页**） | 电商选品观测 | `insight-collect-trend` |
| 趋势 · 色彩 | 商品图片主色/辅色 | 同「趋势 · 元素」图片源 | 电商选品观测（图 → VLM 出 hex） | `insight-collect-trend` |
| 趋势 · 商业选品 | 价格、销量展示值、评价数、上新时间 | 同「趋势 · 元素」 | 电商选品观测 | `insight-collect-trend` |
| 趋势 · 自有素材 | 自有图片资产 | **不采集**：直读 `/assets` 数字资产台账 | 数字资产（既有） | —— |

要点：
- **页面对象是显式枚举**（搜索页 / 话题页 / 博主主页 / 列表页 / 店铺页），不是自由文本；每种对象在 SKILL 包里有对应的打开路径与字段抽取规则（D9 见 §十三）。
- **同一平台的不同页面对象可组合**成一条数据源（如"小红书：`护肤`搜索页 + `#早C晚A`话题页"）。
- 数据源对象由用户新建时填（配一次复用），也可由"从当前页一键建数据源"（在 BotBuddy 主机指纹窗口或本机浏览器里对着目标页点一下，抓当前 URL 模板）辅助生成，减少手填。

### 4.1 网站源头支持配置（三种配置方式，2026-11-17 用户口径）

采集源头**不只平台闭集**，用户可以自配网站：

| 配置方式 | 配置项 | 采集包 | 适用 |
|---|---|---|---|
| A 平台闭集 | 平台（小红书/头条/抖音/视频号…）+ 页面对象 + 关键词/账号 | `insight-collect-hotspot` | 已知平台，打开路径与字段由包内置，命中率高 |
| B 电商闭集 | 电商平台 + 页面对象（搜索列表页/店铺列表页/类目榜页）+ 关键词/店铺 | `insight-collect-trend` | 选品观测 |
| **C 自定义网站源头** | **网站（域名/URL）+ 页面对象 + URL 模板（含 `{keyword}` 占位符）** | `insight-collect-site`（泛化包） | 用户自有站点、行业垂直站、客户站点、资讯列表页等 |

- **URL 模板是自定义源头的核心**：如 `https://www.example.com/search?q={keyword}`、`https://blog.example.com/list/{page}`；保存时校验协议为 http/https、替换占位符后非空、不含 `..`/盘符，校验不过不给保存（阻断必给出路）。
- **泛化包的降级口径**：陌生站点没有内置选择器，采集走「**站点技能（site skill）优先 → 结构识别 → 失败如实回报**」三步；识别不出列表时**不硬猜**，回报"该页面结构未知，请补站点技能或换页面对象"，页面给「从当前页一键建数据源 / 补站点技能」入口。
- 网站源头**逐条显式配置并留痕**，不做全网扫描与默认抓取；仍只采用户自有登录态下可访问的公开页，不采登录后私有内容与私信。
- 源头数量按账号封顶（后台可配，默认 200 条），防配置失控；源头改域名/模板后**不改历史采集行**（按批次隔离，重跑只新增）。

### 4.2 模式同源、配置分治（2026-11-17 用户口径）

用户口径：**「流行趋势分析的采集和全域内容热点分析用同一个模式和相似方法，但配置要相互分开，因为采集目的不一样」**。落到实现上是一句话：**执行链路共用一份，配置面按采集目的（scope）切成两套**。

| 层 | 共用（同一实现） | 分开（两份配置） |
|---|---|---|
| 目的归属 | 契约 `INSIGHT_PURPOSE_SCOPES`（`hotspot→hotspot`，`trend-*→trend`）+ `insightPurposesInScope` / `insightKindsInScope` 单一来源 | 每个采集配置页只列本页闭集：热点页只有「内容互动热度」，趋势页只有「趋势·元素 / 色彩 / 商业选品」 |
| 数据源类型 | 同一张 `insight_collection_sources` 表、同一套校验与采集包派生规则 | 社媒三类（平台搜索/话题/博主）只归热点，电商两类（电商搜索列表/店铺）只归趋势，`customSite` 两侧都可配（同一泛化包） |
| 端点族 | `InsightService` 一套方法（`listSources/saveSource/removeSource/listRuns/listSubscriptions/saveSubscription/toggleSubscription/removeSubscription/collectNow`）多接一个 `scope` 参数 | 热点走 `/enterprise/insight/sources｜runs｜subscriptions`，趋势走 `/enterprise/insight/trends/sources｜runs｜subscriptions`；控制器只是两个薄入口，跨侧读写被当成不存在（404）或目的越界（400 且说明属于哪个工具） |
| 采集派发 | `syncSchedule` / `createCollectionTask` / `collectionGoal` 一套：一源一任务、主通道 BotBuddy 主机、备通道浏览器代理、批次留痕、幂等锚 | 任务的 title 与目标串各自带本侧数据源名，趋势侧不会拿到热点侧源头 |
| 健康度 | `collectionHealth(user, scope)` 一个实现 | `insight/hotspot/overview` 数 hotspot 那组，`insight/trends/overview` 数 trend 那组，两侧的「采集批次」页签各看各的 |
| 前端组件 | `frontend/src/app/insight/_components/collection-tabs.tsx`：`CollectionSourcesTab / CollectionSchedulesTab / CollectionRunsTab / SkillPackPanel` 全部只认 `scope` | 热点页 `scope="hotspot"`（页签名沿用「垂类订阅」），趋势页 `scope="trend"`（页签名「采集排班」）；`insightCollectionApi(scope)` 返回模块级常量端点包，组件不写死端点名 |
| 采集包下载 | 同一份契约清单 `GET /enterprise/insight/skills`、同一批静态 zip | 面板按本页可用包过滤：热点页显示 hotspot+site，趋势页显示 trend+site；前缀挂板块码 `insight`（关掉任一子工具都不该藏掉另一个的下载入口） |
| 开关 | 板块组 `insight` 持有 `/enterprise/insight/skills` | 热点侧前缀归 `insight-hotspot`；趋势侧前缀已被 `insight-trends` 的 `/enterprise/insight/trends` 覆盖，两侧采集配置随各自工具开关 |

## 五、采集 SKILL 包（本版核心新增）

### 5.1 形态（沿用站内既有技能包口径）

- 包内容 = `SKILL.md`（frontmatter `name`/`description` + 正文步骤）+ 可选资源（`field-mapping.json`、站点选择器/站点技能规则）。**平台只把包当资料与指令，不执行包内任何脚本**（同 `content/agent-skills.service.ts` 既有红线）。
- 执行方（BotBuddy 客户端内置 Agent / WorkBuddy / Codex / 浏览器代理）用 `load_skill` 读取包，按正文步骤调用**采集原语**：`open_tab/navigate → harvest（收割条目×字段）→ DataTable_landRows（幂等落表）`，并回报行数与失败原因。
- 分发复用 SkillHub：`GET /enterprise/skillhub/skills/:slug`、`/download` 取 zip；BotBuddy 客户端在本机解包入本机技能库（`docs/Agent-Bot方案.md` §Bot 主机技能中心同款链路）。
- 首批随系统 seed 注册三个包（slug 固定，版本号随包升）：`insight-collect-hotspot`、`insight-collect-trend`、`insight-collect-site`（自定义网站源头的泛化包，§4.1）。

### 5.2 包内声明（参数化）

`SKILL.md` 正文含参数占位，由订阅/数据源派发的指令替换：

| 参数 | 含义 | 来源 |
|---|---|---|
| `{source}` | 数据源对象（平台 + 页面对象 + 关键词/URL 模板） | 数据源表 |
| `{keyword}` | 关键词（搜索页对象用） | 数据源表 |
| `{limit}` | 单次收割上限 | 订阅/数据源配额 |
| `{tableId}` | 目标预置表（热点内容 / 电商选品观测） | 设置表 |
| `{dedupBy}` | 幂等锚列 | 契约 `insightDedupKeys` |
| `{fieldMapping}` | 抽取字段 → 列键映射 | `field-mapping.json` |

契约单一来源：`INSIGHT_COLLECTION_SKILLS`（包 key → slug / 版本 / 参数 / 字段映射 / 落表 / 幂等锚），前后端与打包脚本共用，仿 `BIGDATA_DATASETS` 的口径——**采集包从 contracts 生成，不在业务代码里手抄**。（原按平台写死的 goal 模板 `INSIGHT_HARVEST_RECIPES` 已被采集包取代，2026-11-17 从契约删除。）

### 5.3 执行者与调度（定时执行 SKILL）

| 优先级 | 执行者 | 调度机制（既有） | 前提 | 失败降级 |
|---|---|---|---|---|
| 1 托管（主） | BotBuddy 客户端内置 Agent（`/bot/hosts`，指纹窗口内加载浏览器代理） | `WorkbuddyHostSchedule`（`once/scheduled/recurring`，时区 Asia/Shanghai，**错过不补跑**）到点向配对主机下发"按 SKILL `insight-collect-*` 采集 `{source}`"指令；`WorkbuddyHostScheduleRun` 逐轮留记录 | ① 主机已配对在线；② 主机技能库已装采集包；③ 专用「洞察采集」指纹档案内已人工登录目标平台 | 主机离线/登录态失效 → 降档 2，健康度如实标注 `NEED_LOGIN` |
| 2 备用 | 用户本机 Chrome 的浏览器代理插件 | `RpaChromeSchedule`（同款周期计划任务） | 插件登录本站 | 均无在线设备 → 本轮不执行，记 `NO_DEVICE`，给两条通道连接入口 |
| 3 可选 | WorkBuddy 企业版（`/workbuddy`）/ Codex | 平台下发同一指令口径，由各自运行时的定时能力承载 | 用户已接入对应运行时 | 不可用时降回 1/2 |

实现口径：
- 采集指令**自包含**（主语=SKILL 包 + 数据源对象 + 参数 + 目标表 + 幂等锚），不听历史、可重跑；订阅保存 → 建/更新对应 `WorkbuddyHostSchedule`（或 `RpaChromeSchedule`），停用即暂停，删除即清理（`subscription.scheduleIds` 引用）。
- 设备择优：浏览器代理设备注册链路补**来源标记**（`managed`/`local` + hostId），派发在现有"任一在线设备"闸上按来源择优。
- 落地原语只有一条：`harvest → DataTable_landRows`（≤500 行/幂等锚/`_source` 来源列/审计），托管与备用通道**同一实现**，差别只在"插件跑在哪个浏览器里"。
- AI 用量（若包步骤用了模型抽取）：全走 `ai-gateway`，带 `charge.code` 才扣分。

### 5.4 幂等、留痕、可重跑

- **幂等**：`landRows` 按幂等锚（内容表 `url`、选品表 `url`）去重，重复执行安全。
- **留痕**：每行带 `_source`（来源）+ `collected_at` + `run_id` + `channel`；采集批次表记录轮次；订阅变更、任务启停、快报导出全进 `identity.audit`。
- **可重跑**：批次失败/漏采可"立即补跑一轮"（`WorkbuddyHostSchedule` 的 `run` 入口），重跑不产生重复行。

## 七、分析层（第二段，只读采集结果）

分析不自建采集，入口全部改为"读采集结果"。

### 7.1 热点引擎（后端 `backend/src/insight/`）

- **聚合调度**：`insight.scheduler.ts`，按订阅频率把「热点内容」表新增行滚动归并（增量游标 = 行 id + `collected_at`）。
- **聚类口径（MVP）**：按话题标签 ∪ 归一化关键词分组（分词用 LLM 批量抽取，入库时一次、幂等），**不做向量聚类**；`similarity` 留空位。向量聚类作为决策点 D2，需要时复用 `retrieval-kernel` cosine。
- **打分**（口径继承原方案，权重与阈值 contracts 声明、后台可配）：

```
hot_score = 归一互动分×w1 + 增速分×w2 + 跨平台扩散分×w3 + 内容数分×w4
stage: 萌芽(基数<P30 且增速>+80%) / 上升(+20%~+80%) / 峰值(>P90 且趋平) / 衰退(<-20%)
```

分位数按本账号近 90 天数据标定，避免一刀切。
- **AI 加工**（全走 `ai-gateway`，带 `charge.code` 才扣分）：热点命名与摘要、关联词抽取、情感倾向标注、爆款拆解；批量节奏仿 `content-job.worker-pool`，单次上限受配额科目约束。
- **双库兼容**：SQL 只用 `common/sql-json` 既有工具与通用语法，禁方言函数（见记忆「MySQL/PostgreSQL 双库兼容清单」）。

### 7.2 热点页面（`frontend/src/app/insight/hotspot/`）

| 页签 | 内容 |
|---|---|
| 热点大盘 | 指标卡（总热点/新增/平均增速）、阶段分布、平台占比、Top5 走势缩略；筛选=订阅×数据源×平台×阶段×时间窗(24h/7d/30d) |
| 热点榜单 | TOP 列表：名称/所属订阅/覆盖平台/得分/增速/内容数/情感/阶段标记；行点开=热点详情（成员内容、观点分化占比、关联词云、首发平台时间线、跳转内容原链与表格行）；聚类纠偏入口：拆分/合并/标记非热点（纠偏回灌阈值提示，不改原始行） |

## 十二、合规与风险（继承原方案、按本系统实现口径收窄）

1. 采集只发生在**租户用户自己本机的浏览器**——主通道是 BotBuddy 主机托管的指纹窗口、备用是本机 Chrome 插件，两条都是用户自有设备与自有账号，客户端始终在用户机器上；**采集 SKILL 包只给步骤与字段规则，不绕过登录/验证**；只采显式配置的公开页对象、只存标题/文案/公开互动数/封面，不存视频原文件、不抓登录后可见的私有内容与私信；步骤与截图留痕是审计底座关不掉（同采集落表方案 §H 口径）。托管档案用独立「洞察采集」指纹，与用户日常浏览档案隔离。
2. 平台条款风险如实标注：数据源页与榜单页脚注「来源为用户设备公开页面采集，数据仅供内部选题参考」；不对外宣称平台全量数据。
3. 官方开放平台 API（抖音/小红书热榜接口等）为后续批次的第二通道，资质到位前不承诺。
4. 电商销量取页面公开展示值，界面标注"仅供业务参考，不作为精准经营依据"。
5. 个人信息（博主联系方式）不入预置表列；批量抓联系方式维持「人工确认」红线（采集落表方案 N9=A 已定）。
6. 审计：数据源/订阅变更、采集任务启停、快报导出全部 `identity.audit`；AI 用量全走网关计量。
7. 性能：聚合调度增量游标（行 id + `collected_at`），单次窗口上限 + 分批，防大表全扫；`insight_metrics` 行数 = 键数×周期数，可控；`insight_collection_runs` 按订阅/时间分页归档。

### 14.4 仍待补 / 已知边界

1. 批次终态靠通道回填：主机当轮没跑起来时状态停在「执行中」，需要主机侧回报或超时规则才能收敛成 `failed/skipped`。
2. 泛化网站源头包（`insight-collect-site`）的真实命中率未验证，识别失败目前只按包内红线"如实回报、不硬猜选择器"。
3. UI 只做到静态编译 + 接口链路实测，未做浏览器点击级验收（本会话浏览器截图不可用）。
4. 采集健康度里的"登录态失效 → `NEED_LOGIN`"降档标注尚未实现（当前只在离线时给通道入口）。
5. **不属于本次改动、但同一条链路上的既有缺口（建议一起修）**：`insight_metrics` 只有 `interaction`（来自采集内容）与 `visual`（来自资产打标）有生产者，`commercial` 一支**没有任何写入方**——即趋势采集写进「电商选品观测」表的行目前还没有分析出口，§7.3 的「价格带 / 上新增速 / 爆款打分」和四象限纵轴都还是空的。修法建议：按 `来源关键词` 聚合选品行，用「销量展示值 + 评价数 + 上新新鲜度」出一支 `commercial` 日粒度指标，接法与 `interaction` 完全同形（同 upsert 唯一键、同 `insight_metrics` 表）。本次只做配置分治，没顺手改分析口径。
6. 电商表的关联列没有 `subscription_id`（内容表有），所以趋势侧排班行的"已采行数"读不到按排班的归因；要补就同时补 `collectionGoal` 的留痕指令，两处一起改才自洽。
