> 状态：**P0 底座、P1 核心闭环、P2 分销与资金均已实现并通过静态校验与单测**（见 §十三～§十五）；P2 仍有两处设计范围内未交付项，见 §十五.3。

## 一、产品口径（需求方已确认的四项决策）

| 决策点 | 结论 |
| --- | --- |
| 交付范围 | **分四期全量对齐参考源码**：P1 上门服务核心闭环 → P2 分销代理/渠道业务员 + 卡券营销 + 余额储值 + 提现税点 → P3 门店到店 + 动态社区 → P4 虚拟号 / 服务录音 / 云打印 / 电子合同 / 手机端后台 RBAC。每期独立可验收、可上线。 |
| 发布链路 | **下载定制代码包 + 一键直传微信，两者都给**。用户在后台填自己的小程序 AppID + AppSecret + 代码上传密钥，平台用 `miniprogram-ci` 子进程直传为**开发版**；提审与发布由用户在自己的微信公众平台完成。界面必须明示「上传为开发版，提审发布请在你自己的小程序后台操作」。不做微信第三方平台代开发（需服务商资质，另立方案）。 |
| 小程序源码形态 | **单模板 + 打包注入**：仓库根新增 `onsite-miniprogram/`（原生微信小程序，与既有 `miniprogram/` 同构，不引入 uni-app/Taro），出包时按租户注入 AppID / apiBase / 品牌名 / 主题色 / 模块开关 / tabBar 文案。所有租户共读一份源码，改一处全员生效。 |
| 资金通道 | **租户自有微信支付商户号（APIv3 直连）**，资金直接进租户自己账户，平台不经手、不记账；配套租户自己的 APIv3 密钥、商户证书与回调。未配置商户号时降级为「线下/转账收款」标记，订单流程照跑。 |

一句话产品定义：**每个本站用户都能开一个属于自己的上门服务微信小程序平台——定义服务与技师，配置可约时间与车费，收自己的钱，让技师在同一个小程序里接单打卡，并把小程序一键传进自己的微信账号。**

### 与既有底座的关系（重要）

- `docs/私域小程序与电商小程序工具设计方案.md`（电商小程序工具 `/mall`）**已定稿但未实现**，本方案与它共享同一批底座能力，因此**先把「私域小程序」共享层做出来，两个工具都用它**：
  1. 工作台 → **私域小程序** 分组（三级菜单，沿用「内容创作」分组的写法）。
  2. **按租户的小程序主体层**：`miniprogram_apps`（一店一行：AppID/Secret/上传密钥/robot/合法域名/品牌）+ 按租户的出包台账。加密沿用 `backend/src/miniprogram/miniprogram-crypto.ts` 的 `EXTERNAL_CRED_KEY` + AES-256-GCM 写法，但**上下文串掺入 AppID**，跨主体密文不可互解。
  3. **租户凭据版 `miniprogram-ci` 直传**：现有 `miniprogram-ci.service.ts` 只取平台单份凭据（`settings.ts:201-223`），改为可传入主体凭据（平台凭据作为兜底），子进程隔离与 240s 超时口径不变。
  4. **C 端顾客令牌体系**：独立于站内会话签发（不复用 `issueSsoSession`），载荷含 `shopId + customerId`。
  5. **租户商户号微信支付 APIv3**：下单/签名/回调解密/退款，两个工具共用一个 `wechat-pay-v3` 底座模块。
- 电商方案里的 `mall_wechat_configs` / `mall_releases` 上收为共享表，避免同一种凭据建两张表。**需需求方确认这条改动**（见 §十一 待确认项 1）。
- 现有「用户版小程序」（`miniprogram/`，移动办公延伸，全平台一份 AppID）**不动、不合并**：它是站内能力的移动端壳，业务接口 100% 复用站内契约；上门服务的 C 端顾客不是站内用户，必须物理隔离。

## 四、数据模型

归属口径沿用 `GeoSite` 与电商方案：`ownerUserId`（本站用户 = 平台主人）+ `shopId`（上门服务实例），代客作业留痕 `enterpriseId/enterpriseUserId`。服务层统一 `requireShop(user, shopId)` 二次校验，越权抛 `BusinessException(ErrorCode.FORBIDDEN)`。**所有查询必须带 `shopId`**，这是评审红线。

### 4.1 P1（核心闭环）27 张表

**租户与发布（3）**

- `onsite_shops` `OnsiteShop` — 上门服务实例。`ownerUserId` `shopId` 语义在主体表，此表存：`name` `slug`(全局唯一，C 端 `bootstrap?slug=`) `logo` `slogan` `servicePhone` `status`(DRAFT/ONLINE/SUSPENDED/CLOSED) `themeJson`(主色/导航/背景) `tradeJson`(自动取消分钟、车费开关、超时宽限、可约天数、时间片粒度、前后缓冲、是否派单、是否允许技师抢单、评价开关、协议 ID) `shareImage` `offBy` `offReason` `createdAt/updatedAt`。
- `miniprogram_apps` `MiniProgramApp`（**共享表，非 onsite_ 前缀**）— 一店一行微信侧凭据：`ownerUserId` `shopId` `scene`(ONSITE/MALL，区分主体用途) `appId`(唯一) `appSecretCipher` `uploadKeyCipher` `robot` `mchId` `payApiV3KeyCipher` `payCertSerial` `payPrivateKeyCipher` `payEnabled` `mapKeyCipher` `messageTemplateIds`(JSON：下单/接单/取消/换技师/求救) `qrcodeUrl` `verifiedAt` `status`。接口只回 `xxxConfigured: boolean` 掩码，**任何读接口不回明文**。
- `miniprogram_releases` 扩展 — 在现有表加 `ownerUserId`/`shopId`/`scene`（现有表无归属字段，`schema.prisma:13214-13239`），唯一约束由 `@@unique([version, channel])` 改为 `@@unique([shopId, scene, version, channel])`；新增 `uploadStatus`(NONE/QUEUED/UPLOADING/SUCCESS/FAILED) `uploadError` `wechatVersion` `uploadedAt` `reviewStatus`。**同店直传互斥**：串行队列 + 全局限并发。

## 五、核心算法与状态机（必须集中实现点，禁止散写）

### 5.1 订单状态机

```
DRAFT ──create──▶ PENDING_PAYMENT ──pay──▶ PAID ──accept|dispatch──▶ ACCEPTED
   │  ├─expire(over_time)──▶ EXPIRED
   │  └─customer cancel──▶ CANCELLED
   ▼
ACCEPTED ──depart──▶ EN_ROUTE ──arrive(+拍照)──▶ ON_SITE ──start──▶ SERVING
   ├─staff reject──▶ REJECTED
   ├─change staff──▶ ACCEPTED（保留时间轴，车费差额留痕）
   ▼
SERVING ──complete(+拍照)──▶ COMPLETED ──sign──▶ SIGNED ──review──▶ REVIEWED
   ├─refund apply──▶ REFUND_PENDING ──agree──▶ REFUNDED / ──reject──▶ 回到原态
   └─addon（子单挂在 SERVING/COMPLETED 之上，父单 is_add=1 + parentOrderId）
到店子链（P3）：PENDING_PAYMENT → PAID → ACCEPTED → SERVING → COMPLETED(核销人 verifyOperator)
```

- **每次状态迁移必须在同一事务里写 `onsite_order_status_logs`**（源码 `order_control_log` 就是这个用途）。
- 排期占用判定用 `status NOT IN (PENDING_PAYMENT, EXPIRED, CANCELLED, REJECTED, REFUNDED)`，与源码 `pay_type not in (-1, 7)` 同语义但显式。
- 佣金记录（P2）**下单即预生成、支付才生效**（源码 `status -1 → 1`）；退款联动冲销。这条口径必须在契约注释里写明，避免实现者改成「支付后才算佣」。

### 5.2 可约时间轴（`onsite.schedule.service.ts`，唯一实现点）

入参：`shopId` `staffId?` `serviceId` `date`。参数取自 `shop.tradeJson`：`timeUnitMinutes`(默认 30)、`maxDays`(默认 7)、`bufferMinutes`(前后缓冲)、`allowCrossDay`。

1. 技师可服务时段（`serviceStartAt/serviceEndAt`；**end < start 视为跨零点夜班**，比较时 +86400s）。
2. 切片 → 每片判断：与既有订单区间 `[orderStart - buffer, orderEnd + buffer]` 相交 → 不可选（原因：已被预约）；与休息段相交 → 不可选（原因：技师休息，可点击查看原因）。
3. 已过期片（`slotTime - buffer <= now`）不可选；**技师本人视角不做过期过滤且缓冲为 0**（源码 `is_coach` 分支，属真实业务口径，需保留）。
4. 服务时长需求 > 单片时，按 `durationMinutes` 连续占片校验。
5. 结果写 `onsite_staff_schedule_cache`（缓存），订单变化时按 `staffId + date` 失效。
6. 到店形态（P3）叠加门店营业时段判定（源码 `StoreList::checkStoreStatus`）。

单测覆盖：跨零点、缓冲边界、加钟子单占位、休息段、并发下单占位（事务 + 行锁或乐观锁校验）。

### 5.3 车费引擎（`onsite.travel-fee.service.ts`）

`规则命中（cityId → 店铺级 → 平台预置）→ 距离（驾车距离 API → Haversine 直线 → 失败用默认 `minFee`）→ 计费 = startFee + max(0, km − startKilometers) × pricePerKilometer − freeKilometers 对应部分 + virtualExtraKilometers 加成`。距离与命中规则**整块快照进订单**（改配置不影响历史单）。地图 key 属租户凭据，缺省时降级为直线距离并在订单备注留痕，**不得静默失败**。

### 5.4 分账引擎（P2，`onsite.commission.service.ts`）

参考源码最复杂也最容易做错的一块：一笔佣金由「技师收入」和「代理商收入」按比例分担，平台侧不为佣金垫钱。模型：

```
规则行 = 层级类型(分销商/业务员/渠道商/合伙人/代理/技师邀请充值)
       × {totalRate, staffBorneRate, ownerBorneRate, platformBorneRate}
结算单 = 订单 → 按 order_item 拆分 → 每条佣金带 sourceRole + borneBy(技师/代理/平台) + 承担金额
冲销   = 退款 → 按行按比例反向冲销 + settlements 余额回滚（同事务）
```

金额一律 `@db.Decimal(12, 2)`，服务层以「分」为单位整数运算，禁止浮点累加。

### 5.5 触达

下单/接单/取消/换技师/求救 → 站内通知（现有通知中心）+ 微信小程序订阅消息（租户 AppID + 租户模板 ID，模板由用户在后台填）+ 服务号模板消息（复用 `backend/src/wechat-mp/`）+ 短信（可选，P4）。**同一份 `notify` 编排函数**，缺凭据时按顺序降级并在响应里给出可操作的引导（不是只报错）。

**出包与直传链路**：

```
用户点「生成代码包」
  → onsite.release.service.build(shopId)
      读 onsite-miniprogram/ 源 → 注入 config.js（apiBase/shopSlug/appName/themeColor/features）
      + project.config.json(appid) + app.json 品牌与 tabBar 文案 + sitemap
      → store zip（scripts/lib/zip-store.mjs 语义）+ SHA256 → 上 OSS → 落 miniprogram_releases
用户点「上传到微信」
  → 队列（同店互斥）→ 子进程 miniprogram-ci（凭据取该店 miniprogram_apps 解密值）
  → 成功记 wechatVersion + SUCCESS；失败记 uploadError（可执行中文提示）
下载包入口常驻：zip 直链（OSS），用户可用微信开发者工具自行导入。
小程序码：wxacode.getUnlimited（scene = slug + staffId/serviceId），按 md5(shopId+scene) 幂等缓存进 OSS。
```

主包体积红线：参考源码小程序主包 2.3MB + static 1.1MB，**本方案要求主包 ≤ 1.6MB**（微信 2MB 限制），静态图一律走 OSS URL，不随包带。

## 十二、已识别风险

1. **工作量**：参考源码 113 表 / 113 页面，本方案 P1 收敛到 27 表 / 约 118 接口 / 13 前端页 / 约 44 小程序页，仍是本项目迄今最大的单模块（与电商方案量级相当）。按 P0→P4 顺序推进，每期可独立上线。
2. **排期与车费是两个易错引擎**：跨零点夜班、缓冲重叠、加钟占位、并发抢档、距离降级，必须有单测与唯一实现点，否则多端各写一份必然漂移。
3. **分账语义**：源码「佣金由技师与代理商收入承担、下单即预生成、支付才生效、退款按比例冲销」是容易实现错的口径，P2 开工前先用一张算例表与需求方对齐样例。
4. **`miniprogram-ci` 租户规模化**：依赖重、每店上传起一个子进程，需同店互斥 + 全局限并发 + 240s 超时 + 失败可执行提示；IP 白名单是人工前置，必须在上传前检测并给带操作路径的引导。
5. **资金合规**：资金流不进本站，本站只提供软件；页面明示「资金进你自己的微信商户账户」，平台侧保留「是否允许收款」总开关。
6. **个人信息与安全**：技师/顾客手机号、身份证、实时定位、求救、服务录音，属高敏数据；默认最小化采集，录音与定位默认关闭、明示授权、可设保留期，平台侧可强制关闭。
7. **C 端顾客与站内用户物理隔离**：任何「把 C 端顾客当 `User` 处理」的捷径都会破坏租户隔离，代码评审专项盯。
