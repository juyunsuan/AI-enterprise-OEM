## 一、结论先行：哪些已经集约、哪些没有、哪些不该集约

| 能力 | 现状 | 集约化判断 | 一句话依据 |
|---|---|---|---|
| **客服会话** | ✅ 已高度统一 | 保持；仅收敛 AI 调用 | 全项目唯一 `service_desk_*` 表族（10 张），各端都是引用 |

| **调度器框架** | 30+ scheduler 各自实现 | 可抽框架 | 启动/停止/幂等守卫重复 |

## 二、用户点名场景一：客服是否应统一用 AI 客服？

### 2.1 结论：**已经统一了，且没有第二套客服系统**

`backend/src/service-desk/` 是全项目唯一的客服会话底座（4 个文件：`service-desk.service.ts` 2973 行、`controller`、`public`、`crypto`）。唯一一套会话/消息表：

| Model | 物理表 | 用途 |
|---|---|---|
| `ServiceDeskChannel` | `service_desk_channels` | 渠道（wecom_kf / wechat_mp / feishu_app / custom） |
| `ServiceDeskSite` | `service_desk_sites` | 多站点（每账号上限 20） |
| `ServiceDeskSetting` | `service_desk_settings` | 欢迎语/排队语/AI 模式/转人工关键词/知识库 |
| `ServiceDeskAgent` / `Group` | `service_desk_agents` / `groups` | 坐席与客服组 |
| `ServiceDeskVisitor` | `service_desk_visitors` | 匿名访客（只存 token 哈希） |
| `ServiceDeskConversation` | `service_desk_conversations` | 会话主体 |
| `ServiceDeskMessage` | `service_desk_messages` | 消息（`senderType`: visitor/agent/ai/system） |
| `ServiceDeskCannedReply` / `Faq` | `service_desk_canned_replies` / `faqs` | 常用语 / 固定问答 |

多站点、真人接待（坐席上线/轮询分配/接入/转接/关闭/评分，含并发上限 `maxConcurrent`）、AI 五种模式（OFF/CANNED/SUGGEST/AUTO/BOT）全部在此实现。

### 2.2 各端如何接入（都是引用，不是自建）

| 端 | 接入方式 | 证据 |
|---|---|---|
| 官网 H5 | `/embed/service-desk` → `/api/public/service-desk/open/*` | `frontend/src/app/embed/service-desk/page.tsx` |
| 用户版小程序 | 坐席工作台，`/enterprise/service-desk/conversations` | `miniprogram/utils/api.js:82-94` |
| 上门服务 | webview `/embed/service-desk?key=...`，本域不建会话表 | `onsite.assist.service.ts:18-27` 注释明确 |
| 卡密商城 | `serviceEntry()` 读 `deskSiteKey/deskEmbedUrl` | `card-shop-miniprogram/app.js:104-113`，“本页不含任何客服逻辑” |
| 快递 / 数字人小程序 | 同 webview 引用 `site.deskEmbedUrl` | `kuaidi-miniprogram/pages/service/service.js:12` |
| 企微客服渠道 | `receiveChannel()` 把外部消息写入同一张 `service_desk_message` | `service-desk.service.ts:728-775, 865-872` |
| 品牌商城 | 目前只有电话/二维码，**无在线客服** | `components/diy/assist/`、订单详情 |

### 2.3 那些"看起来像客服"但不是的东西（不该合并）

- **企微 SCRM**：26 张 `scrm_*` 表（客户群/活码/群发/SOP/敏感词），是私域客户运营，与访客会话不是同一实体；板块开关各自独立。
- **SNS 私信**：`sns_mail_threads` / `sns_messages`，`source=LOCAL|AIWORKIN` 有上游同步语义，合并会破坏社交关系模型。
- **IM 连接器**：`im_connectors` 等 7 张表，做的是组织通讯录/通知/审批镜像，**根本没有会话表**。
- **邮箱**：mail_* 表 + 话术模板，`MailboxService` 无任何 LLM 调用。
- **各类 AI 助手**（BI/AI 编程/质检大厅/获客）：各自 session/message 表 + 各自提示词，是"AI 功能"而非"客服接待"。
- **用户版小程序 `service-chat`**：是**坐席端**，与 H5 访客端角色不同，不应合并为同一页面。

### 2.4 唯一的技术债：客服 AI 调用绕开了统一网关

核验代码（`service-desk.service.ts:2229-2240`）：

```ts
private async callModel(...) {
  const { setting, target } = await this.ownerTarget(ownerUserId);  // → this.models.resolveTarget(...)
  const reply = await geoChatMulti({                               // ← 直接发请求，未走 aiChat/meter
    baseUrl: target.baseUrl, apiKey: target.apiKey || '',
    model: setting.aiModel.trim() || target.model || '', ...
```

`ai-gateway.ts:17-31` 自称"全系统统一 AI 网关，收口取模型/发请求/统一计量"，数十个模块已接入，唯独客服没有。后果：客服 AI 对话**不落 `usage_events`、不受统一计量与审计**。

**改法**：把 `callModel()` 换成 `aiChat()`（内置 `requireModel` + `meter`），`moduleModel` 传 `setting.aiModel`、`moduleChannelId` 传 `setting.aiChannelId` 即可——保留客服自己的模型选择，纳入统一计量。

**附带机会**：品牌商城若要做在线客服，直接下发 `deskSiteKey/deskEmbedUrl`（照搬卡密商城），**不要新建会话表**；公众号被动回复可借 `findFaqAnswer()/kbRecall` 提供话术，但保留 5 秒回复约束。

## 三、用户点名场景二：模型是否应统一用平台模型配置？

### 3.1 结论：**不应一律统一，但"取模型算法 + 计量"必须收敛**

`ek_`/平台模型只是"用户未自带渠道时的兜底结算层"（`resolveModel` 第 280-295 行、契约 `model-plaza.ts:22` 明确"用户自带渠道不进广场、不扣积分"）。真正的问题是**有两套真相源**。

### 3.2 三套"统一"的不同层次（核验后的精确判断）

| 层次 | 数量 | 事实 |
|---|---|---|
| 凭据解析函数 | **1 套** ✅ | `ai/ai-channels.ts::loadChannelCredentials()`；channelId 语义统一：`0=AIPDD`、`-1=LocalAPI`、`>0=contentModelChannel` |
| 模型选择算法 | **2 套** ⚠️ | `ai-gateway.resolveModel()`（5 级阶梯）vs `content/model-setting.service.resolveTarget()`（3 级阶梯） |
| 请求发送出口 | 多套 ⚠️ | `geo-llm.client`、`upgrade` 手写 httpRequest、`ai-code-engine`/`agent-engine` 手写 streamRequest、`bot-host-client` Node http、`model-plaza/relay` |
| Key/配置存储 | 7+ 处 | `content_model_slots/channels`、`rpa_llm_settings`、`workbuddy_llm_settings`、`systemSetting.model_platform_defaults`+`model_catalog`+`model_upstreams`、`geo_provider_settings`、本机 SQLite channels、`api_key`(`ek_`)、平台 AIPDD、`ai_call_accounts` |
| 计量覆盖 | **不完整** ❌ | 仅网关 `meter()` 触发；直连链路里只有 `content-media`(recordAiUsage)、`workflow-engine`、`skill-review` 补了账 |

两套解析器实测对比：

| | `ai-gateway.resolveModel()` (210-296) | `ContentModelSettingService.resolveTarget()` (687-767) |
|---|---|---|
| 阶梯 | override → module → **account** → **legacy** → platform | override → account → platform |
| 读取表 | `contentModelSlot` + `rpaLlmSetting` + `workbuddyLlmSetting` + `model_platform_defaults` | 仅 `contentModelSlot` + `model_platform_defaults` |
| 调用方 | 35 处 import 网关（含 `acquisition/bigdata/workflow/kb/insight/rpa/wecom-scrm` 等） | `bi/crm/question-hall/service-desk/lowcode/skill-generator/skill-review/upgrade/ai-code/agent-engine/agent-library/content-media` |
| 缺配置行为 | 返回 null → 调用方规则兜底 | 抛 `BusinessException`（第 732 行） |

**后果**：同一用户在「模型设置」配的模型，经不同功能入口会得到不同解析结果（legacy 层只在网关侧生效）——这正是 `docs/系统AI底座优化升级方案.md:34` 自己诊断的"用户配了却时好时坏"，而该文档第 240 行宣称"调用点已全部迁移"与代码事实不符。

### 3.3 主审实测（命令核验）

```
直连 geoChatMulti 的文件：12（含 2 个 spec + ai-gateway 自身 + 9 个业务模块）
import ai-gateway 的文件：35
*-crypto.ts：22
```

### 3.4 收敛路径与合法独立域

**应当收敛**：
1. 类别 A/B 的直连改为 `aiChat/aiJson/aiStream/aiEmbed`（BI、CRM、专题大厅、客服、低代码、技能生成/审查、升级分析、AI 编程、Agent 引擎/库、内容多媒体、`kb-llm.ts`）。
2. 让 `resolveTarget` 内部委托 `resolveModel`，只保留"抛错 vs 返回 null"差异 → legacy 层对全模块一致生效。
3. 无法立即迁移的自研流式链路，结束时补调 `recordAiUsage()`（网关第 441 行已留此 API，目前仅 2 个模块在用）。

**必须保持独立**（有代码与产品语义证据）：
- **客户端本机模型**：`bot-host-client/src/main/agent/model-client.js` 用 Node 原生 http，配置在 `~/.botbuddy` SQLite，可离线、Key 不出本机——物理上无法走服务端网关。平台已用 `modelGrantForHost()`（`bot-host.service.ts:1431`）做到"配置平台下发、执行在本机"，合理边界；缺口仅是用量回传。
- **GEO 12 平台自带 Key**：目的是观测真实用户在各平台的搜索表现（`geo-settings.service.ts:14-19`），必须用对应用户真实账号，不共享、不回落 env。
- **`ek_` 对外网关**：`/v1/*` OpenAI 兼容协议适配层，自带鉴权结算，必须独立。
- **AIPDD Key 与平台模型双轨**：契约已明确分工，`platform-defaults.service.ts:229` 刻意隔离两者额度，是产品决策。

## 四、其余能力的集约化判断

### 4.1 支付：统一客户端被 4 个模块绕过（P0）

`points/wechat-pay.client.ts`（373 行，`WechatPayClient`）功能完整：`native/h5/jsapi/refund/query/close/parseNotify`，内建平台证书缓存、RSA-SHA256 验签、**5 分钟防重放**。唯一实例在 `services.ts:1457`，但只注入了 onsite、points、health。

4 个模块各自重写（`brand.pay.service.ts` 305 行 / `card-shop.pay.service.ts` 257 / `dh.pay.service.ts` 302 / `kuaidi.pay.service.ts` 247）：`apiBase/nonce/rsaSign/authHeader` 四函数各写一份，`prepay` 下单、`decryptNotify` 解密、`refund`、`notifyOk` 逐行对应。`card-shop vs kuaidi` 相似度 **86–89%**（核心加解密/签名代码零差异）。

**回调验签两套 7 处**：完整验签（RSA+防重放+GCM）3 处走统一客户端；轻量验真（仅 GCM authTag，无防重放）4 处在 brand/card-shop/dh/kuaidi 的 public 里——理由成立但**缺防重放**是实质安全差异。

> 事实纠正：全仓 `grep -i ecb` 无任何匹配，实际全部是 **AES-256-GCM**（微信支付 APIv3 官方算法）。

**可集约**：下单签名/GCM 解密/退款 → `WechatPayClient.jsapi/refund/parseNotify`。**必须保留**：`notifyUrl`、`description`、平台闸门、退款有无、回调后 `markPaid` 副作用、凭据作用域（shopId vs siteId）。health 与 onsite 已证明店主自有商户号转成 `WechatCredentials` 即可复用统一客户端——技术上无阻碍。

### 4.2 凭据加密：22 份同构实现

22 个 `*-crypto.ts` 全部相同骨架：`EXTERNAL_CRED_KEY` → `sha256(context|secret)` → `aes-256-gcm` + 12 字节 IV → `[iv]:[tag]:[body]` base64。相似度：`miniprogram vs wechat-mp` 85%、`mini-app vs health` 81%、`content vs agent-mcp` 79%、`rpa vs workbuddy` 78%。

**可集约**：通用 `encrypt/decrypt` → 单一 `CredentialCrypto(context, scope?)`，以 `AccountCrypto` 为样板。**需改造**：`mini-app-crypto` 用 HMAC 派生 scope、`health-crypto` 用 Hash 串联——统一会改变存量密文可解密性，属**数据迁移级改造**，必须先定策略。领域方法（`signState/verifyState`、`sealConfig/openConfig`、指纹脱敏）保留各模块。

### 4.3 存储：已是集约标杆，仅修补

`StorageService`（`storage/storage.service.ts:8`，"全站唯一存储出口"）→ `OssService`（V4 签名）→ `attachment-files.ts`（10 文件/10MB 上限）→ 前端 `upload-attachments.ts`。**无需再建抽象**。修补点：`dh.public.ts:272` 等直连 `dh.oss.upload()` 应改走门面；`/api/public/digital-human/upload` 声明 100MB 但不在 `bodyLimit` 分级中（默认 12MB），存在错配需实测。

### 4.4 通知：站内统一，渠道分散

`NotificationService.notify/notifyMany` 是站内信唯一写入口（`prisma.notification.create` 全仓仅 1 处），被 25+ 模块调用。但短信（`notify-channel.service.ts`）、营销邮件（`aliyun-mail`）、企微（`scrm.client.ts`）、微信模板消息（`wechat-mp.push.service.ts`）是独立发送链路。可抽 `MessageDispatcher` 门面，但验证码/营销的业务语义、配置源、幂等要求不同，需产品决策后再收编。

### 4.5 审核：内容安全统一，工作流审核不该合并

`publishReviewMiddleware`（`app.ts:313` 全站唯一挂载点）+ `PublishReviewService`（阿里云内容安全，命中抛 `CONTENT_MODERATION_BLOCKED`，上游超时降级放行）。`RULES` 表按"方法+路径"识别发布动作。**潜在缺口**：评论/回复类内容不在规则表中，需评估扩展。工作流审核（好友申请/知识库 PENDING_REVIEW/健康药师审核）是领域状态机，**不该合并**；AI 闸门（`ai-guard.service.ts`，管配额开关）与内容审核（管文本合规）职责不同，也不该合并。

### 4.6 检索、排期、单号、计费：已有底座，保持

- **检索**：`ai/retrieval-kernel.ts`（词面 0.6 + 向量 0.4 混合打分）被 16+ 文件复用；业务列表搜索绑定各自模型与 org scope，不该合并。
- **排期**：`common/schedule.ts` 被 RPA/Workbuddy/内容助理/Bot 主机 6 模块复用；`workflow-cron.ts:122` 另写 cron 解析（注释说"同一口径"但未 import），应收口。30+ scheduler 可抽 `SchedulerRegistry` 统管启停与幂等守卫。
- **单号**：`common/document-number.ts::allocateNo` 覆盖 24 前缀、事务内原子取号、20+ 模块复用；`commerce-core/ident.ts` 是电商高并发+可重试的第二套口径（时间戳+随机+唯一约束兜底），**有业务理由，不建议合并**。幂等可抽轻量 `IdempotencyGuard`（`points.idempotencyKey` 已是事实标准）。
- **计费**：`PointsService.debit/credit/debitTx` 统一（28 处调用）；知识付费站点会员积分是另一运营主体（签到/卡密/内容定价），**保持独立正确**。

### 4.7 导入导出：唯一"完全无底座"的能力

手写 CSV（mechanisms/data-table/card-shop/crm/acquisition/bigdata/lead-prospecting/tencent-qidian）+ 唯一 exceljs 使用者（insight.service.ts:3454-3585 动态 import）+ 直连阿里云名单（aliyun-mail）。可抽 `CsvExportUtil`（BOM/上限/转义/文件名）与 `SpreadsheetService`（惰性加载 exceljs，XLSX/CSV 双写）。`community-import`（Comfy 任务迁移）语义不同，不塞进通用底座。

## 五、集约化路线图（继前份报告 P0/P1/P2 之后）

| 优先级 | 动作 | 证据/收益 | 风险 |
|---|---|---|---|
| **P0-A** | 客服 `callModel()` 改走 `aiChat()` | 补上客服对话计量与审计 | 低：改 1 个函数 |
| **P0-B** | `resolveTarget` 委托 `resolveModel`，消除双解析器 | 同用户跨功能模型一致；legacy 层全模块生效 | 中：需回归各模块取模型行为 |

## 六、开发指引增补

1. **新增 AI 功能**：一律调 `ai-gateway` 的 `aiChat/aiJson/aiStream/aiEmbed`，禁止直接 `geoChatMulti`；确需流式自研，结束必须 `recordAiUsage()`。架构守护脚本可扩展：扫描 import `geo-llm.client` 的白名单（当前仅 `ai-gateway` 与 GEO 自带 Key 链路）。

3. **新增微信支付场景**：用 `WechatPayClient` + `payRuntime` 转 `WechatCredentials`，禁止再复制 `rsaSign/decryptNotify`。

7. **新增定时任务**：业务排期用 `common/schedule.ts`；调度器注册进 `SchedulerRegistry`（落地后），不要裸写 `setInterval`。
8. **新增地区数据需求**：复用 `shared/region-dictionary.ts`，不要自建城市表。
