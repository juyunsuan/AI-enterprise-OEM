# 第一部分　现状结论与目标架构

## 1. 一句话现状与三大架构特征

**现状**：以 **Hono + Prisma（MySQL 事实源 / PG 派生）** 为后端、**Next.js 16 纯 CSR** 为 Web 前端、通过 `@enterprise/contracts` 契约包打通前后端类型、以 **6 个物理独立的微信小程序 + 4 类外部客户端** 为触点的**大型企业 SaaS 单体工作台**。

**三大架构特征（代码事实）**：

1. **契约驱动 + 约定式路由是主干**：`packages/contracts/src/endpoints.ts`（15722 行、440 个 `path:`）定义端点，`http/automation-routes.ts` 用 `moduleHandlers()`（88 次）按前缀派生 handler 动态注册；命令式 `route-groups/`（26 域）与 `app.ts:460-522` 公开通道并存。README 的 2087 HTTP 操作与契约 440 path 是两种统计口径。

2. **租户与身份靠"键 + 令牌 issuer"逻辑隔离，非数据库级**：无独立 `Tenant` model，统一抽象为 `(orgType, orgUserId)`（`tenant-scope.service.ts:11`）；C 端顾客按 `shopId/siteId + customerId` 双条件过滤；不同终端用不同 JWT issuer + HKDF/HMAC 派生密钥物理隔离。边界注释完备，但**隔离正确性高度依赖每个 service 自觉写 WHERE**。

3. **能力在"技术底座层"共享充分，在"业务终端层"几乎零共享**：Web 侧 `api/http.ts` + `endpoint.ts`（2163 处调用）高度统一；后端 `transport.ts`、`ai-gateway.ts`、契约包为真共享。但 6 个小程序的 `request.js/auth.js/session.js/api.js` 是**纯物理复制**（kp↔card-shop request 88.3%、dh↔kp session 82.0%），后端 5 套令牌 dh↔kp 相似度 62%。

## 3. 五个最关键的问题

1. **一致性债已发生**：小程序 401 处理 4 种口径，card-shop 落后为 ES5 回调、brand 独享自动重登——分叉是现实而非假设（一处安全修复要改 6 份）。
2. **计量与审计有黑洞**：客服 AI 直连 `geoChatMulti` 不落 `usage_events`；12 处模型直连只有 3 条链路补账；存储字节 18+ 处绕过台账——**成本看不见，就无法计费与优化**。
3. **存储来源分散、费用不在一处**：字节落在平台 OSS、AIPDD 云中转、本地磁盘（512MB 升级包）三处；归属键混用 `userId`/`siteId`/`shopId`/`ownerUserId`，无法统一归集计费。
4. **计费语义割裂**：平台有 `Points` 钱包 + `ModulePricing` 按量 + `BillingRule` 按量两套引擎，但套餐 `EntitlementPlan` 只有 `priceMonthly` 且零业务调用，小程序各搞私域钱包（kp 积分 / dh 三账户）——**没有"按月/年/次数/订单数"的统一订阅计费**。
5. **边界靠约定不靠框架**：onsite/brand/card-shop 共用 `private-mini-customer` issuer，仅靠 `scene+shopId` 双条件过滤；`customer-token.ts:12` 明示"越权判定交业务层"——任一 service 漏写一个 WHERE 即越权。

# 第二部分　功能能力集约化指引

## 5. 集约化的三条边界原则

是否集约，不看"名字像不像"，而看三件事：

1. **资金/数据归属是否同一主体**——资金直收店主商户号的交易（brand/card-shop/onsite/dh），平台不经手账本，**不能并入平台计费**。
2. **语义是否同一实体**——SCRM 客户群、SNS 私信、IM 通讯录、邮箱、各类 AI 会话与"客服接待访客会话"不是同一实体，**不能合并**。
3. **是否物理上可统一**——客户端本机模型（Key 不出本机、可离线）、GEO 12 平台自带 Key、`ek_` 对外网关、AIPDD 双轨，**物理/产品上必须独立**。

反过来说，**技术骨架（令牌、网络、加密、存储、支付签名、计量）无论业务如何分叉，都应该统一**——这正是当前分叉最严重、收益最大的部分。

## 6. 必须集约 / 条件集约 / 保持独立

### 6.1 必须集约（P0，收益明确、风险可控）

| 动作 | 问题与影响 | 改法（落地依据） | 验收 |
|---|---|---|---|
| **令牌工厂** | 2 套派生范式、5 套物理复制；共 issuer 边界无法审计 | 新建 `auth/mini-token-factory.ts` 统一 `issueToken/verifyToken`，5 套 `*-token.ts` 退化为传参；保留各自 issuer 与分表 | 无重复 HMAC 逻辑；"顾客令牌进不了 `/enterprise/**`""技师/顾客互斥"测试全绿 |
| **租户过滤下沉** | 隔离靠 service 手写 WHERE，漏写即越权 | 顾客态查询构造基类强制注入 `tenantId+subjectId`；扩展 `check-architecture.mjs` 扫描所有顾客态查询；推广 onsite 令牌互斥测试 | 架构守护纳入 CI |
| **@mini/core 抽包** | 6 份 request/auth/session，401 四种口径，分叉已发生 | 抽 `requestCore/sessionCore/loginFlow/errorMap`，各端只留 `config.js`+`api.js`；差异（API_PREFIX/租户码键/自动重登）参数注入 | 6 端 request.js 从 ~90 行降到 <20 行 |
| **模型解析归一** | 两套解析器，同用户跨功能取模型不同；legacy 层只在网关生效 | `resolveTarget` 内部委托 `resolveModel`，只保留"抛错 vs 返回 null"差异 | 回归各模块取模型行为一致 |
| **客服 AI 走网关** | `service-desk.service.ts:2229` 直连 `geoChatMulti`，客服对话不计量不审计 | `callModel()` 改 `aiChat()`，`moduleModel` 传 `setting.aiModel` | `usage_events` 出现客服对话记录 |
| **支付客户端收编** | 4 个 `*.pay.service.ts` 约 1100 行重复（最高 89%）；轻量验签缺防重放 | 下单签名/GCM 解密/退款 → `WechatPayClient.jsapi/refund/parseNotify`；保留 `notifyUrl`/凭据作用域/回调副作用 | 4 文件删除重复四函数；补防重放 |
| **存储字节全走门面+台账** | 18+ 处绕过、AIPDD 中转、本地磁盘；费用看不见 | 见专题一：各域改注入 `StorageService`，字节写入经 `SystemAssetService` 落台账 | bodyLimit 错配消除；`digital_asset_entries` 覆盖所有域 |

### 6.2 条件集约（P1，需先定策略再动）

- **凭据加密**：22 个 `*-crypto.ts` 相似度 78–85%，但 `mini-app-crypto`（HMAC 派生 scope）与 `health-crypto`（Hash 串联）口径不一——统一会改变存量密文可解密性，属**数据迁移级改造**，必须先定兼容策略（双读/渐进迁移），再抽 `CredentialCrypto(context,scope)`。
- **调度器框架**：30+ scheduler 的启停/幂等守卫重复，可抽 `SchedulerRegistry`；但业务排期继续用 `common/schedule.ts`，`workflow-cron.ts:122` 的平行 cron 应收口。
- **渠道消息门面**：短信/营销邮件/企微/模板消息 4 套，可抽 `MessageDispatcher`，但验证码 vs 营销语义、配置源、幂等要求不同，需产品决策。
- **导入导出**：抽 `CsvExportUtil`（BOM/上限/转义）与 `SpreadsheetService`（惰性 exceljs），`community-import` 语义不同不纳入。

### 6.3 保持独立（⛔ 明确不要做）

- 不合并 SCRM / 私信 / IM / 邮件进客服；不合并三类 AI 会话（客服接待 vs 各类 AI 助手）。
- 不合并 logistics / kuaidi / geo（**GEO = 生成引擎优化，不是地理**）。
- 不合并两套单号口径（`allocateNo` vs `commerceOrderNo`）。
- 不合并工作流审核与内容安全审核，不合并 AI 配额闸门与文本审核。
- 不合并站点私域积分（kp）与平台积分（`PointAccount`）——不同运营主体、资金不经平台。
- 不强行统一所有上传为"万能接口"（类型白名单、大小限制、归属差异大）。

## 7. 节约服务器功耗/费用的具体抓手

> "功耗"在此理解为**服务器资源消耗与费用**。以下每条都对应代码事实：

1. **大文件直传 OSS，不经过应用服务器**：`DigitalAssetService.presign()` → `OssService.signFormPost()` 让浏览器直传 OSS（`digital-asset.service.ts:746-779`），字节不进后端 HTTP 层 → 降低应用服务器带宽/内存/bodyLimit 压力，也规避 12MB 默认上限。所有大文件（素材、升级包、商品图）应推广此模式。
2. **存储集中在对象存储，停止本地磁盘扩容**：唯一持久化本地存储是 `upgrade/upgrade-package.service.ts`（512MB 升级包写 `update/packages`），应评估改走 OSS；`ai-code-staging`/`zip-extract` 是临时工件可保留本地。对象存储按量计费远低于自建磁盘冗余。
3. **停止 AIPDD 中转**：`/enterprise/content/uploads` 目前走 `AipddAssetClient.upload()`（`content.controller.ts:595-627`），字节绕开平台 OSS，既不计存储费也无法统一治理；改回平台 OSS + 台账。
4. **计量去重，减少无效 AI 调用**：模型解析归一 + 统一网关后，同一提示词不会因入口不同重复解析/重复调用；`resolveTarget→resolveModel` 消除 legacy 层分歧。
5. **按需计费替代固定容量**：存储按 GB·天、AI 按用量、订阅按周期——把成本与真实使用挂钩，避免为峰值容量长期付费（详见专题二）。

## 10. 系统资产模块设计

### 10.1 分层：采集层 / 门面层 / 出账层分离（关键判断）

> **不要把计费直接埋在 `StorageService.put()` 里**——门面方法签名 `put(path,content)` 没有 `userId`/业务类型，无法知道"该记谁的账"；且存储计费口径是 GB·天（按天快照），按次扣费会与日批重复。

```
   各业务域（digital-human/brand/onsite/health/community/附件/内容...）
        │  统一调用：systemAsset.put({ ownerUserId, assetType, bizRef, bytes })
        ▼
┌─ 采集/归属层（新增 SystemAssetService，位于门面之上）───────────────────┐
│  • 强制参数：ownerUserId + assetType + bizRef + bytes                    │
│  • 内部调 storage.put()/signFormPost()，同步写 DigitalAssetEntry 台账     │
│  • 统一归属键：全部映射到 userId（对象键 enterprise/{userId}/{type}/...）  │
│  • 原型即 DigitalAssetService.storeOwned()，可直接提升                   │
└───────────────┬────────────────────────────────────────────────────────┘
                ▼
┌─ 门面层（StorageService，签名不变，保持纯粹）──────────────────────────┐
│  put / signFormPost / remove / urlOf / stat / read                       │
│  • 唯一字节出口，"换底座只改本类"                                        │
│  • 可选：put/presign 内补一条"只观测不扣费"的 usage_events(bytes)         │
└───────────────┬────────────────────────────────────────────────────────┘
                ▼
┌─ 出账层（PointsBillingService，扩展而非重建）──────────────────────────┐
│  snapshotStorage() 聚合源：digital_asset_entries → 纳入全部域              │
│  chargeStorage()：GB·天 × module_pricing(asset_storage) → points.debit     │
│  → usage_events（billed=1）→ 欠费 ARREARS（只冻结新增，不删数据）           │
└────────────────────────────────────────────────────────────────────────┘

事实契约：DigitalAssetEntry.ossKey / fileSize / userId —— 三表之间的唯一纽带
```

### 10.2 落地改造清单

**可直接复用**：`StorageService` 门面、`DigitalAssetService` 的 `presign/registerUploaded/storeOwned`、`OssSettingsService`（AES-256-GCM 凭据）、`attachment-files.ts` 类型白名单、`PointsBillingService` 计费链路、大文件 presign 直传模式。

**必须改造**：

1. 把 18+ 服务的 `OssService` 注入改为 `StorageService`（`services.ts:3467-3472` 同时暴露 `services.oss` 是绕过根源），并让字节写入统一经 `SystemAssetService` 落台账。`services.oss` 仅保留给 `OssSettingsController.testConnection` 与门面内部。
2. `/enterprise/content/uploads` 从 AIPDD 迁回平台 OSS + 台账（`content.controller.ts:595-627`）。
3. 商品图补齐上传落点：`brand.goods.service.ts:513-514`、`card-shop.goods.service.ts:374` 目前只存外部 URL 字符串，改为上传后登记 `DigitalAssetEntry`。
4. 统一归属键：新增模块以 `userId` 为单一口径（现有数字资产已是此口径），小程序域的 `siteId/shopId` 通过"店主 userId"映射。
5. 修正 bodyLimit 错配：为两个 100MB 上传路径增加分级，或强制走 presign 直传。
6. 512MB 升级包评估改走 OSS presign 直传，停止本地磁盘扩容。

### 10.3 用户计费闭环（"一方面节约服务器费用，一方面给用户计费"）

- **免费额**：`module_pricing(asset_storage).freeQuotaAmount`（月免费 GB），超出部分计费。
- **计量**：`StorageDailySnapshot(userId, bytesAmount, snapshotAt)` 日批，天然对应"GB·天"。
- **计费**：`chargeStorage()` 按 GB·天扣平台积分 → `point_transactions` 留痕 → `usage_events` 记账；不足转 `ARREARS` 冻结新增上传但**不删数据**（`points-billing.service.ts:236-255`）。
- **可见性（建议补）**：给用户展示"当前用量/免费额/计费单价/本月账单"，来源即 `StorageMigrationService.overview()`（存量概览）+ 新增额度查询接口；把 `EntitlementQuota` 的 `GB` 单位真正接到资产存储上，形成"套餐含 X GB + 超量计费"的完整体验。

## 11. 节约服务器费用的量化逻辑

| 维度 | 改造前 | 改造后 | 节约来源 |
|---|---|---|---|
| 字节落点 | OSS + AIPDD 中转 + 本地磁盘三处 | 全部平台 OSS 一处 | 对象存储单价 < 自建磁盘冗余；停止扩容应用服务器 |
| 大文件传输 | 经应用服务器（受 bodyLimit 限制） | presign 浏览器直传 OSS | 省应用服务器带宽/内存，规避 12MB 上限 |
| 成本可见性 | 18+ 处字节不计台账 | 100% 进 `digital_asset_entries` | 能按用户归集、按量计费，成本转嫁真实使用者 |
| 计费口径 | 无统一 | GB·天 + 免费额 + 超量 | 不为峰值容量长期付费 |

> 说明：具体费用节省额取决于实际存储量与 OSS 单价，代码事实只能证明"机制上具备节约条件"（字节集中 + 直传 + 按量计费），不编造金额。

## 13. 边界：交易型订单 vs SaaS 订阅必须分开（最重要）

> 这是统一计费能否落地的关键判断。**不能把 6 个小程序的订单都塞进一个订阅模型**——那会同时破坏资金归属与计费语义。

| 维度 | 交易型订单（⛔ 不统一） | SaaS 订阅计费（✅ 统一） |
|---|---|---|
| 资金流 | 直收店主/站点自有商户号，平台不经手（`brand.pay.service.ts:60-69`、`dh.pay.service.ts:66`、`card-shop.pay.service.ts:66-70`） | 平台收款 → 平台积分/余额 → 按周期扣 |
| 标的 | 商品/卡密/单次服务/一次性权益包 | 一段时间内的**使用权 + 额度** |
| 生命周期 | 下单→支付→发货/履约→售后退款 | 订阅→周期扣费→续费/降级/过期 |
| 现有模型 | `BrandOrder`/`CardShopOrder`/`OnsiteOrder`/`DigitalHumanOrder`/`KnowledgePayOrder` | `EntitlementPlan/Quota/Usage`、`BillingRule`、`UsageEvent`、`Points` |

**结论**：`KnowledgePayOrder`/`DigitalHumanOrder` 虽带 VIP 期限，本质是"一次性购买私域权益"、资金直收站点，**归入交易型**。只有**平台自有业务**（AI 用量、存储、席位、模块功能、小程序 SaaS 服务费）才走"平台积分 + 统一 BillingPlan"。建议在代码层用 `BillingPlan.scope + chargeModel` 字段做**硬隔离**。

## 14. 统一 BillingPlan 模型设计

**建议新增 model（不改造现有表，避免破坏存量）**：

```
model BillingPlan {
  id            Int
  code          String   @unique          // 对齐 EntitlementPlan.code / ModulePricing.code
  name          String
  scope         String                    // PLATFORM_MINIPROGRAM | MINIPROGRAM_SITE | ORG
  ownerKey      String                    // 统一归属键：siteId | orgUserId | miniProgramCode
  chargeModel   String                    // SUBSCRIPTION | METERED | ONE_TIME
  period        String?                   // MONTHLY | YEARLY（空=一次性）
  priceCents    Int                       // 人民币价，对齐 ServicePackage.priceCents
  pointsPrice   Decimal?                  // 平台积分价（仅平台自有业务）
  metric        String?                   // access_count | order_count | storage_gb | api_call | token_in
  includedQuota Decimal?                  // 周期内包含量，复用 EntitlementQuota.limitCount 语义
  overagePrice  Decimal?                  // 超量单价，复用 ModulePricing.unitPriceAmount
  status        String                    // ACTIVE | ARCHIVED
}
model BillingSubscription {                // 含 currentPeriodStart/End、nextBillingAt、status、autoRenew
  ...
}
// 计量事实直接复用 usage_events（建议增 metric 列），不另建表
```

**设计理由（均有代码依据）**：

- `EntitlementPlan` 只有 `priceMonthly`（`schema:11418`），必须新增 `period: MONTHLY|YEARLY` 与年付价。
- `BillingRule.metric` 现为 `token_in|token_out|call|byte|page`（`billing-rule.service.ts:98-122`），新增 `access_count/order_count/storage_gb` 即可复用其 PLAN>ORG>PLATFORM 覆盖逻辑。
- 一次性模式直接复用 `ServicePackageOrder`（`schema:12701` 注释明确"一次性签约交付，不参与周期/到期管理"）的下单即 PAID + 快照 + 交付状态机思路，不塞进订阅表。
- 周期/续费可复用 `OrgEntitlement.startedAt/expiresAt`（`schema:11446`）。

## 15. 四种计费模式的实现映射与计量埋点

| 用户诉求的计费模式 | 映射实现 | 计量埋点位置 | 复用底座 |
|---|---|---|---|
| **按月订阅** | `BillingPlan.period=MONTHLY` + `BillingSubscription.monthly` | 订阅创建时写账单；`EntitlementUsage.period='YYYY-MM'` 计周期用量 | `EntitlementPlan.priceMonthly`、`OrgEntitlement` |
| **按年订阅** | `BillingPlan.period=YEARLY` + 年付价 | 订阅创建一次性扣年费，按周期分摊权益 | 新增 `priceYearly`（现有缺口） |
| **按访问次数** | `metric=access_count` | **API 网关/中间件层**：在 `canonicalPath` 之后按 `miniProgramCode + route` 映射写 `usage_events{billed:0}`，出账时聚合。范式参考 `featureGateMiddleware`（`app.ts:312`）与 `AiGateway.meter()`（`ai-gateway.ts:112`） | `BillingRule.metric=call`、`UsageEvent` |
| **按形成订单数** | `metric=order_count` | **订单创建事务内**：`BrandOrder/CardShopOrder/OnsiteOrder/DigitalHumanOrder/KnowledgePayOrder` 创建/支付成功时写 `usage_events{code:'order_count', refType:'order', refId:orderNo}`（目前 `order_count` 仅是 BI 统计，需新增埋点） | `UsageEvent`、`BillingRuleService.resolve()` |
| （存储 GB·天） | `metric=storage_gb` | 日批快照（专题一） | `PointsBillingService`、`module_pricing(asset_storage)` |

**埋点原则**：

1. **先观测后扣费**：所有计量写 `usage_events{billed:0}`，出账层聚合成账单时再置 `billed:1` 并扣分。
2. **一条 UsageEvent 只走一条扣费路径**（`billing-rule.service.ts:85-86` 已注明），AI 类统一走 `AiEvalService.chargeByUsage()`，避免 `PointsService.charge()` 与 `BillingRuleService` 双重扣分。
3. **按访问次数不计入交易型订单**：`access_count` 只针对平台自有 SaaS 服务（如"AI 客服坐席访问次数""模块功能访问次数"），不能对 brand/card-shop 的商品下单接口计费——那是交易本身，不是 SaaS 使用费。
4. **功能开关与额度分开**：`featureGateMiddleware` 目前只判断 open/closed（`feature-gate.middleware.ts:16-33`），无额度概念；额度由 `EntitlementService.check/require` 承担（需接入业务调用），二者职责清晰不要混。

## 16. 优化后每个能力的归属层与服务

1. **新增小程序**：先评估能否在 brand/card-shop 内加场景；确需新建必须基于 `@mini/core`，只写 `config.js`+`api.js`+页面；后端不新建 `*Member/*Order` 表族与 issuer，复用 `CustomerIdentity`/`Order` 骨架；注册 `registerXxxPublic` 时注释写明 issuer/过滤键。

3. **新增客服入口**：下发 `deskSiteKey/deskEmbedUrl` 走 `/embed/service-desk`，禁止新建会话表。

### 18.2 五条不可逾越的红线

1. **令牌物理隔离**：C 端令牌绝不进 `/enterprise/**`；派生密钥按 issuer 隔离，唯一算法。
2. **顾客态双条件过滤**：任何 C 端读写必须 `siteId|shopId + customerId/memberId/staffId` 双条件，查单接口独立限流。
3. **网络出口唯一**：出站 HTTP/SSE 经 `transport.ts`，前端经 `api/http.ts`+`endpoint.ts`，架构脚本强制。
4. **字节出口唯一 + 落账**：所有数字化内容字节经 `StorageService` + `SystemAssetService` 台账，禁止本地磁盘持久化用户文件、禁止 AIPDD 中转。
5. **资金归属隔离**：交易型订单资金直收店主的，不进平台积分；平台自有业务（存储/AI/订阅）才走 `Points`。计量事实 `usage_events` 一条只扣一次。

# 第六部分　平台级应用互联与故障隔离

> 本部分回应一个更高的架构诉求：**功能集约性 + 相互可调用 + 整体体验提升**。核心原则是——ERP、SCRM、电商、素材工具这些**平台级应用要相互对接，但又要相互隔离；任何一个出问题都不能拖垮其他服务；同一个应用要能服务多渠道、多场景，而不是绑定单一小程序**。
> 结论先行：这些能力**大部分已经存在**，真正的差距在"平台级抽象"与"跨应用集成范式"，而不是从零造轮子。尤其 SCRM 已有一套教科书级的隔离样板，可直接推广到 ERP 与素材工具。

## 19. 核心原则：相互对接、相互隔离、多渠道复用

### 19.1 三条设计原则（基于代码事实校准）

| 原则 | 落地含义 | 代码依据 / 现状 |
|---|---|---|
| **相互对接** | 应用间通过"端口 + 事件"协作，而不是彼此 import service 或直写对方表 | 已有 `commerce-core/scrm-port.ts`：电商侧定义 `ScrmBridge` 接口、SCRM 侧 `WecomScrmBridge implements`、DI 在 `services.ts:1527` 装配，两边互不 import |
| **相互隔离** | 被调用方故障/关闭不阻断调用方主链路；有超时、熔断、退避、幂等、补偿 | `SCRM_OUTBOX_POLICY`（3s 超时 / 5 次熔断 / 10 分钟冷却 / 指数退避）；`enqueue()` 整段 try-catch，"写不进 outbox 也绝不回滚订单" |
| **多渠道复用** | 一个平台级应用实例服务 N 个店铺/渠道；归属键用组织 `(orgType,orgUserId)`，渠道用关联表表达而非隔离边界 | SCRM 26 张表全为 `(orgType,orgUserId)`、无 `shopId`；`ownerUserId` 桥接一个企微主体下多店铺；ERP 同为组织级但**缺渠道键** |

### 19.2 物理隔离是前提：当前是单进程

必须诚实指出一个代码事实：`backend/src/main.ts:157-158` 只有**一个** `createApp(services)` + `serve()`，`ErpService`/`ScrmService`/电商服务共享同一个 `PrismaService`（`http/services.ts:2927` 等）。

**这意味着**：在当前架构下"ERP 服务挂掉"并不是一种独立故障——它等价于数据库故障或整个后端挂掉。因此"一个有问题不影响其他"要分两层实现：

- **逻辑隔离（本期可做）**：端口解耦 + Outbox 旁路 + 超时/熔断/降级，保证"某个应用的功能异常"不冒泡成别的应用故障。这是 SCRM 样板已做到的。
- **物理隔离（中期目标）**：把 ERP、SCRM、素材生成这些重应用拆为独立进程/独立 DB 连接池（ERP 尤其应独立从库），否则进程级崩溃无法隔离。建议 P1 至少做到"独立连接池 + 只读从库"，P2 视规模拆服务。

### 19.3 四类应用现状判定

| 应用 | 现状 | 是否平台级 | 与电商/其他对接 | 隔离能力 |
|---|---|---|---|---|
| **SCRM + 营销工具** | 8 大能力完整（客户/标签/活码/群发/SOP/素材/合规/统计） | ✅ 组织级，已是平台级 | 品牌商城/健康/上门/CRM 四域接入；小程序端 C 侧几乎不直接调用 | ✅ 教科书级（端口+Outbox+熔断） |
| **ERP** | 15 张表、采购→入库→应付→付款完整单据流 | ⚠️ 组织级但**无渠道维度**，是"后台孤岛" | ❌ 与电商/SCRM/电商 PDP **零代码引用** | ⚠️ 仅事件 fire-and-forget + Webhook Outbox；无熔断/无自动重试 |
| **电商（多店铺）** | brand/card-shop/onsite/health 各有商品/库存表 | 多店铺 `shopId` | 电商→SCRM 已有样板；电商→ERP **无** | ✅ 与 ERP 天然隔离（因未对接） |
| **主图/详情图工具（PDP）** | ecom/domestic 两套同构 AI 出图工具 | ❌ 后台孤岛，四张表、仅 `userId` | ❌ 与商品表、小程序、国际站**零对接** | ✅ 单张失败不回滚、登记失败只告警 |

## 20. 现成样板：SCRM 的"端口 + Outbox"隔离机制

这是全仓唯一实现完整的松耦合范式，**应作为 ERP、素材工具对接的统一模板**，务必先读懂再改造。

### 20.1 结构：端口在调用方、实现在被调用方、装配在 http 层

```
   电商/健康/上门（调用方）              SCRM（被调用方）
┌────────────────────────┐        ┌──────────────────────────┐
│ 定义 ScrmBridge 接口    │        │ WecomScrmBridge implements│
│ (commerce-core/scrm-port.ts)│   │ (wecom-scrm/scrm-bridge.ts)│
│ noopScrmBridge 降级实现  │        │ 内部写 scrm_* 表          │
└───────────┬────────────┘        └────────────┬─────────────┘
            │  互不 import                      │
            └──────────────┬─────────────────────┘
                   装配于 http/services.ts:1527
                   new BrandScrmService(prisma, new WecomScrmBridge(prisma))
```

三要素（代码证据）：
- **接口定义**：`ScrmBridge`（`scrm-port.ts:91-108`）：`status/matchContact/appendTimeline/pushFields/readProfiles`；契约注明"商城侧只依赖这个接口，永不调用企业微信、永不直写 `scrm_*` 表"（文件头 `:3-9`）。
- **降级实现**：`noopScrmBridge`（`:111-122`），未接入时空转返回安全值；单测默认注入 `noop`，免装配。
- **唯一写入口**：`WecomScrmBridge`（`scrm-bridge.ts:17`），所有写入带 `(orgType,orgUserId)` 过滤（`:64`）。

### 20.2 隔离机制：Outbox 旁路 + 全套容错策略

**Outbox 表**：`BrandScrmOutbox` / `brand_scrm_outbox`（`schema.prisma:14340-14364`）——`dedupeKey @unique` 幂等、`payloadJson` 存"快照时刻事实"（补发不回读现值）、`status: PENDING|SENT|SKIPPED|DEAD`、`attempts/nextAt/lastError/sentAt`。配套 `BrandScrmBinding`（`(shopId,customerId) → contactId`）做渠道身份映射。

**主链路不阻断**（`brand.scrm.service.ts:53-76`）：`emitScrm()` 只调 `enqueue()`；`enqueue()` 整段 try-catch，注释明写"外发是旁路：写不进 outbox 也绝不回滚订单/退款"；`scrmEnabled=false` 直接 return；真正投递由 `brand.scheduler.ts:67` 的 `drain()` 异步执行。单测 `brand.scrm.spec.ts:130` 验证"写 outbox 抛错也不冒泡到交易主链路"。

**容错策略集中在 `SCRM_OUTBOX_POLICY`（`scrm-port.ts:44-59`）**：

| 策略 | 值 | 代码位置 |
|---|---|---|
| 超时 | `timeoutMs=3000`（`Promise.race`） | `withBridgeTimeout`，`:252-269` |
| 熔断 | 连续失败 5 次 / 打开 10 分钟 | `circuitShouldOpen`，`:245-250`；`drainOrg`，`:178-185` |
| 重试退避 | 60s 起指数放大，上限 6h；5 次落 `DEAD` | `nextRetryAt`，`:236-243` |
| 不可用不计数 | `FEATURE_CLOSED` 等整轮顺延、**不消耗 attempts** | `planOutboxDrain`，`:211-217`（注释："平台管理员关一次 SCRM 就会把所有历史事件打成 DEAD"） |
| 水位/淘汰 | 每组织每轮 50 条、积压 2000、超 30 天淘汰为 `SKIPPED` | `:187-216` |
| 幂等 | `scrmDedupeKey(biz,kind,recordKey)` + `createMany(skipDuplicates)` | `:125-131`、`:106` |
| 隐私 | `scrmMobileHash` HMAC-SHA256（上下文 `scrm-match`），手机号明文不落库 | `:137-143` |
| 运维 | `retryNow/replaySkipped/toggle`（关闭时保留待发事件） | `brand.scrm.service.ts:458-508` |

> 这个样板的价值在于：**它把"对接"和"隔离"同时做到了**——电商能享受 SCRM 的客户运营能力，但 SCRM 关闭、超时、限流、故障都不会影响下单退款。这正是用户要的原则，已经落地了一处，缺的是推广。

## 21. ERP / SCRM / 主图工具 的平台化设计与改造

### 21.1 ERP：从"后台孤岛"到"平台级经营底座"

**现状事实**（`backend/src/erp/`）：`ErpService`（3332 行）+ `ErpController`，能力完整（类目/商品/SKU/仓库/库存流水/领用/供应商/采购/入库/应收/应付/费用/税率/价格策略/AI 经营评估）。15 个 `Erp*` model 全部以 `(orgType,orgUserId)` 归属（`schema.prisma:9247-9569`），**无 `shopId/siteId`**。当前消费者只有 4 类：机制层 CSV 导入导出、growth 自动补货、project 成本/应收、AI Agent 只读查库存工具（`erp_check_stock`）。

**必须正视的三个缺口**：
1. **与电商零对接**：brand/card-shop/onsite/health/PDP 对 ERP 表和服务**零引用**，各自有独立的商品/SKU/库存表（如 `brandProductSku`，`brand.order.service.ts:597 deductStock`）。电商有店铺维度、ERP 没有——这是两侧无法对齐的根本原因。
2. **无渠道维度**：契约 `packages/contracts/src/erp.ts` 里 `shop|site|channel|store` 零命中；前端 `/erp` 无门店切换。不支持"一个 ERP 实例服务多店铺/多渠道"。
3. **隔离能力不足**：`emit()` 是 fire-and-forget（`erp.service.ts:127-129`）；全库无熔断、`ErpOutbox` 不存在、Webhook `nextAt` 无自动扫描调度器（失败只能人工 `replay()`）；`agent` 查库存桥无超时。反向耦合：`decideReceipt` 事务内同步写 `pjCostItem`（`:2020-2055`），ERP 与 project 在同一 DB 事务，一损俱损。

**改造方案（照搬 SCRM 样板）**：

| 动作 | 具体做法 | 依据/收益 |
|---|---|---|
| **补渠道维度** | 二选一：A（推荐平台级主数据）商品/SKU/仓库提升为平台级，新增 `erp_channel_binding`（`shopId/siteId/channel → variantId` + 店铺售价/库存策略）；B（保留组织级）`ErpStock/ErpVariant` 加 `shopId` 并扩唯一键 | 现状无渠道键，必须改 schema+契约+service 三处；A 才能"一个 ERP 服务 N 个小程序" |
| **抽 ErpPort** | 定义 `ErpPort`（`reserveStock/confirmOrder/releaseStock/listStock`）+ `NoopErpPort`；电商只依赖端口，禁止 `import ErpService` | 复用 `ScrmBridge` 模式；growth/project 的 `prisma.erp*` 直写收敛到 ERP 服务 |
| **跨边界写改 Outbox** | 下单扣库存走 `erp_outbox` + 领域事件；支付成功→出库/生成应收订阅 `order.paid`；库存变更→各渠道同步用现有 `erp.stock.moved` + Webhook Outbox | 主链路不依赖 ERP；失败可重放；SAP 类场景最终一致 |
| **同步查库存降级** | 展示用同步 API + ≤1s 超时 + 本地缓存兜底，失败降级"库存待确认"而非阻断 | 参考 `withBridgeTimeout`；用户要即时反馈但不应被 ERP 拖垮 |
| **物理隔离** | ERP 抽独立进程/独立 DB 连接池（至少只读从库） | 单进程下 ERP 崩溃≠独立故障（19.2） |
| **补齐容错** | 超时/指数退避/熔断/幂等（`sourceType+sourceId`，ERP 已有 `syncPurchaseOrderPayable:2081-2088` 写法）/死信对账/定时对账（ERP 库存 vs 电商 SKU） | 参照 `SCRM_OUTBOX_POLICY`；当前全缺 |

**保留不动**：采购→入库→应付→付款状态机、`applyMove` 库存流水、`orgKey()/requireOwnedRow()` 组织隔离、`requireErpRole` 职能权限、`chainNo` 幂等链号——这些是成熟资产。

> 未实现的销售订单/发货/物流、MRP、价格策略实际计算、`locked/inTransit` 写入——如果要做电商深度集成，这些是下一步功能缺口，应在方案外单独立项，不要混进架构改造。

### 21.2 SCRM / 营销工具：从"品牌商城专属"提升为"平台级多渠道"

**现状事实**：26 个 `Scrm*` model 全部 `(orgType,orgUserId)` 归属、无 `shopId/siteId`——**数据模型已经是平台级**。`corpId` 不是租户键，唯一键是 `(orgType,orgUserId)`；`shopId` 只存在于电商侧。二者通过 `ownerUserId` 桥接：`BrandShop.ownerUserId` → `BrandScrmOutbox` 同时存 `shopId` + `ownerUserId` → `drain()` 按 owner 分组 → `drainOrg(ownerUserId)` 查 `scrmCorp` 拿 corpId。**一个企微主体/组织天然服务该账号下多个店铺**。

**已接入渠道**：品牌商城（最完整）、健康（`health_scrm_links` + `HealthScrmService` 调 SOP）、上门（绑定 `scrmCodeId` 活码）、CRM（线索晋升回写 `crmCustomerId`）。**未接入**：card-shop、digital-human、knowledge-pay、公众号、用户版小程序（C 端不直接调 SCRM，经活码被 SCRM 接管）。

**三个改造点**：

1. **把 Outbox 提升为平台能力**：现状 `brand_scrm_outbox`（电商）与 `health_scrm_events`（健康）两套独立实现，且健康版**无超时/熔断/指数退避**（`mark()` 只简单 attempts++，`:351-361`）。建议抽象统一 `scrm_event_outbox`（对齐 brand 版字段：`ownerUserId + sourceChannel + dedupeKey + payloadJson + attempts/nextAt`），统一 scheduler；各域只保留自己的映射表（`brandScrmBinding`/`healthScrmContactRef`）与事件翻译。新增渠道零成本接入。
2. **建立跨渠道客户主数据**：现状 `ScrmContact.unionId` 是普通字段、无唯一约束，各域自建映射（`brandScrmBinding`、`healthScrmContactRef`）——没有"一个 unionId = 一个客户，跨商城/健康/上门共用 contactId"的平台主数据。建议在 SCRM 域加 `(orgType,orgUserId,unionId)` 唯一索引 + 合并/认领接口；`ScrmBridge.matchContact` 已是 unionId 优先（`brand.scrm.service.ts:293-361`），是天然接入点。
3. **营销工具对齐租户口径并打通**：`MarketingQrCode` 归属 `userId`（`schema.prisma:4714`）、`MarketingSurvey` 归属 `createdBy`——与 SCRM 组织口径割裂。建议改为/增加 `(orgType,orgUserId)`，建立 `MarketingQrCode ↔ ScrmCode`、`MarketingSurvey 回收 ↔ ScrmContact` 关联，让活码扫码/问卷留资进入 SCRM 时间线（`ScrmTimelineEvent`），真正实现"多场景融合"。AI 营销技能（`MktService`）已按 `HrmOrg` 组织维度，保持即可。

**保持不动**：8 大 SCRM capability service（通用且已复用）、`ScrmScopeService`/`orgKey()` 租户口径、端口隔离与"不阻断主链路"的全部策略。

### 21.3 主图/详情图工具：从"内容孤岛"到"平台级素材工厂"

**现状事实**（`backend/src/ecom-pdp/`、`domestic-pdp/`）：这是两个**同构的 AI 商品图工具**（不是图片编辑画布）——`create()` 建包 → `plan()` 用文本模型生成图面文案与出图提示词 → `updateAsset()` 逐张改词 → `generate()` 调 `ContentMediaService.editImage/generateImage` 出图 → `refreshStatus()` 汇总状态。ecom 面向跨境（Amazon/TikTok、`market/language`、英文文案），domestic 面向国内（淘宝/天猫、《广告法》合规、中文文案、750px 移动端）。两者注入完全相同的底座（`ContentModelSettingService` + `ContentMediaService`，`services.ts:1162-1174`），仅 prompt 知识层不同。

**四个关键缺口**：
1. **四张同构表、逻辑逐行复制**：`EcomPdpPack/Asset`、`DomesticPdpPack/Asset`（`schema.prisma:7796-7905`），归属只有 `userId`。
2. **无渠道对接**：仅被 `/enterprise/content` 两个 Tab 调用（`content/page.tsx:43-45`）；品牌商城小程序、卡密商城、国际站/GEO 站、其他小程序**均无调用点**——渠道商品表各存各的 URL（`BrandProduct.coverImage/images`、`CardShopProduct.coverImage/images`），无映射表、无跨渠道发布动作，复用只能人工复制 URL。
3. **素材未沉淀到统一资产锚点**：参考图走 `/content/uploads` → AIPDD 平台 OSS（`assets/enterprise/{userId}/inputs`），不写本站 `DigitalAssetEntry`；生成图经 `ContentAssetService.tryRegister()` 虽顺带登记了 `DigitalAssetEntry`（AIPDD 分支），但 `*PdpAsset.assetId` 是字符串、**与 `DigitalAssetEntry.id` 无结构关联**。
4. **未计量**：调 `generateText/generateImage` 未传 `meta`/`JobControl`，不进 `recordAiUsage`，成本报表看不到。

**已有的降级设计（改造时必须保留）**：`meta()` 只提示不抛错；`generate()` 的 catch 不抛出，只写 `asset.status='failed'` + `error`；`refreshStatus()` 让其他已成功图保持 `done/partial`；数字资产登记失败只写 `assetNote`，图仍可用（`asset-registry.service.ts:127-146`）。**商品发布链路完全不引用 PDP**，模型不可用只影响 PDP 自己的图包——这正是"互不影响"的雏形。

**改造方案**：

| 动作 | 具体做法 | 依据/收益 |
|---|---|---|
| **四表归一** | 抽象 `PdpPack/PdpAsset`（或 `MediaGenerationJob/MediaAsset`），加 `channel` 字段（`cross-border/domestic/brand-mall/card-shop/overseas`），`market/platform/tone/language` 移入 `input`；两个 prompt 文件保留为**策略适配器** | 消除逐行重复；新增渠道不改 Service |
| **统一资产锚点** | `PdpAsset` 关联 `DigitalAssetEntry.id` + providerAssetId 双字段；参考图上传改走 `/content/digital-assets/upload`（本站 OSS） | 与第三部分"系统资产"打通，一处存储、多渠道复用、统一计费 |
| **新增渠道发布适配层** | 新建"应用图片到商品"服务，把选中的图 URL 写入 `BrandProduct.coverImage/images`、`CardShopProduct`，以及国际站/GEO 站点素材位——**不改商品服务内部** | 当前零代码，必须新建；适配层独立保证互不影响 |
| **异步出图 + 回填** | 发布接口只写商品基础字段与已有 URL，**绝不 await 生图**；生成成功后回调/轮询回填 URL；失败保留旧图、记录 `asset.error`，不回滚商品行 | 复用 `content-job.service.ts` / worker-pool；生成失败不拖垮发布 |
| **渠道级开关 + 计量** | 每渠道独立 feature flag；传 `meta:{module:'pdp',operation:'plan/generate'}` 接入 `recordAiUsage` | 关某渠道图片生成不影响其他渠道商品读写；成本可见 |
| **编辑器升级** | 从数字资产库选参考图、一键套用同款风格到新渠道、生成结果一键投递各渠道；明确区分"生成失败"与"资产登记失败" | 现有 Tab 只有"改词+生成+看原图"（`ecom-pdp-tab.tsx:155-297`），无发布/下载/选图入口 |

## 22. 集成契约、整体体验与补充路线图

### 22.1 统一的集成契约：所有跨应用协作都走同一套范式

把 SCRM 样板抽象为平台级 `IntegrationPort + EventOutbox`，ERP/SCRM/电商/PDP 一律遵守：

```
【依赖方向硬规则】
调用方定义 Port 接口 → http/services.ts 装配实现 → 被调用方 implements
✗ 禁止跨应用 import 对方 Service
✗ 禁止跨应用直写对方表（如非 ERP 域写 prisma.erp*、非 SCRM 域写 prisma.scrm*）

【协作方式选择矩阵】
┌────────────────────────┬──────────────────────────────────────┐
│ 场景                    │ 机制                                  │
├────────────────────────┼──────────────────────────────────────┤
│ 即时展示（查库存/查客户）│ 同步 Port + 短超时 + 本地缓存/降级值    │
│ 跨应用写（扣库存/发SOP） │ EventOutbox + 领域事件，异步消费可重放 │
│ 状态变更通知            │ 领域事件 + Webhook Outbox（已有底座）  │
│ 应用内强一致（采购→应付）│ 保持库内事务（已有，幂等）             │
│ 失败恢复                │ 指数退避 + 死信表 + 定时对账 + 手动replay│
└────────────────────────┴──────────────────────────────────────┘

【事件目录建议】
order.paid → ERP 出库/应收 + SCRM 客户时间线
erp.stock.moved → 各渠道库存同步（已有 emit，补消费者与自动 drain）
pdp.asset.ready → 商品主图回填 + 数字资产计费
scrm.tag.applied → 营销自动化（SOP 触发）
```

### 22.2 故障隔离矩阵（用户原则的可验收标准）

| 故障场景 | 期望表现 | 依托机制 | 现状 |
|---|---|---|---|
| SCRM 关闭/企微接口超时 | 商城下单退款正常，事件顺延不 DEAD | Outbox + `unavailable 不计数` + 熔断 | ✅ 已实现 |
| ERP 不可用 | 电商按本地 SKU 库存继续下单，标记"待 ERP 确认"，恢复后对账 | ErpPort + Noop 降级 + Outbox + 对账 | ❌ 需建设（当前零对接） |
| 图像模型不可用 | 商品发布不受影响；图包标 `failed`，其他图保持 `done` | 异步出图 + 回填 + 单张失败不回滚 | ✅ 雏形已有，需平台化 |
| 某渠道关停 | 其他渠道读写照常，历史事件不清账 | 渠道级 feature flag + Outbox 顺延 | ⚠️ SCRM 有，PDP 需补 |
| 共享 DB 抖动 | 主链路不被旁路写入拖垮 | 独立 outbox 存储/进程内队列（可选，P2） | ⚠️ 当前 outbox 是同库 await |

### 22.3 整体体验提升（功能集约 + 相互可调用的最终目标）

1. **一次配置、多渠道生效**：在组织级配置企微主体、ERP 连接、图像模型槽位，所有小程序与渠道共享，不再每店配一遍（依托组织归属键 + DI 装配）。
2. **一次生成、多渠道复用**：主图工具产出的图进入 `DigitalAssetEntry`（系统资产），品牌商城小程序、卡密商城、国际站/GEO 站按 `channel` 一键投递，不再人工复制 URL（依托统一资产锚点 + 渠道发布适配层）。
3. **一个客户、全渠道识别**：unionId 归并为平台级客户主数据，商城/健康/上门的顾客在 SCRM 指向同一 contactId，营销触达不重复、不遗漏（依托 unionId 唯一索引 + 合并接口）。
4. **一次集成、处处可用**：ERP 主数据通过 ErpPort 服务所有渠道；新渠道接入只写映射与事件翻译，零改核心（依托端口 + Outbox 平台化）。
5. **成本统一可见**：AI 出图/存储/订阅统一进 `usage_events`，与第四部分计费闭环合流——功能集约的最终收益是"能力可复用 + 成本可计量 + 体验一致"。

### 22.4 应用互联专项路线图（并入第五部分第 17 节统一排期）

| 优先级 | 动作 | 依赖 | 收益 | 风险 |
|---|---|---|---|---|
| **P1-A** | SCRM Outbox 平台化：统一 `scrm_event_outbox` + scheduler，健康域补齐超时/熔断/退避 | 无（照搬 brand 样板） | 新增渠道零成本，隔离能力一致 | 低 |
| **P1-B** | SCRM 跨渠道客户主数据：unionId 唯一索引 + 合并/认领接口 | P1-A | 一个客户全渠道识别 | 中：需定合并冲突策略 |
| **P1-C** | PDP 四表归一 + 资产锚点（关联 `DigitalAssetEntry`）+ 参考图走本站 OSS | 第三部分 P0-5 | 素材一处存储、多渠道复用 | 中 |
| **P1-D** | PDP 渠道发布适配层 + 异步出图回填 + 渠道级开关 + 计量 | P1-C | 主图服务多渠道，生成不拖垮发布 | 中 |
| **P1-E** | ERP 抽 `ErpPort` + 电商下单扣库存改 Outbox + 同步查库存降级 | 无（照搬 SCRM 样板） | 电商与 ERP 松耦合对接 | 中：资金/库存一致性需对账 |
| **P2-A** | ERP 补渠道维度（`erp_channel_binding`）+ 契约/前端门店切换 | P1-E | 一个 ERP 服务多渠道 | 中高：schema 变更 |
| **P2-B** | ERP 独立连接池/只读从库 → 独立进程；补熔断/自动 drain/对账调度器 | P1-E | 物理隔离达成 | 高 |
| **P2-C** | 营销工具对齐组织口径 + 活码/问卷进 SCRM 时间线 | P1-A/B | 多场景融合 | 低 |
| **P2-D** | 统一 `IntegrationPort + EventOutbox` 抽象与架构守护规则 | P1-A~E | 跨应用协作范式统一 | 中 |

**本部分红线（接第五部分 18.2）**：

6. **跨应用只经端口与事件**：禁止 `import` 对方 Service、禁止直写对方表；端口定义在调用方、实现在被调用方、装配在 http 层。
7. **旁路不阻断主链路**：任何跨应用外发（SCRM/ERP/PDP/通知）必须 Outbox 旁路 + try-catch，失败只改事件状态，不回滚主业务；必须有超时与降级值。
8. **不可用不消耗重试额度**：应用被关闭/未配置时整轮顺延、不计 attempts，避免一次关停把历史事件打成 DEAD（SCRM 已有的重要经验）。
