# 双运行时接入（WorkBuddy + Codex）与工作区选择方案

> 版本：v1.0 ｜ 日期：2026-11-13 ｜ 状态：**两条链路均已真机跑通一轮端到端，可以进实施**
> 本文是三件事的合体：① 把可对接的执行体从"只有 WorkBuddy"收口为 **WorkBuddy + Codex（ChatGPT/Codex 桌面客户端）**；② BotBuddy 客户端加**两个「连通」按钮**，点一下即连通并把连通状态上报平台；③ 平台下发的指令**可以携带工作区**，且工作区列表能由客户端枚举上来供用户选。
> 关系：本文件是《Agent-Bot方案》v2 阶段（WorkBuddy + Codex 双运行时）的修订记录，v3（2026-11-14）起执行体已收敛为 BotBuddy 客户端内置 Agent，WorkBuddy/Codex 双运行时口径仅作追溯。
> 本文所有结论都带实测证据（§二台账），未验证的命题一律标注"未判定"，不写成既定事实。

## 一、结论先行

| 问题 | 答案 | 关键证据 |
| --- | --- | --- |
| Codex（ChatGPT 客户端）能不能对接？ | **能，而且比 WorkBuddy 省事**：ACP 桥一条 `prompt` 15.7s 跑完并真实落盘，登录态开箱可用，无激活断点 | C1/C2/C7 |
| exe 能不能各加一个「连通」按钮、点一下连通并上报？ | **能**。两家各自的"连通"都能收敛成固定动作序列（发现 → 拉起/握手 → 自检 → 状态落连接器），状态随心跳 `caps.connectors` 上报，1 个心跳周期（5s）内平台可见 | §四 |
| 平台落下的指令能不能选工作区？ | **能，但两家机制不同，必须两套落法**：Codex 是**会话级**（`session/new` 的 `cwd` 真生效，一个常驻进程可跑多工作区）；WorkBuddy 是**进程级**（`session/new` 的 `cwd` 被忽略，工作区在拉起 sidecar 时钉死）→ WorkBuddy 侧需要"**工作区运行时池**"（每个工作区一个实例，未命中现起 1.5s） | C2 / W2 |
| exe 能不能拿到工作区列表？ | **能**。Codex 直接读 `~/.codex/config.toml` 的 `[projects."<绝对路径>"]`（带 `trust_level`）+ rollout 首行 `session_meta.cwd`，本机枚举出 50 个去重绝对路径、其中 36 个目录仍存在；WorkBuddy 走**在线会话注册表的 `cwd`**（精确）+ `~/WorkBuddy/*` 默认根 + `projects/` sanitize 目录名反解（本机 2 条唯一命中，未命中全是探针自删的目录） | C5/C6/W5 |
| 新发现的第二个无人值守断点？ | **Codex 的权限询问**。`read-only` 档下写文件会抛 `session/request_permission`，客户端**不应答就整轮挂死**；实测必须就地按策略选 `optionId` 才能跑完 | C3 |
| 还堵在哪？ | 只剩 WorkBuddy 托管运行时的**激活**：复用启动 `--session-id` 的会话能建，**另开新会话直接 `-32000 Authentication required`（`data.category=auth`）**——这就是之前 `stopReason=refusal` 的机器可读源头 | W3 |

一句话：**Codex 侧现在就能上生产；WorkBuddy 侧照旧等一次激活。** 两家差异集中在"工作区能不能会话级切换"和"权限谁来批"，这两点决定了本方案的抽象边界（连接器 + 运行时池 + 权限策略）。

## 三、接入范围收口：两家，其余降级为兼容性事实

1. **产品承诺的执行体只有两个**：`workbuddy` 与 `codex`。契约层 `agent` 枚举收口为这两值。
2. 之前对 Claude Code / OpenClaw 的 stdio ACP 兼容性验证**保留为方言选型依据**（证明"ACP over stdio + ACP over HTTP 双transport"这套客户端代码站得住），**不写进用户可见的对接清单**，避免背书的锅。
3. 菜单与文案：现在接的是两家，「Workbuddy 主机」这个名字会误导（用户会以为只管 WorkBuddy）。**建议菜单名改中性**（如「Agent 主机」），路由 `/workbuddy/hosts` 与已交付页面**保持不变**，只动文案与 i18n 键；客户端产品名 `BotBuddy` 本就是中性的，不改。此项影响面小、可回退，等一句话确认就动。

## 四、两个「连通」按钮：连接器抽象

### 4.1 为什么是"按钮"而不是"自动"

现状是单连接器（只有 WorkBuddy），连通性由心跳顺带体现。加第二家后必须显式化：

- 用户机器上可能只有 Codex、只有 WorkBuddy、或两个都有；
- 一键连通要有**可点击的失败入口**（现在"检测 WorkBuddy 链接"按钮已被验收条款固化，两家就顺理成章扩成两个按钮）；
- 状态上报要区分"没装 / 装了没连 / 连了但只能明示注入 / 连了且可静默派活"，这四档混在一个"在线"里会误导调度。

### 4.2 连接器状态机（7 态）

```
ABSENT ──发现安装──▶ DISCOVERED ──点击连通──▶ CONNECTING ──自检通过──▶ CONNECTED
  ▲                     │                        │                        │
  │                     │                 自检失败│                        │能力降级(隔离不成立/沙箱不可用)
  └──卸载/移除──────────┘                        ▼                        ▼
                                            FAILED(reason)         DEGRADED(仅明示注入)
CONNECTING/CONNECTED ──错误含 category=auth / refusal──▶ 桌面 sidecar 可挂靠？
                                                          ├─ 是 → DEGRADED(ATTACH_ONLY，profile=attach)
                                                          └─ 否 → NEEDS_ACTIVATION ──用户完成一次激活──▶ CONNECTING
任意态 ──用户在 exe 里断开──▶ DISABLED（DISABLED 的主机不领任务）
```

| 状态 | 平台侧显示 | 可否领 `silent` 任务 |
| --- | --- | --- |
| ABSENT | 未安装 | 否 |
| DISCOVERED | 已发现，未连通 | 否 |
| CONNECTING | 连通中 | 否 |
| CONNECTED | 在线·可静默派活 | 是 |
| DEGRADED | 在线·仅明示注入 | 否（只接 `into-current`/手工确认） |
| NEEDS_ACTIVATION | 在线·需激活 | 否 |
| FAILED / DISABLED | 失败（带原因）/ 已停用 | 否 |

### 4.3 点击「连通 WorkBuddy」的确定动作序列

1. 发现安装：`F:\Program Files\WorkBuddy\WorkBuddy.exe` + `resources\app.asar.unpacked\cli\bin\codebuddy`（探测，不硬编码版本）；
2. 拉起托管运行时（固定端口 + 稳定 `--session-id` + `--permission-mode` + `--tools` 白名单 + `--add-dir <默认工作区>`，两条必需 env，自建 Job Object）；
3. 就绪判定：注册文件命中 `sessionId` 为主判据（实测 1.5s），端口探活兜底；
4. `connect → initialize → session/new`，并做**会话归属自检**：返回的 `sessionId` 必须等于指定值，且 `projects/` 绑定目录必须等于期望工作区（W2 的教训：`cwd` 参数不可信，只能信 spawn）；
5. 激活探测：任何 `-32000 / category=auth` 或 `stopReason=refusal` → 先试 §5.7 的桌面挂靠：注册表 `~/.workbuddy/sessions/<pid>.json` 里有活跃会话（心跳 < 90s）且 `connect+initialize` 通过 → `DEGRADED` + `profile=attach` + `failReason=ATTACH_ONLY`（能干活、只能明示注入）；挂靠不可用才落 `NEEDS_ACTIVATION`；
6. 成功 → `CONNECTED`，把 `{profile, endpoint, pid, port, workspace, readyLatencyMs, authenticated, permissionMode, toolsWhitelist}` 写进连接器记录，随心跳上报。

### 4.4 点击「连通 Codex」的确定动作序列

1. 发现 `codex.exe`：按 `%LOCALAPPDATA%\OpenAI\Codex\bin\*\codex.exe` → MSIX 包 `app/resources/codex.exe` → PATH 顺序探测（C6：路径含内容哈希，绝不能写死）；
2. 登录态检查：`codex login status` 的文本结果作为 `authenticated` 判据（本机为 API key 已登录）；未登录 → `NEEDS_ACTIVATION` 并引导用户登录一次；
3. 握手：起 `codex-acp` 桥（**一期用随客户端自带的缓存副本**，不赌 `npx` 现拉，C10），`initialize → session/new(cwd=<默认工作区>)`，读回 `modes.currentModeId` 与 `configOptions`；
4. 沙箱可用性探测：跑一条无副作用命令验证 Windows 沙箱不报 `spawn setup refresh`（C9）。**本机实测沙箱拉不起来，因此策略档位按下表降级**（C11），不把不可用的 `auto` 档当默认：

   | 本机策略 | 会话 mode | 谁来做边界 | 实测 |
   | --- | --- | --- | --- |
   | `deny`（默认） | `read-only` | 权限闸门一律拒绝 | ✅ 只读问答正常，写操作 `cancelled` |
   | `allow-edits` | `read-only` | 权限闸门按工作区路径逐条裁决 | ✅ 区内落盘、区外拒绝（C11） |
   | `allow-all`（需本机再确认） | `full-access` | 不设边界（不发权限询问） | ✅ 直接写盘 |

   `auto` 档只在沙箱可用的机器上有意义，一期不用：它既不能落盘（沙箱起不来），又不能给边界（可写根含桥进程 cwd）。
5. 成功 → `CONNECTED`，上报 `{cliVersion, bridgeVersion, mode, permissionPolicy, workspace, spawnCwd, readyLatencyMs}`。

### 4.5 上报契约（心跳载荷扩展，零 schema 变更）

```jsonc
caps.connectors = {
  "workbuddy": { "state": "CONNECTED", "profile": "managed", "endpoint": "http://127.0.0.1:45873",
                 "pid": 34276, "port": 45873, "workspace": "E:\\work\\demo",
                 "authenticated": true, "permissionMode": "bypassPermissions",
                 "toolsWhitelist": ["Read","Write","Edit","Glob","Grep","MultiEdit"],
                 "readyLatencyMs": 1500, "lastStopReason": "end_turn",
                 "workspaces": ["E:\\work\\demo", "C:\\Users\\me\\WorkBuddy\\Claw"],
                 "failReason": null },
  "codex":     { "state": "CONNECTED", "cliVersion": "0.155.0-alpha.9.2", "bridgeVersion": "0.15.0",
                 "mode": "auto", "permissionPolicy": "allow-edits", "spawnCwd": "E:\\work\\demo",
                 "readyLatencyMs": 800, "lastStopReason": "end_turn",
                 "workspaces": [ /* 50 条候选里过滤后的 Top-N，带 exists/trust/isGit/lastUsedAt */ ],
                 "failReason": null }
}
```

- 仍走既有 `caps` 自由 JSON 列，**不加表、不加迁移**；
- **本期只保留最近一次快照**：平台每次心跳用新值整体覆盖 `caps`，界面读到的就是最后一次上报的状态与 `failReason`。§七 的"不加表、不加迁移"决定了本期**不落状态跳变台账**，因此"某连接器何时从 `CONNECTED` 掉到 `FAILED`"无法事后回溯——要回溯得单开一张审计表，届时明确迁移成本（列为二期待办）。要现场查原因，看当前 `failReason` + 客户端日志；
- `failReason` 必须是**机器可读枚举 + 一句人话**，实测已见的取值：`MISSING_ENV_ELECTRON_RUN_AS_NODE`、`BUNDLE_MODULE_NOT_FOUND`、`ACP_HEADER_MISSING(403)`、`AUTH_REQUIRED(-32000/category=auth)`、`MODEL_REFUSAL(stopReason=refusal)`、`SESSION_MISMATCH`、`WINDOWS_SANDBOX_UNAVAILABLE`、`CODEX_NOT_LOGGED_IN`、`BRIDGE_SPAWN_ENOENT`。

## 五、工作区：指令级可选，两家两种落法

### 5.1 契约新增（就四个字段）

```ts
// 指令下发时可选携带；不携带则用连接器的 defaultWorkspace
agent: 'workbuddy' | 'codex'            // 缺省 = 主机默认运行时
workspace: { id?: string; path?: string } // 二者必居其一；path 必须命中客户端白名单
mode?: 'read-only' | 'auto' | 'full-access' | 'bypassPermissions' | 'acceptEdits' | 'plan'
deliveryMode?: 'silent' | 'into-current' | 'probe'   // 沿用 v1.1 §5.7
```

回执与运行记录里回写**实际生效的工作区**（不是请求值），这是唯一能证明"没跑错目录"的凭据。

### 5.2 Codex：会话级，天然满足

实测 C2 证明 `session/new(cwd=WS)` 真生效，因此**一个常驻 ACP 桥进程就能按指令逐条切工作区**，无需进程池。落法：每条指令 → `session/new(cwd=workspace)` → `session/prompt` → 收 SSE → `session/close`（`sessionCapabilities.close` 实测存在）。

### 5.3 WorkBuddy：进程级，必须运行时池

实测 W2 证明 `session/new` 的 `cwd` 被忽略、工作区在 spawn 时钉死，因此客户端维护：

```
runtimePool: Map<workspacePath, { port, sessionId, child, pid, lastUsedAt, state }>
```

- 命中池 → 0ms 直接用；未命中 → 现起（实测 1.5s），端口与会话 id 按工作区派生，保证可复现；
- 池上限（建议 4）+ LRU 回收，回收即 `taskkill /T /F` 并等注册文件消失；
- **同一个工作区同一时刻只允许一条指令在跑**（串行队列按工作区分桶，不同工作区可并行）——这是把 v2.1 的"全局串行"松绑成"每工作区串行"的唯一理由：实测证明工作区之间由进程隔离，不会串台。

### 5.4 工作区列表从哪来（客户端枚举，白名单闸门）

| 家 | 来源（优先级从高到低） | 精度 |
| --- | --- | --- |
| Codex | `~/.codex/config.toml` 的 `[projects."<绝对路径>"]`（带 `trust_level`）→ `~/.codex/sessions/**/rollout-*.jsonl` 首行 `session_meta.cwd`（带最近使用时间）→ 用户在 exe 里手动添加 | 绝对路径，直接可用 |
| WorkBuddy | `~/.workbuddy/sessions/*.json` + `~/.codebuddy/sessions/*.json` 的 `cwd`（在线会话，精确）→ `~/WorkBuddy/*`（桌面默认根）→ `projects/` sanitize 目录名反解（补全）→ 用户手动添加 | 仅前两类精确；反解有失效风险（目录被删即解不回） |

三条硬闸门（这是本方案的安全底线，必须实现）：

1. **白名单命中才执行**：指令里的 `workspace.path` 必须等于客户端枚举登记表中的某一项；平台传任何未登记路径 → 拒执并回执 `WORKSPACE_NOT_ALLOWED`。否则平台侧一旦被攻破，"选工作区"就等价于"任意目录写权限"。
2. **存在性 + 新鲜度过滤**：实测 Codex 50 条候选里 14 条目录已不存在，UI 必须默认过滤并按 `lastUsedAt` 排序，只报 Top-N（建议 20）+ 搜索。
3. **trust 继承（Codex）**：`trust_level != trusted` 的工作区不允许 `silent`，只允许明示注入。

### 5.5 平台 UI 怎么摆（2026-11-13 定稿口径）

**选择顺序是固定的三步：先主机 → 再执行体 → 最后工作区**，每一步的可选项都由上一步的实测状态决定，不做"先摆一排灰按钮让人猜"。

| 步 | 位置 | 可选项从哪来 | 没得选时 |
| --- | --- | --- | --- |
| ① 主机 | 对话面板左栏顶部的主机清单 | 该账号下已配对的主机（`GET /hosts`） | 空态指向「主机」页签去配对 |
| ② 执行体 | 左栏主机清单下方（`执行体` 分组） | **只渲染心跳 `caps.connectors` 里 `state === 'CONNECTED'` 的那几家**；未连通的那家**整个不出现**（不摆灰态、不摆禁用项） | 一句可执行引导：去 BotBuddy 点「连通 WorkBuddy / 连通 ChatGPT（Codex）」；有 `CONNECTING` 的则显示「X 正在连通…」并 5s 轮询 |
| ③ 工作区 | 右侧对话面板**页头行末**（`Panel.extra`） | 所选执行器上报的候选表，过滤掉 `exists === false`，首项是「默认工作区 · <路径>」 | 客户端没上报候选时显示「默认工作区」并说明指令会落在连接器默认目录 |

四条硬规则（前端与后端一致，缺一条就会出现"看着能点、点了派不出去"）：

1. **已连通即绿色**：执行体选项是带绿点的胶囊（`.agent-pick-item`，选中态 `--success-soft` 底 + `--success` 字），右边小字「已连通」。绿色在这里的语义是**现在就能派活**（`CONNECTED` ⇔ `canSilent`），不是"装了"。
2. **未连通不渲染**：`ABSENT / DISCOVERED / NEEDS_ACTIVATION / FAILED / DISABLED` 一律不出现在选项里；`DEGRADED`（只能明示注入）同样不出现——本版口径是「能静默派活的才算可选」。要看状态与失败原因，去「主机」页签的台账（每家一行状态 + `failReason`）。
3. **换执行体即清空工作区**：A 家的路径不一定在 B 家的白名单里，切家时工作区回落「默认工作区」，由用户在 B 家候选里重选。
4. **当前执行体掉线自动改选**：轮询发现选中的那家不再是 `CONNECTED`，自动挪到还连通的一家（并清空工作区），避免留一个派不出去的目标；全都不通时发送按钮禁用。

定时任务表单同口径（`AgentTargetPicker` = 执行体胶囊 + 工作区下拉），另加「未连通 → 显示当前状态 + 一键连通」的兜底，因为表单可能在连通之前就打开。

其余：

- 主机台账每家一列状态 + 该家工作区数量徽章；上手说明里加"工作区怎么加"。
- 回执与运行记录里显示**实际生效的工作区**（`effectiveWorkspace`），不是请求值。

## 六、为什么一期不走 Codex 的原生 app-server / queue

C8 显示还有更"正"的面：`app-server daemon`、`queue --thread --message`、`agents`、`remote-control`。一期**不用**，理由写清楚，避免后来者以为漏了：

1. 全部标 `[experimental]`，且 `codex.exe` 是 alpha 版本（`0.155.0-alpha.9.2`），协议随版本漂移的风险高于已经稳定的 ACP；
2. ACP 与 WorkBuddy 同协议族，客户端可以**一套 ACP 实现吃两种 transport**（HTTP+SSE 打 WorkBuddy，stdio 打 Codex），代码增量最小、已实测端到端；
3. `queue` 的前提是"已有 thread"，而我们的任务是**新建任务**为主，续接留作开关（与 W3 口径一致）。

二期若要更"贴原生"，迁移点在客户端连接器内部，平台契约不变。

## 九、风险与未闭环（如实列）

1. **WorkBuddy 托管激活未通（W3）**：本方案已把它变成连接器的一等状态，平台不会被"假在线"骗到；WorkBuddy 侧真实**静默**派活仍为 0 交付，但**明示注入已可跑通**（挂靠桌面已登录 sidecar，实测 `end_turn`）。根因已定位到密钥层：凭据文件 `%LOCALAPPDATA%\CodeBuddyExtension\Data\Public\auth\workbuddy-desktop.info` 用 `$wbEncrypted` 信封加密，主密钥 `keyblob` 只在桌面 GUI 进程里，独立 spawn 的运行时读它必 `missing-key`（`security/at-rest-failures-v1.json` 记 `processRole=cbc`、`category=missing-key`）；把 `CODEBUDDY_CONFIG_DIR` 指向 `~/.workbuddy` 或直接复制 keyblob 均无效（实测仍 `-32000 auth`）。
2. **Codex CLI 是 alpha**：`0.155.0-alpha.9.2` + 桥 `0.15.0`，`login status`/`session/new`/`request_permission` 任一处随版本变更都可能破；对策是连接器自检矩阵（§4.4 五步）每次升级后跑一遍，`tools/agent-workspace-probe.js` 就是回归用例。
3. **权限自动应答是把双刃剑**：`allow-all` 等于让平台间接获得任意命令执行权。默认 `deny`、`allow-edits` 需用户在 exe 明示开启、`allow-all` 必须再配一次本机确认，且每次应答写审计。
4. **`allow-edits` 的边界由客户端自建，不是 OS 级隔离**：路径闸门只看 `toolCall.rawInput` 里的 cwd 与命令行绝对路径，命令里若用变量/环境变量/相对跳转拼出界外路径（如 `cd ..; Set-Content ..\x`），静态解析看不到。缓解：本档位只放行"能在命令行里看清目标路径"的操作，其余仍走 `cancelled`；真正需要硬隔离时必须先修好 Windows 沙箱（C9）。
5. **`read-only` 档的写操作要靠权限询问才生效**：客户端必须就地应答 `session/request_permission`，不应答整轮会挂到超时（C3）。桥进程被 `taskkill /T /F` 回收时正在跑的轮次会以 `bridge exited` 收场，回执要落 `FAILED` 而不是 `ok`。
6. **工作区 sanitize 反解不可靠**（W5）：目录删除即解不回、含 `-` 的名字理论可歧义。所以 WorkBuddy 侧只把在线注册表当权威来源，反解结果一律标"待用户确认"。
7. **ACP 面零鉴权**：自托管 sidecar 的 ACP 面只有静态头 `x-codebuddy-request`，本机任意进程可用它执行工具——沿用 v1.1 的收口（仅绑 127.0.0.1、端口由客户端私有派生、工具白名单、Job Object），并新增一条：连接器只用自己起的端口，绝不连"扫到的别人的端口"。
8. **未判定**：WorkBuddy `--add-dir` 的硬/软边界（被 K3 卡住）；WorkBuddy 会话内 `mode` 切换是否生效（W4 只见选项）；Codex `agents/app-server` 在多主机场景是否有端口/套接字冲突（一期不用）。

## 附：一句话结论

两家都能对接、都能一键连通、状态都能上报、工作区都能选——**差别只在机制**：Codex 的工作区是会话级的（一个常驻进程通吃多工作区，代价是必须替它应答权限），WorkBuddy 的工作区是进程级的（必须每工作区起一个运行时，代价是池化与串行分桶）；因此方案把"连接器 + 工作区白名单 + 权限策略"三件事抽象成平台与客户端的共同契约，把两家的差异彻底关在客户端里。唯一没变的老阻塞还是 WorkBuddy 的激活。
