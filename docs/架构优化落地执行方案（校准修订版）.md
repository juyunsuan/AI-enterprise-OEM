# 架构优化落地执行方案（校准修订版）

> 校准对象：[《架构优化总体方案》](架构优化总体方案.md)（母本）及其两份前身报告。
> 校准方法：对母本每条量化结论重新实测（`grep`/`wc`/`diff` 逐文件核对），并叠加本迭代已落地的
> `backend/src/tool-launch/`（建站工具启动设置 + 周期计费 + PV/流量计量）与多店铺商城平台（B0–B4）。
> 校准时间：2026-11-18。凡与母本结论不一致处，**以本文件为准**。

## 一、结论先说

母本的方向判断是对的：**技术骨架该集约、业务语义该独立、成本必须先可见**。需要修订的有两类：

1. **数字过期或偏高**（9 个小程序不是 6 个；支付重复 1725 行而不是 1100 行；存储绕过 28 处不是 30+；调度器 30 个是同一种范式复制 30 份，不是"几种范式"）。
2. **做法在本仓走不通或会造出第二套**（`@mini/core` 发 npm 包、静态扫描租户条件、再建一套 `BillingPlan/BillingSubscription` 账本、统一 Outbox 合表、PDP 四表归一、ERP 独立进程）。

修订后的主线只有一句话：**先让每个能力有"唯一实现点"，再让每个字节/每次调用/每个账期都有"唯一计量事实"，最后才谈扣费与体验**。

## 三、母本中需要改掉的做法（含替代方案）

### 3.1 `@mini/core` 发 npm workspace 包 → 改为「构建期注入单一真源」

不可行的原因（代码事实）：9 个小程序目录**没有 package.json、没有 node_modules、没有任何构建步骤**，是纯原生 CommonJS；出包链路 `pack-miniprogram.mjs` 与 `private-mini/package-builder.ts` 只做 `config.js` 空串槽位注入与 `project.config.json` 的 AppID 注入。一旦改成 npm 依赖，用户下载 zip 后必须先"工具 → 构建 npm"才能跑，直接破坏现在"下载即导入、导入即出包"的体验，也让后端出包的 2MB 主包体积闸门不可控。

替代方案（收益相同、零运行时风险）：

1. 仓库根新建 `shared/mini-core/core.js`（单文件、ES5 兼容、`module.exports`），承载 `requestCore`（baseUrl 组装、信封解包、401 单一策略、超时、合法域名提示文案）、`sessionCore(storageKey)`、`loginFlow(apiAdapter)`、`errorMap`。
2. 各端 `utils/request.js` 退化为 10–20 行薄封装：`const core = require('./core'); module.exports = core.createRequest({ apiPrefix, sessionKey, onUnauthorized })`。
3. 新增 `pnpm sync:mini-core` 把 `shared/mini-core/core.js` 复制进 9 个 `*/utils/core.js`；`package-builder.collectTemplate` 与 `check-architecture.mjs` 增加一致性校验（哈希比对，模板里的 `core.js` 与 shared 不一致就报错），保证"注入后与真源一致"。
4. 验收：9 份 `request.js` 合计从约 790 行降到约 180 行；401 只有一种实现；差异全部走参数。

### 3.2 再建一套 `BillingPlan / BillingSubscription` → 改为「目录层补字段 + 复用刚落地的订阅台账」

本迭代已经落地 `tool_subscriptions`（账号 × 工具一条订阅，启动预付、到期日批续扣、欠费宽限停服、补扣复活）+ `tool_subscription_bills`（`subscriptionId+periodKey` 唯一幂等）+ `module_pricing.billing_cycle`（`FREE/DAY/DAY30/YEAR/USAGE_PV/USAGE_BYTES`）+ 平台后台「建站启动计费」页与用户侧启动设置页。母本提议的 `BillingPlan/BillingSubscription` 与之高度重叠，两套并存必然出现"两个余额、两个到期日"。

修订为三层、只有一处账本：

| 层 | 归属 | 现状 | 待补 |
| --- | --- | --- | --- |
| 目录/定价 | `module_pricing`（code 唯一 + 单价 + 周期 + 免费额 + 起扣 + 是否允许自启） | 已有 | 若需要"人民币价/套餐组合"再补 `priceCents`，仍不落新表 |
| 额度/权益 | `EntitlementPlan/Quota/OrgEntitlement/EntitlementUsage` | 有目录无拦截 | 把 `check/require` 接进业务前置校验（P1） |
| 订阅实例与账本 | `tool_subscriptions` + `tool_subscription_bills` + `point_transactions` + `usage_events` | 已实现（8 工具周期计费） | 按量出账开关（等计量观察期结束） |

### 3.3 「API 网关中间件写 access_count」 + 「订单事务内写 order_count」 → 改为「一条计量事实 + 交易只观测不扣费」

- 访问/流量：已有 `tool_usage_daily`（站主 × 工具 × 日）。**不再加一层中间件、也不日批复制成 `usage_events` 行**——那是同一事实存两份，出账时还要判断哪份为准。改为与 `asset_storage` 完全同构的既有范式：`tool_usage_daily` 是快照事实源，只有真正出账那一步才写 `usage_events{code:'tool_launch', billed:1}`（`tool-launch.settle.ts` 已是这个写法）。母本要的"进 usage_events"在出账时自然满足，未出账期间不制造待结算噪声行。
- 订单数：`order_count` 同样落在这张快照表上（加 `orders` 列），而不是散到 `usage_events` 的 `billed:0` 行——一张表就是"本工具本日用了多少"的唯一答案，出账、看板、额度都从它读。
- 订单数：母本第 15 节自己写了"`access_count` 不能对交易型订单计费"，但同一节又主张在 5 个交易订单创建点埋 `order_count` 做扣费，**自相矛盾**。修订：`order_count` 只作为**计量与看板/额度**（商家看到"本月 320 单，套餐含 500 单"），若要向交易收平台费，走已实现的 marketplace 抽佣/结算（`MpCommissionRule` + `MpSettlement`）与服务商签约，绝不新增第二条平台扣积分路径。

### 3.4 「静态扫描所有顾客态查询是否含租户条件」 → 改为「越权用例矩阵 + 结构性守卫」

Prisma 的动态 `where` 组装、`aggregate/count`、`$queryRaw` 让这类正则扫描必然漏报误报，最后退化成"再给白名单加一行"。替代：

1. **越权用例矩阵**（真正的防线）：对 8 个私域通道各写一条自动化用例——用 A 店顾客令牌访问 B 店的订单/地址/券，断言 403 或空集。跑在 `pnpm test` 里，比扫描可靠。
2. **结构性守卫**（可静态判定）：公开路由必须经各域既有的 `resolve*/require*` 助手取站点上下文（如 `kp.member.enabledSite`、`card-shop.site-context`、`brand.public.shopOf`），守护脚本只断言"注册在 `/api/public/<域>` 的 handler 里出现了该助手调用"。
3. **令牌工厂**（3.5）落地后，`verifyToken` 直接校验 `scene` 白名单，把"共 issuer 误配"从约定变成代码约束。

### 3.5 令牌工厂：范围从"5 套"扩到 8 个模块，并保留 issuer 与 TTL 差异

`auth/mini-token-factory.ts` 统一 `deriveKey(issuer, secret)`（单一派生算法，消除 `createHmac(...).update(issuer)` 与 `createHash(...).update("oem-xxx|"+secret)` 两种范式）、`issueToken({issuer, scene, tenantId, subjectId, ttl, payload})`、`verifyToken(token, expectedIssuer, {scene})`。8 个模块退化为传参；**issuer 名、TTL、payload 字段名一律保持现值不变**（改了会让线上小程序令牌全部失效），只统一算法，并补"跨 issuer 必拒 + 跨 scene 必拒"用例。

### 3.6 统一 `EventOutbox` 合表、PDP 四表归一、ERP 独立进程 → 降级/改法

- **Outbox**：只抽**策略与工具**（超时/退避/熔断/幂等键/顺延不计数——现已在 `commerce-core/scrm-port.ts`），提到 `common/outbox-policy.ts`；表**先各自保留**（`brand_scrm_outbox`/`health_scrm_events`/未来的 `erp_outbox`），等出现第 4 个消费者再考虑合表。过早合表要把已验证的 brand 链路再迁一次，风险不对等。
- **PDP（主图/详情图）**：先做**零迁移归一**——把 `ecom-pdp.service.ts` 与 `domestic-pdp.service.ts` 的 `create/plan/generate/refreshStatus` 合成一个共享服务 + 两个 prompt 适配器，表保持两套；表合并只在需要"按渠道查询历史"时再做。
- **ERP 物理隔离**：本期不做独立进程。先做 `ErpPort`（端口 + Noop）+ 把 36 处直访改成端口调用 + 守护禁直读；进程拆分等"确实出现 ERP 慢查询拖垮主链路"的线上证据后再排。

## 五、对"增强集约性 / 关注客户体验"的落点说明

- 客户体验直接受益的三条：B4（一处修复 9 端生效，401 行为一致，不再"这家店能进那家店进不去"）、B5（大文件不再莫名失败，存储用量与费用在一个页面看得清）、B1+订阅页（扣费口径与账单可解释——本迭代已上线启动设置页，B1 把"按访问/按流量"的计量补成可公示的数据）。
- 集约性受益的三条：B2（−600 行支付重复）、B3（−8 份令牌派生）、B6（一套 ERP 服务多渠道）。
- 成本可见性：B1 让 AI 调用不再黑洞，B5 让字节 100% 进台账，两者合起来才具备"给用户计费"的前提。

### 6.3 B3 令牌工厂（进行中）—— 对母本 §3.5 的一处必要修正

母本写的是「统一 `deriveKey` 派生算法」。**这条不能照做**：现在并存两种历史派生口径——

- `hmac-issuer`：`HMAC_SHA256(JWT_SECRET, issuer)`（顾客、技师、代理、医护令牌）；
- `sha256-concat`：`SHA256("oem-xxx|" + JWT_SECRET)`（数字人、知识付费、多店铺会员）。

派生算法一换，此前签出的令牌全部验不过，等于把 8 个在营业的小程序顾客**集体踢下线**（会员令牌 90 天有效，影响会持续三个月）。所以本批统一的是**实现**——签名、有效期、Bearer 剥离、时钟容差、错误文案、场景白名单——而把派生算法做成显式策略 `derive: 'hmac-issuer' | 'sha256-concat'`，各 profile 原样传入自己的 issuer/context/TTL/载荷字段名。将来真要收口成一种，用 `legacyDerive + legacyContext` 开双读窗口，先兼容旧令牌一个 TTL 周期，再切写路径。

已完成：`auth/mini-token-factory.ts` + `mini-token-factory.spec.ts`（8 条，含**与历史口径双向等价**、跨 issuer 拒绝、场景白名单、过期/篡改、缺 `JWT_SECRET` 报服务不可用、双读窗口）；`dh.token.ts`、`kp.token.ts` 已改为工厂传参（各从 71/72 行降到 41 行）。
待做（同一模板照搬，风险低）：`private-mini/customer-token.ts`（含 scene 白名单）、`marketplace/mp.token.ts`、`onsite/{staff,agent}-token.ts`、`health/health-staff-token.ts`、`common/upstream-token.ts`，以及 8 域的跨店越权用例矩阵。

过程中发现并修掉一个**真实缺陷**：新写的守护正则里，`\b` 被写成退格控制符（0x08），正则永不匹配，等于守护悄悄失效——已用 hexdump 定位、重写并全仓扫描确认无其他文件被污染（`scripts/packages/backend/frontend/docs` 控制字符扫描 0 命中）。教训：**守护规则必须配反向用例**，否则"检查通过"可能只是规则没生效。

### 6.4 B2 支付收编的复核结论（发现并修掉 1 个回归）

支付那一路把 5 个 `*.pay.service.ts`（合计 1725 行）收编进 `WechatPayClient`，本地 `rsaSign/nonce/apiBase/GCM` 全部删除，净 −226 行；回调验真补上 ±5 分钟时间窗（`notifyTimestampOk`），未复用 `parseNotify` 的理由（路由只拿到密文、证书拉取失败会把可重试的 400 变成 5xx）经核对成立。

- `wechat-pay.client.ts` 的 `refund()`：`notify_url` 改为**有值才带**（微信退款接口本就允许不带回调，同步返回 + 退款单号轮询即可收敛）；
- brand / dh / mp 三域新增 `refundNotifyUrl(id)`：域名缺失返回空串而不是抛错；**下单路径保持严格版 `notifyUrl()`**（没有回调就没人把订单置成已支付，这里必须拦）。

顺手纠正了自己一次误操作：第一次批量替换时把宽容版打到了**下单**路径（dh 与 brand 各一处），已按语句位置核对并回正——`grep` 现在可以验证：三域的 prepay 用 `notifyUrl`，refund 用 `refundNotifyUrl`。

保留不合并的部分经复核同意：kuaidi 的多商户号账户 CRUD 与 `MiniAppCrypto` 密文、各域 `notifyUrl` 路由段与凭据作用域、下单前闸门（板块开关 / 金额>0 / openid / 站点域名）、退款失败的 `adminRemark` 留痕。

### 6.6 退款状态与存储账（已完成）

**退款：只认微信回的状态，不认 HTTP 200。**
`points/wechat-pay.client.ts` 的 `refund()` 现在要求 `status === 'SUCCESS'` 才返回，其余（`CHANGE / ABNORMAL / PROCESSING`）抛出带状态与退款单号的文案。这一步必须收在客户端：五个业务域原先都按「200 且拿到 refund_id」把售后单写成已退款，而 `ABNORMAL` 也是 200——钱没退出去、账上已退完，本仓又没有退款回调路由，连自愈机会都没有。同一 `out_refund_no` 微信侧幂等，所以重试不会退两笔。
配套改动：`brand/dh/mp` 的 `refundNotifyUrl()` 删除（它返回的是**支付**回调地址，退款通知打过去会被当无效回包 ACK 掉，比不通知更糟）；`onsite/health` 的退款凭据不再要求站点域名（域名只决定回调地址，健康域原来缺域名会掉进「手工退」分支——订单写成已退款而微信侧钱没动）；新增 `refundQuery()`，按退款单号直接问微信要状态。

**存储：同一份字节只算一份账。**
`digital_asset_entries.fileSize` 求和就是 GB·天账单，两处会多收钱：
1. 对象键里带 `randomUUID()/Date.now()`：店主每点一次「生成小程序码」就多一个对象、多一条账，永不下降。现在按身份定名（`common/asset-key.ts` 的 `stableAssetName(page)`；海报按 `copy.kind`；出包去掉随机段）。
   **命名必须覆盖台账行的整个唯一键**：版本行的唯一性是 `(店铺, 版本, 通道)`，所以对象名里也要带通道——
   只按版本命名会让同一版本的 STABLE 与 BETA 共用一份字节，删其中一个会把另一个的对象与账一起带走
   （这条是改完后自查时发现的，8 个域逐一按各自行的写法对齐：brand/card/dh/mp/kuaidi 用规范化后的 `channel`，
   onsite/health 用与行一致的 `body.channel`，knowledge-pay 出包没有通道维度因而名字里也不带）。
   用户上传的图片（后台手工传小程序码）仍保留随机段：那是彼此独立的资产，不该互相覆盖。
2. 删字节不出账：`SystemAssetService.remove()` 原先只删对象，注释写「台账行由调用方负责」，而没有任何调用方去删。现在删字节同批 `DigitalAssetService.forgetByOssKey()` 出账（连带共享授权），七个 release 域的删除入口改走这个门面。
`registerOwned()` 补了同键覆盖写；历史脏数据（同键多行）由 `forgetByOssKey` 一次清干净——用例专门钉了这条。机制导出的工件仍走 `storage` 直桶（本来就不入用户台账），删除路径保持原样。

新增用例：`content/digital-asset-ledger.spec.ts`（同键覆盖、异键分行、跨归属不误覆盖、删字节必出账、空键不动账、历史脏账一次清）、`system-asset.service.spec.ts` 补 remove 两条、`points/wechat-pay.client.spec.ts` 补非 SUCCESS 抛出与 `refundQuery` 路径两条。

## 八、M 批次：小程序分发改为「统一源码包 + 用户自助发布」

需求方口径（2026-11-19，含两次澄清后的最终版）：

| 决策点 | 结论 |
| --- | --- |
| 分发包 | 平台**统一输出**的源码分发包（zip）。包内**不含账号参数**：`config.js` 的 apiBase/租户码/主题色、`project.config.json` 的 AppID 由用户自己在开发者工具里填 |
| 编译与发布 | 平台**不编译、不代传**：用户在微信开发者工具里编译、预览、上传，提审发布在微信公众平台完成。各工具发布页的「上传到微信」入口下线（服务端 miniprogram-ci 底座保留给用户版 OA 小程序自用，那条链路不在本次范围） |
| 域名配置 | 平台管理员在后台配站点域名 → 前台**自动生成**微信服务器域名清单（request / uploadFile / downloadFile 同一 origin），未配置时给"去后台站点设置"的可操作入口而不是空值 |
| 说明呈现 | 同一份数据源三处呈现：① 建站管理·小程序板块该行右侧「小程序发布说明」；② 每个小程序发布页内嵌同样说明；③ 帮助中心「小程序发布说明」章节。正文由后台可编辑，账号参数与域名由后端渲染——**任何一处复制写死文案都算不合格** |
| MCP | 需求方一度提出"把发布做成 MCP，让 WorkBuddy/Codex 调开发者工具"，随后**明确撤回**：编辑与发布属于用户本机自己的工具链，与平台无关，平台侧不新增任何 MCP 面 |

为什么"平台代传"要下线（技术依据）：代传要求平台集中保管每个商户的 AppSecret 与代码上传密钥，且上传成功与否依赖把商户 IP 加进微信白名单；一旦平台侧代传，凭据泄露面与 IP 白名单运维成本都归到平台，而收益只是省一次用户手工点击。改为统一包后，平台只负责产出可编译的源码与准确的填写清单。

实现落点（契约先行）：`packages/contracts/src/mini-guide.ts` 定 `MiniGuide_view/shared` 与 `MiniGuideAdmin_view/save`；后端 `backend/src/mini-guide/`（工具元数据复用 `tool-launch.catalog.ts`，不再立第二套工具枚举）；出包侧删除 `injectConfig/injectAppId` 调用（`package-builder.ts` 内函数保留供平台自用底座），代传入口改为**任何台账写入之前**就明确拒绝。体积闸门 `MAIN_PACKAGE_LIMIT` 继续生效——统一包同样可能超 2MB。
