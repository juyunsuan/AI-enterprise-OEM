# 建站管理 · 品牌商城（B2C）与多店铺商城平台（B2B2C）设计方案

> 状态：设计定稿，分阶段实现。
> 参考源码：`CRMEB-v8.0`（Apache-2.0，PHP ThinkPHP + Vue3 + uni-app，124 张表 / 5 类模块 / 10 类驱动）。
> **本方案不移植 CRMEB 代码**，而是把它的业务能力与中台分层按本项目架构（Next.js 16 + Hono + Prisma + antd 6 + zod 契约）重写：PHP 控制器 → Hono controller + service 分层，`cb_*` 表 → 各自的 `brand_*` / `mp_*` 表，uni-app 一套三端 → 仓库内原生微信小程序模板 + 出包注入直传。
> v8.0 已改 Apache-2.0（与《私域小程序 · 电商小程序工具设计方案》写作时参考的闭源多商户 v4.2 不同），允许商用与二次分发；仍要求保留出处声明，且不得复制其文案、图片素材与 UI 截图。

## 一、产品口径（已与需求方确认的六项决策）

| # | 决策点 | 结论 |
| --- | --- | --- |
| 1 | 卡片划分 | **两张卡、两种业务**：**品牌商城** = B2C（本站用户自营一个品牌店）；**多店铺商城平台** = B2B2C（本站用户是平台方，商户入驻开店）。不合并、不共用一套业务表 |
| 2 | 现有 `/mall` 归属 | 「电商平台小程序」按 B2C 语义**演进为品牌商城**（目录 `mall` → `brand-mall`，表 `mall_*` → `brand_*`，操作 `Mall_*` → `BrandMall_*`）。它至今未提交入库，改名成本最低，且能保住已实现的算价/售后/出包逻辑 |
| 3 | 技术复用 vs 数据隔离 | **代码抽象复用、数据物理分离**：抽一层表无关的商城中台引擎 `backend/src/commerce-core/`，两个业务各自实现仓储适配器并拥有独立表、独立小程序主体、独立 C 端顾客库 |
| 4 | B2B2C 首期深度 | **真 B2B2C**：商户入驻申请与平台审核、商品归商户、跨商户购物车**自动拆单**（父单 + 商户子单）、平台**抽佣比例**与**待结算台账 + 提现申请** |
| 5 | C 端载体 | 仅**原生微信小程序**模板（两套独立源码），出包注入后 `miniprogram-ci` 直传为各自主体的开发版；不做 uni-app、不做 H5/APP 端 |
| 6 | 客服 | **复用站内 AI 客服（`/service-desk`）**，不新建任何聊天表；每个商城实例挂一个 `ServiceDeskSite`，会话按 `externalMeta` 回写店铺/商户归属（见 §九） |
| 7 | 顾客层与 SCRM | 商城顾客层**可对接营销工具·企业微信 SCRM**，但**松耦合**：事件外发 + 身份绑定表都在商城侧，SCRM 表只由 SCRM 自己写；`wecom-scrm` 与 `brand-mall` / `marketplace` 任一被关闭，另一个功能与数据完全不受影响（见 §九之二） |

一句话：**同一套商城中台引擎，长出两个互不干扰的业务体——一个自营品牌店，一个商户入驻市场。**

## 三、复用矩阵（尽量吃现成服务，不重造）

| 现成能力 | 位置 | 两个业务怎么用 |
| --- | --- | --- |
| 私域小程序底座（主体凭据、出包注入、`miniprogram-ci` 直传、小程序码、顾客令牌） | `backend/src/private-mini/`、`packages/contracts/src/private-mini.ts`、`miniprogram/miniprogram-ci.service.ts` | 加两个 scene（`BRAND` / `MARKET`）即整套继承；`app_id` 全局唯一天然防两个业务抢同一主体 |
| AI 客服（站点、访客、会话、坐席、AI 模式 OFF/CANNED/SUGGEST/AUTO/BOT、FAQ、转 CRM） | `backend/src/service-desk/`（含 `service-desk.public.ts` 的访客侧 `open/session` + SSE） | 每个商城实例一行 `service_desk_sites`；小程序 C 端走访客接口，店主在既有 `/service-desk` 页面接待 |
| 企业微信 SCRM（客户、标签、客户群、渠道活码、群发、SOP、客户时间线、自定义字段） | `backend/src/wecom-scrm/` | 松耦合格子：商城侧 outbox + 绑定表，经 `ScrmBridge` 端口单向送事件、只读回画像；SCRM 表不由商城写（见 §九之二） |
| 对象存储 / 素材上传 | `backend/src/oss/`、`backend/src/storage/` | 商品图、装修图、售后凭证、出包 zip、小程序码全走 OSS；不新建上传通道 |
| 积分与计费底座 | `backend/src/points/` | 平台侧按商城实例计量扣积分；C 端顾客积分归各业务自己的资产表，不与站内积分打通 |
| 微信支付 APIv3（JSAPI 下单、回调解密、退款） | `backend/src/mall/mall.pay.service.ts`（现有实现上收到 `commerce-core/pay`） | 商户号来自各主体 `miniprogram_apps`；B2B2C 每笔子单落各自商户号 |
| 单据号与方言适配 | `backend/src/common/constants.ts`、`common/db-provider.ts`、`common/sql-json.ts` | 单号前缀分业务：品牌 `BD`、市场父单 `MP`、子单 `MS`、售后 `AF`、结算 `ST`、提现 `WD` |
| 省市字典 / 快递公司预置 | 平台侧预置数据（现 `mall_express_companies` 的 `shopId=0` 口径，上收为 `commerce_express_presets` 只读共享表） | 两个业务只读同一份预置清单，各自维护本店启用的快递（写自己的表），避免录两遍又不互相污染 |
| 通知与站内消息、订阅消息模板位 | `backend/src/notifications/`、底座 `templates` | 下单/发货/售后/入驻审核完成统一走既有通知中心 |
| 模型网关（AI 能力） | `backend/src/ai/` | 客服机器人、商品文案与主图 alt 生成一律经网关，禁止直连上游 |

## 四、中台引擎 `commerce-core`（表无关，可被 N 个业务复用）

CRMEB v8 的中台化（商品中台 / 订单中台 / 售后退款中台 / 用户与资产 / 交易模式注册中心）落到本项目，做成**代码层引擎 + 每业务一份仓储适配器**，而不是共享表：

```
backend/src/commerce-core/
├─ types.ts            // 泛型领域类型：CommerceLine（含 splitKey / requiresShipping）、CommerceTradeRules、JSON 归一化
├─ money.ts            // 分单位整数：toCents/fromCents/clamp + allocateCents（分摊合计恒等的不变量）
├─ ident.ts            // 店铺码、单号（前缀+时间戳+随机）、规格 uniqueId
├─ product.ts          // 商品形态注册中心 + 规格笛卡尔积 + SKU 价/库存汇总 + 上架超卖拦截
├─ cart.ts             // 行合并/勾选/计数/结算项（不存价格快照，改价无需回写购物车）
├─ pricing.ts          // 唯一算价入口：券（满减/折扣 + 全场/分类/商品范围）→ 运费（全虚拟→满额包邮→模板首续件→统一运费）→ 积分抵扣与返分 → 阻断口径
├─ split.ts            // 按 splitKey 拆单 + 优惠/运费按权重分摊 + 落库前对账
├─ order-machine.ts    // 状态机 + 分角色可操作按钮 + C 端进度条 + 自动取消判定
├─ aftersale.ts        // 售后准入规则链（开关→状态→进行中→形态→时限）+ 金额口径 + 副作用幂等协议
├─ diy.ts              // 组件白名单校验、props 与初值合并、条数上限、链接归一化（只允许站内路径）
├─ support.ts          // AI 客服会话上下文：externalMeta 组装与按店铺/商户过滤（不重建会话系统）
├─ publish.ts          // 注入键 vs 运行期键的分类、版本号口径、开发版合规话术
├─ scrm-port.ts        // ScrmBridge 接口 + noop 实现 + 幂等键 + 脱敏 + outbox 投递计划/退避/熔断
├─ modules.ts          // 能力注册表与统一「还没开放」文案
├─ index.ts            // 业务只从 `../commerce-core` 引用
└─ *.spec.ts           // 11 个 spec / 91 条断言
```

引擎形态按「**纯函数 + 业务注入数据**」落地，不设 `ports.ts` 仓储接口：算价、拆单、状态流转、售后准入都只吃已归一化的行与规则，DB 读写留在各业务 service 里。业务对引擎的唯一注入点是 `ScrmBridge`（可替换、可空转），因此 `commerce-core` 目前**零跨目录依赖**（只 import `node:crypto`）。

**硬约束**：`commerce-core` 不得 import 任何业务 model，也不得出现 `brand_` / `mp_` 字面量；两个业务不得互相 import。业务互不影响靠这条边界守住（配 `check:architecture` 扫描）。

## 五、数据模型

### 5.1 品牌商城 `brand_*`（由 `mall_*` 17 表改名，按 v8 与集成需求新增 6 张 → 23 表）

改名沿用（迁移里用 `ALTER TABLE ... RENAME TO`，MySQL / PG 同语法）：
`mall_shops→brand_shops`、`mall_categories→brand_categories`、`mall_products→brand_products`、`mall_product_skus→brand_product_skus`、`mall_product_reviews→brand_product_reviews`、`mall_express_companies→brand_express_companies`、`mall_customers→brand_customers`、`mall_customer_addresses→brand_customer_addresses`、`mall_customer_bills→brand_customer_bills`、`mall_cart_items→brand_cart_items`、`mall_orders→brand_orders`、`mall_order_items→brand_order_items`、`mall_order_logs→brand_order_logs`、`mall_refund_orders→brand_refund_orders`、`mall_coupons→brand_coupons`、`mall_coupon_tickets→brand_coupon_tickets`、`mall_diy_pages→brand_diy_pages`。

v8 对照后**新增**：

- **`brand_shipping_templates` + `brand_shipping_template_rules`** — 运费模板（对应 `cb_shipping_templates` 与 region/free/no_delivery 三张子表，本项目收成「模板 + 规则行 JSON」两张：按区域/首重续重/满额包邮/不发货区域）。商品的 `freightTemplateId` 指向它；缺省回落店铺 `tradeJson` 默认运费。
- **`brand_product_params`** — 商品参数与售后保障（对应 `cb_store_product_param` + `protection`），一行一商品，JSON 存参数清单与保障标签。
- **`brand_refund_effects`** — 退款副作用幂等台账（对应 `cb_refund_effect`）：回补库存、退券、扣积分各自一行，唯一键 `[refundId, effect]`，重试不重复执行。这是 v8 售后退款中台最值得直接吸收的一点。

- **`brand_scrm_bindings` + `brand_scrm_outbox`** — SCRM 身份绑定与事件外发箱（见 §九之二）：只引用 `scrm_contacts.id`，不在 `scrm_*` 表上加一列、不建跨业务外键。

预留但首期不开放（接口 `notReady()`）：`brand_customers.level/points/balance` 已有列；会员等级、签到、储值提现、积分商城、秒杀拼团砍价、分销佣金 → 二期。

### 5.2 多店铺商城平台 `mp_*`（新建 28 表）

租户与账号

- **`mp_markets`** — 市场实例（一个本站用户一个平台，`ownerUserId` + `shopCode` 公开寻址 + `themeJson` + `tradeJson` + `settleJson`(默认抽佣/结算周期/提现门槛) + `status`)。
- **`mp_merchants`** — 商户主体：`marketId` `name` `licenseNo` `contactName/Phone` `categoryIds`(经营范围) `auditStatus`(PENDING/APPROVED/REJECTED/BANNED) `auditNote` `auditAt/By` `commissionRate`(null=按类目/平台默认) `expireAt` `status`。
- **`mp_shops`** — 商户店铺（商户可有 1..N 店，首期 1:1）：`marketId` `merchantId` `name` `logo` `categoryIds` `shopCode` `mchId`(微信支付商户号，回落到主体配置) `payEnabled` `status` `sortOrder`。
- **`mp_merchant_users`** — 商户后台账号（**独立于站内 `User` 与 org-staff**，避免把外部商户塞进企业组织树）：`merchantId` `username`(全局唯一) `passwordHash` `salt` `role`(OWNER/STAFF) `phone` `lastLoginAt` `status`。令牌与 C 端顾客令牌同一套签发机制（HMAC + 过期），上下文串掺入 `marketId`，跨市场不可互解。

商品与内容

- **`mp_categories`**（平台统一类目，商户只能选不能造）、**`mp_products`**、**`mp_product_skus`**、**`mp_product_reviews`**
- **`mp_product_audits`** — 商品送审与平台审核流水（`auditStatus`、`reason`、快照 hash）。

交易

- **`mp_carts`** — 顾客购物车（跨商户混选）。
- **`mp_orders`** — **父单**（一次结算一个父单）：`orderNo`、顾客、`goodsAmount/freightAmount/discountAmount/payAmount`、`payStatus`、`payType`、`transactionId`、`shopOrderCount`、`expireAt`。父单只做支付与整体状态，不持有发货动作。
- **`mp_shop_orders`** — **商户子单**（拆单产物，发货/售后/结算单位）：`orderId` `marketId` `merchantId` `shopId` `subOrderNo` `goodsAmount/freightAmount/discountAmount/payAmount` `commissionRate` `commissionAmount` `status/payStatus/refundStatus` `receiver*` `expressCompany/expressNo` `shippedAt/completedAt`。
- **`mp_order_items`** — 明细，挂 `shopOrderId`（下单快照：标题/规格/单价/数量/佣金快照）。
- **`mp_order_logs`** — 时间线（区分 SYSTEM/CUSTOMER/MERCHANT/PLATFORM 四类操作者）。

售后与支付

- **`mp_after_sales` + `mp_after_sale_items`** — 售后单与明细（商户审、平台可介入仲裁 `platformNote`）。
- **`mp_refunds` + `mp_refund_effects`** — 统一退款单与幂等副作用（含佣金冲销）。
- **`mp_pay_records`** — 支付流水（父单一次支付、按子单拆分记录 `payAmount`/`commissionAmount`，供结算对账）。

顾客与资产

- **`mp_customers`**（`[marketId, openid]` 唯一）、**`mp_customer_addresses`**、**`mp_customer_bills`**、**`mp_customer_follows`**（关注店铺，私域复访入口）。
- **`mp_scrm_bindings` + `mp_scrm_outbox`** — 同品牌商城口径，绑定行另带 `merchantId`（客户的企微归属通常落在具体商户的导购身上，事件按商户维度送）。

营销与装修

- **`mp_coupons` + `mp_coupon_tickets`** — 券分两档：`issuerType`(PLATFORM/MERCHANT) + `merchantId`(0=平台券)、`scope`；跨商户下单时父单券分摊到子单。
- **`mp_diy_pages`** — 市场首页/分类页/活动页；**`mp_shop_diy_pages`** — 店铺首页（商户自装，平台可下架）。

结算（B2B2C 的本质差异）

- **`mp_commission_rules`** — 抽佣优先级：商户专属 > 类目 > 平台默认（沿用本项目「单据号前缀解析优先级」同思路的优先级链）。
- **`mp_settlements` + `mp_settlement_items`** — 结算单：按周期把子单净额（`payAmount - refundAmount - commissionAmount`）汇成一条待结记录，`status`(PENDING/CONFIRMED/PAID)。
- **`mp_withdrawals`** — 提现申请与平台审核打款回填（`applyAmount`、`fee`、`bankInfo`/`wechatOpenid`、`status`、`voucher`）。

> 首期**不建**：直播带货、到店核销/门店（`system_store`）、外卖配送与骑手、云打印电子面单、发票、社区种草、多语言、ERP 库存打通、商户子账号细粒度 RBAC（`role` 只分 OWNER/STAFF）。

### 5.3 迁移编排（双库）

1. `0123_commerce_rename` — `mall_*` → `brand_*` 改名 + 新增 4 张 v8 补齐表（运费模板两张、商品参数、退款副作用）+ `supportSiteId` 列。（`0122_card_shop` 已被卡密商城工具占用，本方案一律从 `0123` 起排。）
2. `0124_brand_express_presets` — 抽平台预置快递共享表并回填两个业务只读入口。
3. `0125_brand_scrm_bridge` — `brand_scrm_bindings` + `brand_scrm_outbox`（表先建、桥后接，表与桥分两次评审）。
4. `0134_mp_market_core` — 市场/商户/店铺/商户账号 + 平台类目。
5. `0135_mp_catalog_trade` — 商品域 + 父单/子单/明细/日志/购物车/地址。
6. `0136_mp_aftersale_settlement` — 售后、退款与副作用、支付流水、抽佣规则、结算单与提现。
7. `0139_mp_marketing_diy_scrm` — 券、市场装修、店铺装修、关注、`mp_scrm_bindings` + `mp_scrm_outbox`。
8. `0140_mp_market_scrm_enabled` — `mp_markets.scrmEnabled` 市场级 SCRM 开关。

口径：一律 `pnpm prisma:migrate:deploy`（本地 MySQL 绕开仓库 wrapper），**禁止 `db push`**；改完跑 `pnpm db:gen:pg`。金额 `@db.Decimal(12,2)` + 分单位整数；JSON 列不做跨库函数运算；结构变更 SQL 只用两库同语法子集（`ALTER TABLE ... RENAME TO`、`CREATE TABLE`、`CREATE INDEX`）。

## 六、后端接线（每个业务四处，照 geo-site / mall 现有做法）

1. 契约文件在 `packages/contracts/src/index.ts` 与 `endpoints.ts` 展开（`brandMallEndpoints`、`marketplaceEndpoints`）。
2. `backend/src/http/services.ts` 构造服务图：`commerceCore` 引擎以适配器参数分别实例化两个业务的服务集。
3. `backend/src/http/automation-routes.ts` 加 `moduleHandlers('BrandMall_'|'Mp_'|'BrandMallAdmin_'|'MpAdmin_', controller)`。

## 九、客服复用（走 AI 客服底座，不重建）

1. 商城实例创建/首次进入发布页时，经 service-desk 的建站点接口幂等确保一行 `service_desk_sites`：`ownerUserId` = 店主，`name` = 店铺名，`appearance` 取店铺主题。**`siteKey` 由客服底座自己生成（`sk_` + 24 hex）且支持轮换，商城不自行拼造**；service-desk 每账号限 20 个站点，配额用尽要给出可点的清理入口而不是只报错。
2. C 端小程序顾客走既有访客接口：`POST /api/public/service-desk/open/session`（带**当前** `siteKey` + 顾客昵称头像）→ 会话 + 访客令牌 → `GET /open/stream/:id`（SSE，小程序 `wx.request({enableChunked:true})`）→ `POST /open/messages/:id` 发文本/图片（`/open/upload`）。`siteKey` 每次由商城按 `supportSiteId` 现查，绝不写进小程序包内常量——店主轮换密钥后包里写死的旧 key 会让入口全断。
3. 会话归属回写：创建会话时写 `externalMeta = { biz:'brand'|'market', shopId, shopName, orderId? }`；B2B2C 首条消息带 `[商户:<name>]` 前缀 + `externalMeta.merchantId`，商户在自己的后台只看得到 `externalMeta.merchantId` 命中的会话（视图过滤，不改 service-desk 表结构）。
4. AI 模式（OFF/CANNED/SUGGEST/AUTO/BOT）沿用店主的 `/service-desk` 设置；商城侧只提供「客服」入口与 `groupId` 预设，不复制一套机器人。
5. 唯一新增落库：`brand_shops.supportSiteId` / `mp_markets.supportSiteId` 一列引用，便于展示与重绑。
6. **关闭独立性**：关掉 `brand-mall` / `marketplace` 不影响 `/service-desk` 既有会话与坐席；关掉 `service-desk` 时小程序客服入口显示「客服未开通」空态与跳转链接，商城交易主链路不受任何影响。

## 九之二、顾客层 × 企业微信 SCRM（松耦合）

需求：**商城顾客要能与营销工具·企业微信 SCRM 对接**（把私域买家识别成企微客户、把消费行为送进客户时间线、把 SCRM 标签拿回来做分层运营），但**两个服务互相独立，平台管理员关掉任何一个都不能影响另一个**。

### 9b.1 唯一耦合点：`ScrmBridge` 端口

```
backend/src/commerce-core/scrm-port.ts（已落地，以下即实现签名）
export type ScrmBridge = {
  /** SCRM 是否可用（板块开关 + 该 org 是否配好企微凭据）。不可用时给出可执行原因。 */
  status(orgId): Promise<{ ok: boolean; reason: 'OK'|'FEATURE_CLOSED'|'NOT_CONFIGURED'|'UNAUTHORIZED'; hint: string }>;
  /** 按 unionId / 手机号哈希匹配企微客户；匹配不到返回 null，不抛错。手机号明文不进桥。 */
  matchContact(orgId, q: { unionId?: string; mobileHash?: string }): Promise<{ contactId: number } | null>;
  /** 追加一条客户时间线（kind='MALL'）。 */
  appendTimeline(orgId, e: { contactId: number; title: string; detail: string; at?: Date }): Promise<void>;
  /** 按 SCRM 侧已定义的自定义字段键回写值（字段不存在则整项跳过，不报错），返回实际写入条数。 */
  pushFields(orgId, contactId: number, values: Record<string, string>): Promise<{ written: number }>;
  /** 只读回画像：标签名 + 最近互动时间（无互动为空串）——供商城顾客详情页展示。 */
  readProfiles(orgId, contactIds: number[]): Promise<Map<number, { tags: string[]; lastInteractionAt: string }>>;
};
```

- 手机号在商城侧用 `scrmMobileHash()`（HMAC-SHA256 + 固定上下文前缀）算完再进桥，桥与 SCRM 都拿不到明文；展示给用户看的是 `scrmCustomerLabel()` 的脱敏串（`138****1111`）。

- 商城代码**只依赖这个类型**，不 import `wecom-scrm/` 下任何实现类；`backend/src/http/services.ts` 装配时注入真实实现，SCRM 未接入/未开启时注入 `noopScrmBridge`（所有方法 `Promise.resolve` 降级值，永不抛错）。
- 写 SCRM 的动作一律经 SCRM 自己的 service（`Scrm_*` 背后的 contact/timeline/field 服务），**商城不直接写 `scrm_*` 表**，也不给 SCRM 表加列。

### 9b.2 数据落在商城侧（两张表 × 两个业务）

- **`brand_scrm_bindings` / `mp_scrm_bindings`** — 身份绑定：`ownerUserId` `shopId`（`mp_` 另带 `merchantId`） `customerId` `contactId`(普通 INT，0＝未匹配，**不做外键**) `unionId` `mobileHash` `bindSource`(AUTO_UNIONID/AUTO_MOBILE/MANUAL) `status`(BOUND/UNBOUND/IGNORED) `lastSyncAt`。唯一键 `[shopId, customerId]`。
- **`brand_scrm_outbox` / `mp_scrm_outbox`** — 事件外发箱（本地事务表，**outbox 模式**）：`shopId` `customerId` `eventKind` `dedupeKey`(唯一) `payloadJson` `status`(PENDING/SENT/DEAD/SKIPPED) `attempts` `nextAt` `lastError` `sentAt`。索引 `[status, nextAt]`、`[shopId, createdAt]`。

事件清单（`eventKind`）：`CUSTOMER_REGISTER`（首次授权登录）、`ORDER_PAID`、`ORDER_COMPLETED`、`ORDER_REFUNDED`、`COUPON_RECEIVED`、`REVIEW_SUBMITTED`、`BALANCE_RECHARGED`（二期）、`CUSTOMER_SILENT_30D`（scheduler 每日扫）。`dedupeKey = <biz>:<eventKind>:<业务主键>`，重放不产生重复时间线。

### 9b.3 发送侧的独立性规则

1. 下单/退款/领券的**主事务内只写 outbox 一行**，提交即返回；发送由 scheduler 异步完成（每轮每 org ≤ 50 条、同 org 串行、单次调用 3s 超时、连续 5 次失败熔断冷却 10 分钟）。SCRM 挂了、慢了就是一次网络抖动，商城顾客下单速度不受影响。
2. `bridge.status()` 返回 `FEATURE_CLOSED`（`wecom-scrm` 被平台/账号关闭）或 `NOT_CONFIGURED` 时：事件保持 `PENDING` 并把 `nextAt` 顺延（**不计入 attempts、不判 DEAD**），重试上限 5 次仅针对真实调用失败。恢复后自动补发。
3. 补发窗口有界：`PENDING` 超过 30 天或积压超过 2000 条时按最旧淘汰为 `SKIPPED` 并留痕，防止 SCRM 长期不开导致表膨胀。
4. 匹配不到客户（`matchContact` 返回 null）：不猜、不新建企微客户，事件记 `SKIPPED(match-miss)` 并在集成健康度里给计数；店主可在 SCRM 侧加客户后由「一键重投」补发。
5. 匹配锚点优先级：`unionId`（微信开放平台同一主体下天然一致，主锚）> 手机号（仅当企业在 SCRM 侧定义了手机号自定义字段才可用）> 店主人工绑定。**手机号匹配走 SCRM 自定义字段查询，不在商城存 SCRM 明文手机号**，商城侧只存 `mobileHash`（HMAC-SHA256，上下文串 `scrm-match`）用于本地比对与展示脱敏。
6. 数据最小化：送出去的是 `unionId / 昵称 / 事件类型 / 金额 / 订单号 / 店铺名`，**不送**收货人姓名、地址全文、订单明细。
7. 关掉 `brand-mall` / `marketplace`：outbox 停止生产，SCRM 里已生成的 `MALL` 时间线保持原样（SCRM 永不反查商城），SCRM 客户详情页的「商城画像」块自动隐藏。

### 9b.4 入口与可见性

- 商城侧新增页签 `/brand-mall/setting?tab=integration`（`/marketplace/setting?tab=integration` 同构）：SCRM 开关（默认关）、绑定数、待发送/失败/跳过计数、「立即重试」「一键重投 SKIPPED」、企微配置跳转 `/marketing-tools?tab=wecom-scrm`。
- 顾客详情页只读展示：企微客户名 + 标签胶囊 + 最近互动时间；未开启或匹配不到 → 一行灰字说明 + 跳转按钮，不留空指针。
- SCRM 侧不改菜单、不加页面；`kind='MALL'` 的时间线在既有客户时间线里自然渲染（`title` 写清「品牌商城」「多店铺平台」来源）。
- 能力开关：`FEATURE_API_PREFIXES` 三条互不包含的前缀（`/enterprise/wecom-scrm`、`/enterprise/brand-mall`、`/enterprise/marketplace`），按 §5.10 最长前缀命中规则天然互不牵连；集成健康度接口归商城前缀（关商城时随之不可见，关 SCRM 时仍要能显示「SCRM 未开通」）。

### 9b.5 顺带的用户层口径

商城顾客对外只暴露 `customerId + unionId + mobileHash` 三元组作为身份锚。SCRM 之外将来接 CRM / BI / 短信营销，一律复用这同一个 outbox + bridge 形状再加一个端口实现，**不再为某个下游单独造同步表**。

## 十一、隔离与合规硬约束（评审清单）

1. `commerce-core` 不 import 业务 model；两业务不互相 import；CI `check:architecture` 加一条扫描规则。
2. 每个中台入口第一道校验 `requireShop(user, shopId[, merchantId])`：owner 归属 + scene/edition 匹配，不匹配即 `FORBIDDEN`，禁止「先查再判 owner」的宽松写法。
3. C 端顾客**绝不**与站内 `User` 混用；顾客令牌 payload 必带 `biz + marketId/shopId`，跨业务密文不可互解。
4. 父单只承载支付，发货与售后一律在子单；结算台账只依赖子单与退款副作用，缺副作用记录不得生成结算单。
5. 资金表述统一：在线收款直进商户自己的微信商户号，平台侧抽佣为**台账与线下结算**，页面与合同文案不得写成分账。
6. 凭据只回 `xxxConfigured`，任何读接口不回明文；上传密钥仅经子进程 stdin。
7. 关掉 `brand-mall` 不得影响 `marketplace`，反之亦然；底座与 C 端通道不因业务开关而掐死已发布小程序。
8. **三块业务（品牌商城 / 多店铺平台 / 企业微信 SCRM / AI 客服）两两独立开关**：`FEATURE_API_PREFIXES` 里 `brand-mall`、`marketplace`、`wecom-scrm`、`service-desk` 四个前缀互不包含，任关其一不牵连其余；关掉 SCRM 或客服时，商城的下单、售后、出包路径必须逐条有自动化用例覆盖（`*.spec.ts` 里显式断言 bridge 返回降级值时交易仍成功）。
9. 商城**永不**直接写 `scrm_*` / `service_desk_*` 表：写动作经 SCRM / service-desk 自己的 service，读动作经只读查询端口；`commerce-core` 编译期只依赖端口类型，运行期由 `services.ts` 决定注入实现还是 `noop`。
10. 事件外发只能走 outbox（本地事务表 + 异步投递），**严禁**在下单/退款事务里同步调用 SCRM 或客服；这是「关掉一个不影响另一个」在代码层的唯一保证点，评审逐处核对。

## 十三、已识别风险

1. **A0 是一次全量改名**（17 表 / 77 操作 / 约 11 个前端页 / 22 个小程序页面 / 出包脚本 / 平台后台板块）。虽然 `/mall` 未入库，但本地已有 `0118_mall` 迁移产物：改名迁移必须用 `RENAME` 而不是 drop-create，否则本地测试数据全丢。
2. **B2B2C 是本仓迄今最大单模块**（28 表 + 约 107 操作 + 两套前端 + 一套新小程序模板）。按 B0→B4 推进，每期可独立演示；不要跨期并行铺表。
3. **商户账号体系**若图省事复用站内 `User`/org-staff，会把外部商户塞进企业组织树并打通计费，属于不可逆污染——列为评审红线。
4. **拆单与支付的原子性**：父单一次支付、子单分商户号收款，在微信侧不是一个原生能力。首期按「父单支付成功后按商户拆子单、各子单绑定各自商户号做后续退款」实现，若要求资金直进各商户号则需微信服务商模式（平台资质），已列待定项，页面上先明示当前为平台代收后按台账分账结算的口径。
5. **`miniprogram-ci` 并发**：三套模板 × 多租户上传，需同店互斥、全局限并发、240s 超时与可执行错误提示（底座已具备，容量待压测）。
6. **参考源码许可**：CRMEB v8.0 为 Apache-2.0，可参考结构与口径；禁止直接复制其源码、语言包与图片素材进仓库，README 与本文档保留出处声明。
7. **unionId 跨主体不一致是 SCRM 对接的真实天花板**：`unionId` 只在「同一微信开放平台账号下的 AppID」之间一致。商城小程序用的是租户自己的 AppID，企微 SCRM 的客户 `unionId` 只在企业自己的开放平台绑定后才有值——两者若不属于同一开放平台主体，自动匹配率就是 0。因此：顾客表与底座必须完整保存 `unionId`（`code2Session` 在开放平台已绑定时才回传，需在小程序侧引导静默授权并落库），并把**手机号自定义字段匹配**与**店主人工绑定**当作主路径之一而不是补丁；集成页签必须显示「可自动匹配 / 已绑定 / 匹配不到」三档计数，避免用户以为功能坏了。
8. **outbox 积压与语义漂移**：事件是「快照时刻的事实」，补发时商城侧数据可能已变（订单已再次退款）。所以 payload 必须自带当时的金额与单号，SCRM 时间线只做展示与打标依据，**禁止**让 SCRM 侧回读商城现值；`CUSTOMER_SILENT_30D` 这类扫描事件要按 `[customerId, day]` 去重，防止补发风暴刷屏。
