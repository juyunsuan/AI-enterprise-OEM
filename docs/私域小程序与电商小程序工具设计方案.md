# 私域小程序 · 电商小程序工具 设计方案

> 状态：设计定稿，进入分阶段实现。
> 参考源码：CRMEB Merchant v4.2（PHP ThinkPHP8 + Vue2 多商户电商，182 张表 / 268 控制器 / 约 800 前端页面）。
> **本方案不是移植 CRMEB 代码，而是把它的业务能力按本项目技术架构（Next.js 16 + Hono + Prisma + antd 6 + zod 契约）重写一遍。**
> CRMEB 为闭源软件，仓库内只允许参考其业务口径与数据结构设计，不得复制其源码、文案与图片。

---

## 一、产品口径（已与需求方确认的四项决策）

| 决策点 | 结论 | 与 CRMEB 的差异 |
| --- | --- | --- |
| 租户层级 | **两层：本站用户 → 消费者**。本站用户即「商城主人」，其小程序里的 C 端客户直接归属该用户 | CRMEB 是「平台方 → 入驻商户 → 消费者」三层，`mer_id` 贯穿 100 张表。本方案用 `shopId + ownerUserId` 取代 `mer_id`，**不做商户入驻审核、保证金、区域代理、商户分账** |
| 小程序发布 | **用户自带 AppID + 代码上传密钥，平台直传微信**（复用已实现的 `miniprogram-ci` 子进程链路）生成开发版；提审/发布在用户自己的微信公众平台完成 | CRMEB **没有**真正的按商户上传能力（只有一个平台小程序 + DIY 店铺页）。这是本方案相对参考源码的净新增能力 |
| 在线收款 | **用户自填微信支付商户号（APIv3 直连）**，资金直接进用户自己账户，平台不经手、不记账 | CRMEB 支持平台电商收付通进件+分账。本方案不做资金归集，因此**没有平台侧资金账本**，只有订单支付状态 |
| 首期范围 | **核心交易闭环**：店铺 + DIY 装修 + 商品多规格 + 分类 + 购物车 + 订单/售后 + 发货 + 会员与地址 + 优惠券 + 微信支付 + 小程序出包直传 | 秒杀/拼团/砍价/限时折扣、分销佣金、积分商城、签到、储值提现、WebSocket 客服、同城配送、直播带货、社区种草、云打印、商户子账号 → 全部列入二期及以后（见 §九） |

一句话产品定义：**每个本站用户都能开一个属于自己的微信小程序商城，装修自己的页面，管自己的商品和订单，收自己的钱，并把小程序一键传进自己的微信账号。**

### 与「私域小程序」共享底座的关系（2026-11-18 决定，已落地）

并行的《私域小程序 · 上门服务小程序工具》方案先把共享层建了出来（迁移 `0117_private_mini_core`）。经需求方确认，**电商侧不再自建凭据表与发布台账，一律上收为共享表**：

| 原本方案 | 现在的归属 |
| --- | --- |
| `mall_wechat_configs`（AppID / Secret / 上传密钥 / 商户号 / APIv3 密钥） | `miniprogram_apps`，按 `scene='MALL' + shopId` 一行 |
| `mall_releases`（出包与直传台账） | `miniprogram_tenant_releases`，按 `scene='MALL' + shopId` 隔离 |
| 契约 `mallWechatViewSchema` / `mallReleaseSchema` 等 | 直接复用 `packages/contracts/src/private-mini.ts` 的 `miniAppViewSchema` / `miniReleaseRowSchema` 等，操作 ID 改为 `Mall_app*` / `Mall_release*` |
| C 端公开寻址键 `slug` | 统一叫 `shopCode`（与 `miniBootstrapSchema.shopCode`、`onsite_shops.shop_code` 同口径） |

**「小程序都是不同的小程序」这条必须在实现与文案上都成立**：

- 一个店铺 = 一个**独立微信小程序主体**，自带 AppID（`miniprogram_apps.app_id` 全局唯一，两个主体不得重复占用）、自带代码上传密钥、自带支付商户号、自带类目/域名/隐私协议。
- 共享的是**机制**而不是**小程序**：出包时按店铺注入 `AppID / shopCode / 品牌名 / 主题色 / 接口基址 / 模块开关`，产出的 zip 各店不同，直传目标是各店自己的微信账号。
- 电商模板 `mall-miniprogram/` 与上门模板 `onsite-miniprogram/` 是**两套独立源码**（不同 scene、不同页面），互不引用。
- 加密上下文串掺入 AppID（底座口径），**跨主体密文不可互解**；平台版小程序（`miniprogram_settings` 单行，站内移动办公壳）与租户主体互不影响。
- 因此首期表数从 19 张降为 **17 张**。

## 三、数据模型（首期 17 张表）

归属口径沿用 `GeoSite`：`ownerUserId`（本站用户，= 商城主人）+ `enterpriseId` / `enterpriseUserId`（代客作业留痕），行内再带 `shopId`。所有业务表都通过 `shopId` 归属到租户，服务层用 `requireShop(user, shopId)` 二次校验，越权抛 `BusinessException(ErrorCode.FORBIDDEN)`。

### 3.1 租户与发布

- **`mall_shops` `MallShop`** — 商城实例（一个用户可开多店，受平台配额约束）。
  `ownerUserId` `enterpriseId` `enterpriseUserId` `name` `slug`(全局唯一，C 端短链 `/api/public/mall/bootstrap?slug=`) `logo` `slogan` `servicePhone` `status`(DRAFT/ONLINE/SUSPENDED/CLOSED) `themeJson`(主色/导航/背景) `tradeJson`(交易配置：自动取消分钟、运费默认、售后开关、积分开关、最低起送) `shareImage` `createdAt/updatedAt` `offBy` `offReason`（平台停服留痕）。
  > 交易参数不另建表：一店一行 JSON，读写同 `GeoSite` 的 `seo` 口径。
> **微信侧凭据与出包台账不在本域建表**（见 §一「与共享底座的关系」）：
> `miniprogram_apps`（`scene='MALL' + shopId`，`app_id` 全局唯一；密钥列为 AES-256-GCM 密文且上下文掺入 AppID，跨主体不可互解，接口只回 `xxxConfigured` 掩码）
> 与 `miniprogram_tenant_releases`（同 scene 按店隔离的版本与直传台账）由底座统一读写。
> 本模块只提供店铺维度入口：`Mall_app*` / `Mall_release*` / `Mall_publishState`。

### 3.2 商品域

- **`mall_categories` `MallCategory`** — `shopId` `parentId` `name` `icon` `image` `level`(1–3) `sortOrder` `enabled`。
- **`mall_products` `MallProduct`** — `shopId` `categoryId` `title` `subtitle` `coverImage` `images`(JSON 串) `detail`(富文本 JSON/HTML) `type`(NORMAL/VIRTUAL) `price` `marketPrice` `costPrice` `stock`（无 SKU 时的库存；有 SKU 时取 SKU 汇总） `sales` `unit` `weight` `volume` `specs`(JSON：`[{name, values:[]}]`，多规格模板) `guaranteeTags`(JSON) `status`(DRAFT/OFFLINE/ONLINE) `isHot` `isNew` `isGood` `sortOrder` `virtualRemark`。
  > **不落 `attr_template` / `product_attr_value` / `product_attr_result` 三张表**：CRMEB 用三张表拼多规格笛卡尔积，本项目用 `specs` JSON + `mall_product_skus` 行做唯一真源，读写更少、双库无差异。
- **`mall_product_skus` `MallProductSku`** — `productId` `shopId` `skuName` `image` `uniqueId` `specValues`(JSON `{规格名:值}`) `price` `marketPrice` `costPrice` `stock` `sales` `weight` `volume` `barcode` `enabled`。索引 `[productId]`、`[shopId, uniqueId]`。
- **`mall_express_companies` `MallExpressCompany`** — `shopId`(0 = 平台预置全量快递) `name` `code` `phone` `enabled` `sortOrder`。
- **`mall_product_reviews` `MallProductReview`** — `shopId` `productId` `orderId` `customerId` `rating`(1–5) `content` `images` `status`(PENDING/PUBLISHED/HIDDEN) `reply` `replyAt` `createdAt`。索引 `[productId, status]`。

### 3.3 顾客域（C 端身份，一店一套）

- **`mall_customers` `MallCustomer`** — `shopId` `openid` `unionId` `nickname` `avatar` `phone` `gender` `level` `points` `balance` `source`(MINIPROGRAM/H5/QR) `referrerCustomerId`(为二期分销预留字段，首期不写逻辑) `status` `lastLoginAt` `createdAt`。唯一索引 `[shopId, openid]`。
  > **顾客不复用站内 `User`**：C 端是租户自己的私域流量，与站内账号体系必须物理隔离，否则 A 店客户会出现在 B 店的用户列表里。
- **`mall_customer_addresses` `MallCustomerAddress`** — `customerId` `shopId` `realName` `phone` `province` `city` `district` `detail` `postalCode` `isDefault` `tag`。
- **`mall_customer_bills` `MallCustomerBill`** — `customerId` `shopId` `type`(POINT_EARN/POINT_USE/BALANCE_PAY/BALANCE_REFUND) `amount` `balanceAfter` `relatedType` `relatedId` `remark` `createdAt`（首期只在下单返积分与退款时写流水，储值/提现二期开）。

### 3.4 交易域

- **`mall_cart_items` `MallCartItem`** — `shopId` `customerId` `productId` `skuId` `quantity` `selected`。唯一索引 `[shopId, customerId, skuId]`。
- **`mall_orders` `MallOrder`** — `shopId` `orderNo`(唯一，`MD` + 14 位时间 + 6 位随机) `customerId` `status`(PENDING_PAYMENT/PAID/SHIPPED/COMPLETED/CANCELLED) `payStatus`(UNPAID/PAID/REFUNDING/REFUNDED) `refundStatus`(NONE/PENDING/APPROVED/REJECTED/DONE) `goodsAmount` `freightAmount` `discountAmount` `payAmount` `pointsDeduct` `pointsReturn` `couponTicketId` `payType`(WECHAT/BALANCE/OFFLINE) `transactionId` `prepayId` `receiverName/Phone/Province/City/District/Detail` `buyerRemark` `sellerRemark` `expressCompany` `expressNo` `shippedAt` `paidAt` `receivedAt` `completedAt` `cancelledAt` `cancelReason` `expireAt`(自动取消锚点) `clientIp` `createdAt/updatedAt`。
- **`mall_order_items` `MallOrderItem`** — `orderId` `shopId` `customerId` `productId` `skuId` `title` `skuName` `image` `price` `quantity` `totalPrice` `refundStatus` `refundedAmount` `reviewed`（**下单快照**，商品改名改价不影响历史订单）。
- **`mall_order_logs` `MallOrderLog`** — `orderId` `shopId` `operatorType`(SYSTEM/CUSTOMER/OWNER) `operatorId` `action` `content` `createdAt`（时间线，供店主端与 C 端共用）。
- **`mall_refund_orders` `MallRefundOrder`** — `shopId` `refundNo` `orderId` `orderItemId` `customerId` `type`(REFUND_ONLY/RETURN_REFUND) `reason` `desc` `images` `amount` `status`(PENDING/AGREED/REJECTED/REFUNDED/CANCELLED) `adminRemark` `rejectReason` `returnExpress` `refundTransactionId` `refundedAt` `createdAt/updatedAt`。

### 3.5 装修与营销

- **`mall_diy_pages` `MallDiyPage`** — `shopId` `name` `type`(HOME/CATEGORY/MINE/ACTIVITY) `components`(JSON 组件树) `styles`(JSON 页面级背景/配色) `coverImage` `isDefault` `status`(DRAFT/PUBLISHED) `publishedComponents` `publishedStyles` `publishedAt` `sortOrder`。
  > 与 `GeoSite.content` / `publishedContent` 同构：**草稿与线上快照分离**，装修改一半不影响用户端。
- **`mall_coupons` `MallCoupon`** — `shopId` `name` `type`(FULL_REDUCE/DISCOUNT) `value`(满减金额 / 折扣百分比) `threshold`(满多少可用) `totalCount` `receivedCount` `usedCount` `perLimit` `validType`(FIXED/DAYS) `startAt` `endAt` `validDays` `scope`(ALL/CATEGORY/PRODUCT) `scopeIds`(JSON) `status` `sortOrder`。
- **`mall_coupon_tickets` `MallCouponTicket`** — `shopId` `couponId` `customerId` `status`(UNUSED/USED/EXPIRED) `orderId` `expireAt` `receivedAt` `usedAt`。唯一索引 `[couponId, customerId]` 配合 `perLimit` 做领取去重（>1 时改用计数校验）。

**首期不做表**：品牌、参数模板、次卡/预售/预约商品、卡密、秒杀、拼团、砍价、限时折扣、积分商城、储值、提现、海报、客服会话、配送站/骑手、直播、社区、发票、子账号 RBAC、商户入驻。

## 四、后端结构

```
backend/src/mall/
├─ mall.controller.ts          // Mall_* / MallAdmin_* 全部方法，方法名 = 契约后缀驼峰
├─ mall.shop.service.ts        // 店铺 CRUD、状态机、配额、tradeJson 读写、requireShop 可见性
├─ mall.wechat.service.ts      // 凭据保存(加密)/掩码回显/连通性测试/access_token 按店取
├─ mall.product.service.ts     // 分类 + 商品 + SKU（含规格笛卡尔积生成、库存汇总）
├─ mall.review.service.ts      // 评价与店家回复
├─ mall.customer.service.ts    // C 端顾客、地址、流水、登录与令牌
├─ mall.cart.service.ts        // 购物车
├─ mall.order.service.ts       // 下单/算价/取消/发货/确认收货/完成 + 单据号
├─ mall.refund.service.ts      // 售后与退款回写
├─ mall.coupon.service.ts      // 券与券票
├─ mall.diy.service.ts         // 装修页草稿/发布/组件校验
├─ mall.release.service.ts     // 出包（调 pack 注入）+ OSS + SHA256 + 直传微信
├─ mall.wechat.client.ts       // 微信开放接口：code2Session / wxacode.getUnlimited / 订阅消息
├─ mall.pay.wechat.ts          // 微信支付 APIv3：JSAPI 下单、签名、回调解密(AES-256-GCM)、退款
├─ mall-crypto.ts              // 凭据加解密（EXTERNAL_CRED_KEY + 上下文 `oem-mall`）
├─ mall.token.ts               // 顾客令牌（独立于站内用户会话）
├─ mall.diy-widgets.ts         // 组件白名单与默认值（前后端共用校验）
├─ mall.public.ts              // /api/public/mall/** 免鉴权路由（bootstrap/login/商品/购物车/订单/支付回调）
├─ mall.scheduler.ts           // 定时：超时未付款自动取消、券/券票过期、库存回补
└─ mall.*.spec.ts              // 单测
```

**接线四处**（照 `geo-site` 逐一对应）：
1. `packages/contracts/src/mall.ts` → `endpoints.ts` 加 `import { mallEndpoints }`、`typeof mallEndpoints &`、`...mallEndpoints`。
2. `backend/src/http/services.ts` 构造服务图 → `services.controllers.mallController`。
3. `backend/src/http/automation-routes.ts` 加 `moduleHandlers('Mall_', c.mallController)` 与 `moduleHandlers('MallAdmin_', c.mallController)`。
4. `backend/src/http/app.ts` 调 `registerMallPublic(app, services)`（与 `miniprogram` 公开路由同一位置）。

**双库兼容硬约束**（本项目 MySQL/PG 同时跑，是踩过坑的地方）：
- 金额一律 `@db.Decimal(12, 2)`，服务层用字符串/分单位整数运算，禁用浮点累加。
- 原生 SQL 只经 `Prisma.sql` + `common/sql-json.ts` 的 `jsonText()`；JSON 列不做跨库函数运算（`scopeIds` 命中判断取回内存里算）。
- 不写 `ON DUPLICATE KEY UPDATE`、不用 `INSERT IGNORE`；幂等靠 `upsert` 或先查后写。
- 单据号沿用项目既有「单据号自增方言适配」口径，不在本模块新造原子自增。
- 结构变更走 `pnpm prisma:migrate:deploy`（新增迁移目录 `0116_mall`），**不用 `db push`**；同步补 `pnpm db:gen:pg`。

### 5.3 C 端 `mall.public.ts`（`/api/public/mall/**`，顾客令牌）
`bootstrap`（按 slug/appId 取店铺+主题+装修发布快照，**免登录**）、`login`（`wx.login` code → openid → 顾客令牌）、`category/tree`、`product/list`、`product/detail`、`review/list`、`cart/*`、`order/preview`（试算）、`order/create`、`order/list`、`order/detail`、`order/cancel`、`order/receive`、`refund/create`、`address/*`、`coupon/available`、`coupon/receive`、`pay/notify/:shopId`（微信回调）、`shop/upload`（头像/图片，走既有 OSS）。

**安全红线**（本项目有 `check:architecture` 与安全不变量守卫）：
- 支付回调验签 + 幂等（同一 `transactionId` 重复回调只生效一次）；金额与订单 `payAmount` 严格比对，不符只记录不改状态。
- C 端所有读写强制 `customerId + shopId` 双条件，**禁止**用请求体传入的 id 直接查（防横向越权）。
- 凭据字段永不出现在任何响应体；日志脱敏。
- `bootstrap` 是公开接口 → 不返回 `appId` 之外的任何凭据痕迹，且按 IP 做限流。
- C 端令牌：`mall.token.ts` 独立签发（载荷含 `shopId`/`customerId`），**不复用** `issueSsoSession`，避免顾客令牌获得站内用户权限面。

## 七、小程序端（`mall-miniprogram/`）

原生微信小程序（**与仓库既有 `miniprogram/` 同构，不引入 uni-app/HBuilderX**，否则平台侧无法自动出包）。

- `config.js`：`{ apiBase, shopSlug, appName, themeColor }` —— 出包时由脚本注入改写。
- 页面：`index`(DIY 首页渲染) `category` `cart` `me` 四个 tabBar；`goods-list` `goods-detail` `goods-search` `order-confirm` `order-pay` `order-list` `order-detail` `order-logistics` `refund-apply` `refund-detail` `address-list` `address-edit` `coupon-list` `coupon-detail` `login` `webview` `diy-page`(活动页) `review-submit` `settings`。
- `components/diy/*`：与 §六 的 14 个组件**一一对应的原生渲染器**；`utils/diy-render.js` 解析发布快照。
- `utils/request.js`：带 `Authorization: Bearer <顾客令牌>`，401 自动静默重登一次。
- 支付：`wx.requestPayment` 参数由 `order/create` 后的 `pay/params` 接口返回（后端用租户商户号签名）。
- 图片上传走平台 OSS（复用既有 OSS 动态配置底座）。

**出包与直传链路**（关键：全部复用已实测过的阶段二能力）：

```
用户点「生成代码包」
  → pack-mall-miniprogram.mjs 等价逻辑（后端内实现，不落 shell）
      读 mall-miniprogram/ 源 → 注入 config.js + project.config.json(appid) → store zip
  → 上传 OSS，落 mall_releases（sha256/size/version）
用户点「上传到微信」
  → 复用 MiniProgramCiService（子进程隔离，密钥只经 stdin，240s 超时）
      appId/uploadKey 来自该店 miniprogram_apps(scene=MALL) 的解密值
  → 成功记 wechatVersion + SUCCESS；失败记可执行中文提示（IP 白名单/密钥不匹配/AppID 不符）
```
文案硬约束：**界面必须写「上传为开发版，提审与发布请在你自己的微信公众平台完成」**，不得让用户误解为上传即上线（沿用既有方案的合规口径）。
下载包入口保留：用户也可下载 zip 自行用微信开发者工具导入。

## 十、已识别风险

1. **工作量**：参考源码 182 表 / 800 页面，首期收敛到 19 表 / 约 95 接口 / 约 11 个前端页 + 约 22 个小程序页面，仍是本项目迄今最大的单模块。按 P0→P8 顺序推进，每期可独立验证。
2. **`miniprogram-ci` 的租户规模风险**（底座能力，电商与上门两个工具共担）：该依赖很重（类型图 300 个声明文件），已用子进程隔离规避主进程崩溃；但每店上传都会拉一个 Node 子进程，需要串行队列（同店互斥、全局限并发数），并在 240s 超时下给出可执行提示。
3. **IP 白名单是人工前置**：微信要求把本服务器公网 IP 加入「小程序代码上传」白名单，且用户须自行操作。必须在上传前检测并给出带操作路径的提示，不能只报错。
4. **资金合规**：用户自填商户号意味着资金流不经过本站，本站只提供软件服务。需在页面明示，并保留平台侧「是否允许收款」开关（未开时下单走线下标记）。
5. **C 端与站内账号物理隔离**：顾客不是站内用户，任何「把 C 端顾客当 User 处理」的捷径都会破坏租户隔离，代码评审需专项盯。
6. **双库**：JSON 列多（`specs`/`components`/`tradeJson`），PG 与 MySQL 的 `->>` 语义差异已由 `sql-json.ts` 兜住，但**新代码不得绕过它自拼 SQL**。
